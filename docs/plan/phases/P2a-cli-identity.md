# P2a — `sweepky-cli`: identity, keys and circle

## Goal

The first part of the `sweepky` binary: the network config and library entry point, `login --identity` with the shared tail of `login`, `keys`, `logout`, the circle, the writers' lock, the config and state directories, and a minimal `init`. It builds on the records, the `Pubky` newtype and the path builders from [P1a](P1a-core-records.md), and on the age keys and secret types from [P1b](P1b-core-crypto.md). The Ring login (option A) follows in [P2d](P2d-cli-ring-login.md).

## Build

- **Network config and entry point.** A library function runs every command given a `Pubky` client, the auth relay URL and the default homeserver; the binary builds those from `--testnet` / `SWEEPKY_TESTNET=1` (testnet client, `http://localhost:15412/inbox`, the testnet homeserver) or the production defaults. The end-to-end test injects an `EphemeralTestnet`'s client instead. The watch list defaults to the selected homeserver.
- **`login --identity <name> [--homeserver <pk>] [--signup-token <code>]` (option B):** local keypair under that name (created or reused), `PubkySigner::signup` then `signin_blocking` on first login, secret in a Sweepky 0600 file, optional scrypt passphrase wrap (`--passphrase-file`, see Notes). Homeserver defaults to the testnet's under `--testnet`, else `homeserver.pubky.app`. On production, warn that this creates a separate public pubky and spends a signup token. Later commands sign in and sign out per run.
- **Shared tail of `login`:** age key generated (on a later login of the same install, reused instead, its record read back and republished if missing; see Notes); `keys/<deviceId>.json` written as the capability probe, mapping 403 ("this identity's signup token does not allow `/pub/sweepky/`; use a dedicated identity") and 507 ("storage quota full") to messages and aborting; device id recorded in the local list of this owner's installs; backup reminder printed. Recovery files (fixed first line) and anything shaped like a raw key or mnemonic are rejected with a one-line reason.
- **Writers' lock.** `post`, `run`, `submit`, `done`, `circle`, `keys` and `logout` take an exclusive `fd-lock` on `~/.config/sweepky/credential.lock` around session restore plus writes, because each restore replaces the grant's bearer. `pull` reads public data without a session except for its one `discovered.json` write, which also takes the lock.
- **`logout`:** mark the device key revoked, then `signout()` (which revokes the grant) or forget the identity, then delete the local files.
- **`circle create|add|remove|show`; `keys list|revoke`.** `keys list` and `pull` compare `keys/` against the list of device ids this owner's own installs created and alarm on unknown ids.
- Config and state under `~/.config/sweepky/` (secrets, install list, pinned owner keys, 0600) and `~/.local/share/sweepky/` (pulled sweeps, groups, cursors); `SWEEPKY_HOME` overrides both.
- **`sweepky init <dir>` (minimal):** creates the directory, writes the `.sweepky` marker and a `.gitignore` containing `sweeps/`, and nothing else. `run` ([P2b](P2b-cli-sweep.md)) requires that marker. The rest of `init` belongs to [P3](P3-skill-and-sandbox.md): the sandbox `.claude/settings.json`, the project `CLAUDE.md`, the skill copy into `.claude/skills/sweepky/`, the playbook install and the launch line.

## Done when

- Unit tests pass for: the requested capability string; the lock serialising two writers; the 403 and 507 mapping to their messages; a recovery file rejected.
- A testnet test logs in a throwaway identity with `--identity`, publishes a key, lists it, revokes it (a second key the test publishes for the throwaway, standing in for another install or an operator; see Notes) and logs out; after `logout` this install's key record has `revokedAt` set, and the identity and its local files are gone. The throwaway identity is not one of A, B or C from the end-to-end test in [06](../06-verification-and-limits.md#verification). The test runs as `#[tokio::test]` + `#[pubky_testnet::test]` over an `EphemeralTestnet` with the HTTP relay, the client injected.
- `cargo clippy -- -D warnings`, `cargo deny check` and `cargo nextest run` clean.

## Resolved questions

- **Signup token for option B on production.** Plain text, three ways to get one ([06](../06-verification-and-limits.md#production-homeserver-as-deployed-on-2026-10-15)). v1 is bring-a-token.

A new `.gitignore` is created the same way holding `sweeps/`; an existing one is appended to only when no line reads exactly `sweeps/` (bytes, split on `\n`), starting a new line first if the file does not end with one, so every existing byte stays. `init` refuses a marker or `.gitignore` that is a symlink or not a regular file, and will not append to a `.gitignore` with a second hard link (that would change the other name too); before reading or appending it checks that the file it opened is the one it inspected (same device and inode).

- Record times, P2a's record (P1a left the encoding to this phase). Sweepky writes every time field, `createdAt` and `revokedAt` here and `startedAt`, `finishedAt` and `doneAt` in later phases, as RFC 3339 in UTC with `Z`, to the second: `YYYY-MM-DDTHH:MM:SSZ`, such as `2026-10-16T09:41:07Z`. `sweepky-core` builds the text with `RecordTime::from_unix_seconds(u64)`, which is pure, so core still reads no clock: Howard Hinnant's `civil_from_days` with checked arithmetic (clippy's `arithmetic_side_effects` lint is on for it), for the years 1970 to 9999, and an `Err` for any later second, because an RFC 3339 year has exactly four digits. The CLI's `clock::now()` reads `SystemTime::now()` against the Unix epoch and drops the fraction of a second; a clock before 1970 or past 9999 is an error message, never a panic. Readers stay opaque, as P1a set out: `RecordTime` never parses a date, has no ordering and accepts any valid value, so a record another client wrote with milliseconds or an offset still reads. [01](../01-records-and-discovery.md) leaves the encoding open and is unchanged.
- Config and state directories, P2a's record (`dirs.rs`). By default the config directory is `$HOME/.config/sweepky/` and the data directory `$HOME/.local/share/sweepky/`. `SWEEPKY_HOME=<dir>` moves both: config to `<dir>/config/`, data to `<dir>/share/`, and `HOME` is then not read. `XDG_CONFIG_HOME` and `XDG_DATA_HOME` are ignored, because the sandbox template denies reads of exactly `~/.config/sweepky` and `~/.local/share/sweepky` ([02](../02-encryption-and-safety.md#sweeper-safety)). The variable in use must be a non-empty absolute path: an empty or relative `SWEEPKY_HOME` is an error, never a fall back to `HOME`, so a script that meant to keep an identity apart never writes into the user's own config, and a missing, empty or relative `HOME` without `SWEEPKY_HOME` is an error too. `main.rs` reads both variables with `var_os` and passes them to `Dirs::resolve`, which touches no file, and the `Context` carries the result; `init`, which needs neither, reads neither. The config layout: `credential.lock` (the writers' lock), `login.json` (which login this install uses), `installs.json` (the device ids this owner's installs created), `device.key` (this install's age identity), and `identities/<name>.key` and `identities/<name>.json` (a dedicated identity's secret and its public details). The pinned owner keys ([P2b](P2b-cli-sweep.md)) and the data directory's subtrees ([P2c](P2c-cli-pull-done.md)) are added by those phases. A directory is created by the first command that writes into it, not at start-up.
- Identity names, P2a's choice (`identity.rs`, replacing the device-id rule this note first recorded): `--identity <name>` is an `IdentityName`, 1 to 32 characters of `[a-z0-9_-]` starting with a letter, so `identities/<name>.key` is always one plain path segment inside `identities/`. Lower case only, because macOS filesystems ignore case by default and `Throwaway` and `throwaway` would be one file; at most 32 characters, so that no raw key (64 hex digits, 43 characters of base64, 52 of z-base32) and no recovery phrase (it has spaces) is ever a valid name. The check's messages never quote the value, which may be a pasted secret.
- Identity material, P2a's record (`identity.rs`). A dedicated identity's secret is its 32-byte Ed25519 seed, held as an `IdentitySecret`: a `Zeroizing<[u8; 32]>` with no `Debug`, `Display`, `Serialize`, `Deserialize`, `Clone` or `PartialEq`, checked at compile time by a copy of core's test-only `assert_not_impl_any!` in `test_support.rs`. It is not held as a `pubky::Keypair`, which is `Clone` and `Debug`; one is made from the seed when signing needs it, and `Keypair::secret()`'s plain copy goes into the `Zeroizing` at once. Its file, `identities/<name>.key`, is Sweepky's own format and never a Pubky recovery file: the line `sweepky-identity/v1`, then the seed as 64 lower-case hex digits, each line ending in `\n`, 85 bytes and nothing else. A file whose first line is that marker (with or without a `\r`) but differs anywhere after it (upper-case digits, a byte too many or too few) is refused as malformed; a first line that starts `sweepky-identity/` with another version is refused as a version this build does not read; anything else goes through the classifier below, so a recovery file or key dropped in as `<name>.key` gets its own reason, and the rest is refused as not a Sweepky identity file. Every one of these messages is fixed text. The hex is written and read without a branch or a table lookup on the secret's value, a best effort the compiler does not guarantee. `MAX_IDENTITY_FILE_BYTES` (4 KiB) is the read cap for both the `--identity` argument's file and an identity file read back through `private_fs`. `identities/<name>.json` holds an `IdentityMeta`, `{"schemaVersion":1,"name":…,"pubky":"<z32>","homeserver":"<z32>","signedUp":true}` plus any fields a newer Sweepky added, read with a 64 KiB cap and with serde_json's messages replaced by the fault's kind and position, through core's `RecordError` conversion as for a record. It is a cache `login` can rebuild from the key and the homeserver; `<name>.key` alone is the Sweepky identity file that [P2c](P2c-cli-pull-done.md) copies.
- Refusal rules, P2a's record. `refuse_secret_material(bytes)` returns a `Refusal`, or `None`: `RecoveryFile` when, after any UTF-8 byte-order mark and leading whitespace, the bytes start with `pubky.org/recovery` or the legacy `pkarr.org/recovery` (the two first lines `pubky-common` 0.16.2's `decrypt_recovery_file` accepts), in any case; `Mnemonic` when the whole input is 12, 15, 18, 21 or 24 whitespace-separated words of letters in any script, at most 16 each; `RawKey` when any token has a key's shape: 64 or 128 hex digits in either case (a seed, or a seed and its public key), 43 or 86 characters of base64 or base64url once the `=` padding is split off, 52 of z-base32, or a string starting `AGE-SECRET-KEY-`, with tokens split at every byte outside the shape's alphabet, one pass per alphabet, so a key inside `KEY=…`, a path or a JSON string counts (a base64 key that itself holds a `/` is missed inside a path, and refused for another reason). Each check is a shape, so it errs towards refusing: what it sees has already failed to be a name or an identity file, so a false match changes only the wording of a refusal. Each `Refusal` prints one fixed line saying what was found, that an identity's secret controls that identity forever and this CLI runs beside agents that read untrusted code, and to use a dedicated identity (`login --identity <name>`) or Pubky Ring instead; no refusal or parse error quotes any of the input. The classifier runs on the `--identity` argument, on the file it names, and on every identity file read back that is not in Sweepky's format. The tests build every key and recovery file at run time (the recovery files with `pubky::recovery_file::create_recovery_file`, under an `#[expect(clippy::disallowed_methods)]` on that one test helper), so no secret is committed.
- The name-before-path rule, P2a's record. `IdentityName::from_arg(value, read_file)` reads `--identity`. A value that passes the name check is a name and nothing else: `read_file` is not called, so a stray file of that name in the working directory is never read in its place. Otherwise, when the value names a regular file, at most 4 KiB of it is read into a `Zeroizing` buffer and classified, giving a refusal's reason or "Sweepky does not import identities; --identity takes a name". `read_argument_file`, the reader the command passes, follows a symlink (the read only ever leads to a refusal), never opens a directory, a device or a FIFO, checks that the file it opened is the one it inspected (device and inode), and reads a file other users can read, because a downloaded recovery file usually is one and the point is to recognise it. Otherwise the text itself is classified, for a key or phrase pasted in place of a name, and failing that the name check's own error is returned. A refusal is the error itself, so a caller can `downcast_ref::<Refusal>()`; [P2d](P2d-cli-ring-login.md)'s end-to-end check passes `--identity <path to a recovery file>` through this.
- Owner-only files (`private_fs.rs`), which every secret and state file goes through. Directories are created 0700 (`DirBuilder` with `mode`, parents included) and files 0600 (`OpenOptions` with `create_new` and `mode` on a temp file beside the target, named from the process id, the clock and a counter), so the mode is set by the call that creates them and never by a later `chmod`; `umask` can only take bits away. A file is written with `write_all` and `sync_all` and then renamed over the target, and the temp file is removed if any step fails. A symlink (dangling or not) or anything but a regular file is refused on read and write, and a directory that is a symlink or not a directory is refused. A directory with any group or other permission bit, and a file being read with one, is refused, not fixed, with the `chmod 700` or `chmod 600` that fixes it, as ssh refuses a loose key; a write replaces whatever regular file is at the target, loose or not, with a new 0600 one, because the rename swaps the whole file and no `chmod` is involved. Ownership is not checked separately, because another user's 0600 file or 0700 directory cannot be opened anyway. A read checks type, mode and size against the caller's cap on the `lstat` before opening, checks after opening that it got the same file (device and inode, as `init` does) and repeats the checks on it, then reads exactly that many bytes with `read_exact` into a zeroed `Zeroizing` buffer that never grows, and refuses a file that grew or shrank meanwhile. A missing file reads as `None`. Removing a missing file counts as success, so `logout` can tidy up a partly missing state; the bytes are not overwritten first, which on SSDs and copy-on-write filesystems would promise more than it does.
- Writers' lock, P2a's record (`lock.rs`). `WritersLock::open(&Dirs)` creates the config directory (0700) if needed and opens `credential.lock` through `private_fs::open_private_lock_file`: read and write, created empty and 0600 with `create_new`, never truncated or replaced, and a symlink, anything but a regular file or a loose mode refused as for every other config file, with the same device-and-inode check after the open. `hold(on_wait, work)` tries `fd_lock::RwLock::try_write` (`flock` with `LOCK_NB`); on `WouldBlock` it calls `on_wait` once, for the caller's "waiting for another sweepky command" line, and tries again after a `tokio` sleep of 10 ms doubling to 500 ms, giving up after 10 minutes with an error naming the file. The blocking `write()` is never called: in-process tests run several commands on one runtime, where it would deadlock. `work` is an async closure run while the lock is held, and the lock is released when it returns, fails or is dropped. It is not a guard-returning `acquire`, because a retry loop that returns `fd-lock`'s guard, which borrows the lock, does not compile under today's borrow checker (`E0499`). A `flock` belongs to an open file, so two `WritersLock`s in one process exclude each other as two processes do, and the kernel drops it when the process exits, so no lock is ever left behind. Nothing deletes or replaces `credential.lock`, `logout` included, because a new file would let a second writer in. The unit tests: two writers on a multi-thread runtime never overlap; a second writer waits while the first holds the lock, and says so once (on a single-thread runtime with a 30-second limit, so a blocking wait fails the test rather than hanging it); the give-up; the file's mode and the symlink refusal. `fd-lock` =4.0.4 adds only itself to `Cargo.lock` (`cfg-if`, `rustix` 1.1.5 and `windows-sys` 0.52.0 were already there), and the tests turn on tokio's `sync` feature for a oneshot channel and a barrier.
- Remote reads and write errors, P2a's record (`remote.rs`). `get_public(pubky, owner, path, cap)` reads anyone's public file through the SDK's public storage, addressed with the `(PublicKey, path)` pair rather than a formatted URL; `get_own(session, path, cap)` reads the signed-in user's own. Both give `None` for a 404 and hand back the body in a `Zeroizing` buffer. Every body goes through `read_capped`: a `Content-Length` over the cap is refused before a byte is read, then the body is read chunk by chunk and refused at the chunk that would cross the cap, which is never copied in; growing the buffer moves it into a new one so the old one is wiped. A record is read with `MAX_RECORD_BYTES` and parsed with its type's capped `from_json`, the only record parser; the SDK's `text()`, `bytes()`, `get_json` and `list().send()` are never used on remote data. `read_capped` takes the response's `content_length()` and an `async || response.chunk().await` closure rather than the response, because the response is `reqwest`'s type and the crate has no `reqwest` dependency to name it with.
- Directory listings, P2a's record. The SDK's `ListBuilder::send()` is not used: in pubky 0.16.2 (`actors/storage/list.rs`) it buffers the whole answer with `resp.bytes()` and decodes it with `String::from_utf8_lossy`, and `.limit()` bounds only what an honest server sends. `list_dir(pubky, owner, dir, limits)` sends its own anonymous `GET` (`pubky.client().request_async(Method::GET, url)`, the path the SDK's public storage uses) to the directory's `PubkyResource::to_transport_url()` with `limit=<page size>` and, after the first page, `cursor=` the last entry's `pubky://` URL. It checks the status itself: a 404 is an empty directory (the homeserver answers 404 "Directory Not Found" for one with nothing in it, confirmed on an `EphemeralTestnet` on 2026-10-16), any other non-2xx an error naming the status alone, whose body is never read. Each page is read through `read_capped` with a cap of page size × (4096 + 2) bytes and parsed by `ListingParser`: lines split at `\n` with one `\r` dropped and trimmed, blank lines ignored; a line over 4096 bytes, not UTF-8 (never decoded lossily) or not a `pubky://` or `https://` resource URL refuses the listing, and so do a page with more entries than asked for and a listing past `max_entries` or `max_pages`. An entry of another owner (compared as keys, by bytes) or outside the directory is skipped and counted, and so is one `SweepkyPath::parse` refuses, such as a `keys/` name that is not a valid device id. A page with fewer entries than asked for is the last; a full page continues from its last entry of this owner inside the directory, and a full page with none is refused. `ListLimits::DEFAULT` is 100 entries a page, at most 1000 entries in 11 pages. A page size outside 1 to 1000 is refused before any request, because the homeserver quietly sends at most 1000 whatever `limit=` asks for, and a capped page would read as a short last page and cut the listing off. `url` =2.5.8 becomes a direct dependency for the `Url` these take ([03](../03-cli-and-skill.md#dependencies)).
- Write errors, P2a's record. `write_refusal` maps a 403 to "the homeserver refused the write (HTTP 403): this identity's signup token does not allow `/pub/sweepky/`; use a dedicated identity" and a 507 to "the homeserver refused the write (HTTP 507): storage quota full; use a dedicated identity", for `login`'s key write to abort with; every other error goes through `request_error`. Neither quotes the server's error body or a request URL: a homeserver's answer is shown as its status and the `http` crate's reason for it, a transport error as "network error" with "timed out" or "could not connect" and any status, and the rest as fixed sentences. The SDK's own `Display` of a transport error includes the URL, and its server error carries the server's text, so neither is ever printed.
- Terminal sanitiser, P2a's record (`display.rs`), for P1a's carry-forward note to P2c, applied here to key labels and circle names and labels. `sanitize(text, max_chars)` writes as visible `\u{..}` escapes every control character (C0, DEL, C1, so ESC and every escape sequence it starts), the separators U+2028 and U+2029, every Unicode 16.0 format character (`Cf`: the bidi controls U+061C, U+200E/F, U+202A–202E and U+2066–2069, the zero-width characters, U+FEFF, U+00AD, the tag block and the rest), every other default-ignorable code point and the noncharacters; it doubles a backslash so no stranger can write a lookalike escape; and it shows at most `max_chars` characters of the text (`MAX_LABEL_CHARS`, 64, for labels and names), counted as characters, then `…(truncated)`. Ordinary text, accents, other scripts and emoji are unchanged, except that an emoji built with U+200D or a variation selector shows those as escapes.
- `login --identity`, P2a's record (`login.rs`). The argument is classified first (`IdentityName::from_arg`), and `--homeserver` is read as text and parsed by `login` with the SDK's `PublicKey` (which checks the Ed25519 point), not by clap, whose parse error would quote the value; the error is fixed text. Then, under the writers' lock, a pure `plan_login` decides from the network kind, the default homeserver, the flags, what is on disk and `login.json`: (1) when `login.json` names a pubky, only that identity may log in again, and anything else (a new identity included) is refused with "run `sweepky logout` first … or set SWEEPKY_HOME to another directory"; (2) a new identity, or a key with no pkarr record, signs up on `--homeserver` or else the network's default; a known identity stays on the homeserver its details name, a key without details on the one its pkarr record names, and a `--homeserver` that names another one is refused, never followed; (3) a signup on the production network's default homeserver (homeserver.pubky.app) without `--signup-token` is refused with the three ways to get one (Homegate by SMS, Google or Lightning; the `st` parameter of pubky.app's copy-sign-up link; `pubky.app/invite/<code>`) and the note that a free IP-verification token allows only Paykit and Bitkit paths; another homeserver on production is not assumed to need one, and its own answer says so if it does; (4) every signup on the production network prints the warning that it makes a separate public pubky, not the one in Ring, plus "and the signup spends your signup token" when a token goes with it, on standard error before any identity file is written or the signup sent (only the writers' lock file and, for a key without details, its pkarr lookup come first); the testnet and an injected network never warn. A new identity's secret file and then its details with `signedUp: false` are written before the signup, so a crash never loses a spent token, and `signedUp` becomes `true` after it. The token is held as a `SecretString` from the moment clap parses it (a `value_parser`), so `Command` has no `PartialEq` and its `Debug` shows `[REDACTED]`; it reaches the SDK only as the `Option<&str>` `signup` takes. A failed signup prints fixed text and the HTTP status (with a hint to check the token for 400, 401 and 403), or `request_error`'s fixed category when there is no status, never the SDK's message: a transport error's `Display` holds the request URL, and the URL's query holds the token. Then `signin_blocking` with `CLIENT_ID`, `login.json` is written (keeping its unknown fields when the same identity logs in again), and the session is signed out; a sign-out that fails is a warning. A token passed when no signup is needed is not sent, and the report says it is still unspent. `login` without `--identity` says "the Pubky Ring sign-in arrives in a later build; use --identity <name>" until P2d.
- "Already registered" is HTTP 409, P2a's record, confirmed on an `EphemeralTestnet` on 2026-10-16 (the end-to-end test's fourth step) and in pubky-homeserver 0.16.2's source: `create_user_in_tx` checks for an existing account before it looks at the token and answers 409 "User already exists". `login` counts a 409 as a finished signup. The SDK's `signup` publishes the identity's pkarr record only after a 2xx, and `signin_blocking` needs that record to find the homeserver, so after a 409 `login` publishes it itself (`signer.pkdns().publish_homeserver_force(Some(homeserver))`), which also mends a crash between a signup and its pkarr publish.
- The copied key file, for [P2c](P2c-cli-pull-done.md): copying `identities/<name>.key` alone into another `SWEEPKY_HOME` is enough. `login --identity <name>` there finds the key without its details, resolves the identity's homeserver from its pkarr record (`get_homeserver_of`), writes the details with `signedUp: true` and signs in, with no signup and no token. `--homeserver`, if given, must name the same homeserver. A key whose pkarr record resolves to nothing is treated as never signed up and signs up on `--homeserver` or the default, a 409 counting as done. The other install has its own `login.json` (and, with the shared tail, its own device key).
- `login.json`, P2a's record (`state.rs`): `{"schemaVersion":1,"kind":"identity","name":"<name>","pubky":"<z32>","homeserver":"<z32>","deviceId":"<id>"}` plus any fields a newer Sweepky wrote, which are kept on rewrite. `kind` is an open-string enum (`LoginKind` with `as_known()`); P2d adds the Ring kind, and `name` is left out for a login without one. `deviceId` is written once the shared tail of `login` has published this install's key, and left out until then, so a `login.json` never names a key that is not published. The file holds public values only; no secret is ever added to it. It is read with a 64 KiB cap. An identity's details without its key file are refused (the secret is gone), and so are details that name another identity or another pubky than the key's; a key file that is a recovery file, a raw key or a phrase gets its `Refusal`.
- Device keys, P2a's record (`device.rs`). A device id is `RecordId::from_timestamp(Timestamp::now())` written out: 13 characters of upper-case Crockford base32, such as `0035G87EK4XFE`, which is always a valid `DeviceId`, sorts by when the install was made, and carries pubky-timestamp's random per-process clock byte, so two installs that start in the same microsecond still differ. `new_device_id` asks `clock::now()` before it reads `Timestamp::now()`, because pubky-timestamp's `now()` panics on a clock before 1970 and `clock::now()` refuses one with a message; the check is inside it so no caller can forget it. The record is `{"schemaVersion":1,"alg":"age-x25519","recipient":"age1…","label":"sweepky-cli","createdAt":"<RFC 3339>","revokedAt":null}`, core's `DeviceKey` written as compact JSON. The label is the fixed `sweepky-cli` for every install, because `keys/` is world-readable and a host name there would tell everyone what the owner's machines are called. `device.key` holds `DeviceIdentity::to_secret_string()` and nothing else: the 74 bytes of the age identity string, no newline, 0600 through `private_fs` (a temp file, then a rename). It is never written over: anything at the path, a symlink included, is refused with "already holds a device key that login.json does not record; Sweepky never replaces a device key … Move the file somewhere safe and run `sweepky login` again", because that key may be the only one that opens the sweeps encrypted to it. It is read back with a 4 KiB cap (the wrapped form is 256 bytes), unwrapped first when it is wrapped (the passphrase note), into a `SecretString` and `DeviceIdentity::from_secret`, every error fixed text. With `--passphrase-file` the file holds that string wrapped with the passphrase instead.
- `installs.json`, P2a's record (`installs.rs`): `{"schemaVersion":1,"owners":{"<owner z32>":["<deviceId>",…]}}` plus any fields a newer Sweepky wrote, kept on rewrite. Each owner's ids are in the order they were made, an id is recorded once (recording it again does not write the file), and an owner goes with its last id; it is read with a 64 KiB cap and holds public values only. For [P2c](P2c-cli-pull-done.md): the list is local, so it knows only the ids that installs sharing this config directory made. A second install of the same owner on another machine sees the first install's key under `keys/` as unknown and alarms on it (and the first install alarms on the second's) until the lists are joined. P2c has to settle how, without simply accepting whatever ids `keys/` holds at some moment, since an injected key is exactly what the alarm is for.
- The shared tail of `login`, P2a's record (`login.rs`). It runs between the sign-in and the sign-out when `login.json` records no device id for this pubky (a first login on this `SWEEPKY_HOME`, an earlier tail that rolled back, or a `login.json` from before the tail), in this order: (1) a new `DeviceIdentity`; (2) its secret in `device.key`, before anything is published, so a crash never leaves a published key nothing can open; (3) its id in `installs.json` under the owner, also before the write, so the owner's own key never shows up as unknown; (4) the PUT of `keys/<deviceId>.json` with the session, the capability probe, its error mapped by `write_error` (403 and 507 to the two messages above, anything else to `request_error`'s fixed text, never the server's words). On any failure after step 2 it removes `device.key` and then the install entry (that order, so an interrupted rollback leaves a stale id rather than a key file `login.json` does not record), never anything it did not make in that run, keeps the identity and its details, leaves `login.json` as it was, and aborts with "could not publish this install's device key, so login removed it again: <reason>" (or names what it could not remove). A `device.key` that is already there is refused in step 2, before there is anything to roll back, and nothing is published. On success the device id goes into `login.json` (a failure of that write is reported and undoes nothing: the key is published and its secret stays) and the report adds "Published this install's device key as keys/<id>.json" and the reminder "Back up <config dir> the way you would an SSH key: it holds this install's device key, and losing that file loses every sweep encrypted to it that you have not pulled yet". When `login.json` already records a device id for this pubky, the tail reuses that key instead (the next note). After the tail, on either branch, `login` checks `keys/` for ids this owner's installs did not create (the `keys list|revoke` note). A write that fails without a status (a timeout, say) may still have landed; the rollback then leaves a published key with no secret behind it, which is not in `installs.json`, so `keys list` will show it as unknown and `keys revoke` retires it.
- Reusing this install's device key, P2a's record (`login.rs`, `reuse_device_key`). A later `login --identity <same name>` on an install whose `login.json` records a device id for this pubky keeps that key and id, so an install has one age key ([00](../00-overview.md#decisions-locked)): a new key would orphan every sweep encrypted to the old one and leave its `keys/<id>.json` unrevoked beside a second. Login never writes over or deletes `device.key`. It runs in the same lock and session as the rest of `login`, in this order: (1) `device.key` is read (`read_device_key`, 4 KiB cap). Missing, it is refused with "`<path>` is missing, but login.json records it as the secret of this install's device key keys/`<id>`.json, so login changed nothing: restore `<path>` from your backup, or run `sweepky logout` to retire keys/`<id>`.json"; unreadable (not an age identity, a loose mode, a link), with the same two ways out after its own reason. Either way before any request. Only the recipient is kept; the secret is dropped before the network is used. (2) `keys/<id>.json` is read back with `get_own_key` (`MAX_RECORD_BYTES`) and parsed by core's `DeviceKey::from_json`. Absent: it is published again with the local recipient and a new `createdAt`, the capability probe once more, so 403 and 507 get their messages, and a failure undoes nothing, `device.key` included. Present, it is checked in this order: revoked (`revokedAt` set) is refused with "is revoked … Run `sweepky logout` to retire it, which also forgets this identity: giving an identity a new device key on an install is not part of this build" (with `--identity`, `logout` forgets the identity, so key rotation is outside P2a); then `encryption_recipient()` must succeed and equal the local recipient, compared as `AgeRecipient` values, never as the record's text. Anything else (not a record, another `alg`, a recipient that fails the strict parse, another key) is the alarm of [02](../02-encryption-and-safety.md#who-can-read-a-sweep): "alarm: keys/`<id>`.json, this install's own device key record, does not hold this install's key: someone other than this install wrote it, with this identity's credentials or as an operator of its homeserver …", pointing at `logout` to revoke it, with core's fixed reason after it. A refusal changes nothing locally or remotely, and no message holds a recipient or the server's text, only the device id. A matching record is reused with nothing written to the homeserver. (3) The id goes back into `installs.json` if it is missing there (the file deleted or restored from an older copy), so the owner's own key never reads as unknown; this comes last, so a refusal leaves the file alone. `record_install` writes nothing when the id is already listed, so a plain second login rewrites only `login.json`, with the same id. The report says "Reusing this install's device key, keys/`<id>`.json", or that it was published again. Any earlier step of `login` that mends the identity's own files (its details rebuilt, `signedUp` set) has run by then and stays. Step (1) reads a wrapped `device.key` through the passphrase note's unwrap path; without `--passphrase-file` it is refused with how to give it and "login changed nothing", rather than the backup advice, because the file is fine.
- The key-store seam, P2a's record (`device.rs`). Two small crate-private traits of `async fn`s. `PublicKeys` reads anyone's `keys/` with no session: `list_key_ids(owner)` (public `remote::list_dir` of `keys/` with `ListLimits::DEFAULT`, the device ids and a count of the entries skipped) and `get_key(owner, id)` (public `remote::get_public` of `keys/<id>.json`, capped at `MAX_RECORD_BYTES`). `KeyStore: PublicKeys` (a supertrait, so every key store reads public storage too) adds `get_own_key(id)` (the user's own `keys/<id>.json` through `remote::get_own`, capped at `MAX_RECORD_BYTES`) and `put_key(id, bytes)` (the session's PUT, handing the SDK's error back so the caller maps it). `PublicKeyReader` (on the client alone, for `keys list`) and `SessionKeyStore` (on the signed-in session and the client, its public reads going through a `PublicKeyReader`) are the real ones; callers take `&impl PublicKeys` or `&impl KeyStore`, because a trait of `async fn`s cannot be a `dyn` object. The unit tests use `test_support::FakeKeyStore`, which implements both, keeps one owner's records in memory (its listing is every record's id, skipping none), logs every call and can refuse every PUT with a given status and its own server text, which the tests check no message repeats. `login` uses `put_key`, `get_own_key` when it reuses an existing key, and `list_key_ids` and `get_key` for its check of `keys/`; `keys list` uses `PublicKeys` alone and `keys revoke` `get_own_key` and `put_key`. The fake also lets a test read what a record holds and put one in place behind the CLI's back (`record`, `set_record`, neither logged as a call).
- `keys list|revoke`, P2a's record (`keys.rs`, with the comparison and the alarm text in `installs.rs` so that [P2c](P2c-cli-pull-done.md)'s `pull` reuses them). **`keys list`** takes no session and no lock: it reads `login.json` (whose pubky it lists; not logged in is an error) and `installs.json`, which every writer replaces whole with a rename, and the rest is public storage through `PublicKeyReader`. It lists `keys/` (`list_key_ids`: paged and capped, names that are not a valid `keys/<deviceId>.json` skipped and counted, as the listing note says; a line that breaks the protocol refuses the listing, so `keys list` fails rather than show part of it), reads each listed record (`get_key`, `MAX_RECORD_BYTES`), each id once, and parses it with `DeviceKey::from_json`. A record that is gone or does not parse is not listed: it gets a warning naming its device id and the fixed reason. Each unrevoked record goes through `DeviceKey::encryption_recipient`, the one way from a record to a key; one that fails (another `alg`, or a recipient that fails the strict parse) is marked unusable, with a warning naming the device id and core's fixed reason, never the recipient. A revoked record is shown as revoked and not checked. The result is a typed `KeyListing` (per key: id, label, alg, `createdAt`, `revokedAt`, why it is unusable, whether it is this install's and whether it is unknown; the unreadable ids; the count of skipped names; the alarms), which the tests read and whose `render` is the text printed, one line per key (`keys/<id>.json: <this install | another install made here | UNKNOWN: not created by this owner's installs here>; <in use | revoked <time> | unusable: this build cannot encrypt to it>; alg …; label …; created …`), then the warnings, the skipped count and the alarms. Every string a record holds (`label`, `alg`, `createdAt`, `revokedAt`) goes through `display::sanitize` (`MAX_LABEL_CHARS` for the first two, `RecordTime::MAX_LEN` for the times); device ids and the pubky are printed as they are, as a `DeviceId` holds only `[A-Za-z0-9_-]`. No recipient is ever printed. **The alarm** ([02](../02-encryption-and-safety.md#who-can-read-a-sweep)): `installs::unknown_key_ids(created, listed)` gives the listed ids not among the ids this owner's installs created, compared as `DeviceId` values (the owner's entry in `installs.json` is found by key bytes); `keys list` counts `login.json`'s own device id as created too, so this install's key never reads as unknown if `installs.json` lost it. An unknown id raises `installs::unknown_key_alarm`, "alarm: keys/<id>.json is a device key that this owner's installs here did not create …", naming an operator of the homeserver or a leaked grant, with the fix (`sweepky keys revoke <id>`; if a grant may have leaked, also revoke it in Pubky Ring and log in again) and the note that a key published from another machine shows up too, because the list is local. P2a's choice: an unknown id whose record reads and is revoked is still marked `UNKNOWN` but raises no alarm, since revoking is the fix the alarm asks for and a revoked key takes no further sweeps; a record that is gone or cannot be read still alarms, so nothing unchecked passes for settled, and a revoked record rewritten as unrevoked alarms again. 02 now says so. **At `login`**, after the shared tail on either branch and before the sign-out, `keys::unknown_key_alarms` lists `keys/`, reads only the unknown ids' records, and the report gets one alarm per id; a check that cannot run (the listing or `installs.json` fails) is a warning in the report pointing at `keys list`, never a failed login, because the key is published and `login.json` written by then. **`keys revoke <deviceId>`** reads the id as text and checks it with core's `DeviceId` (whose error never quotes it), then inside `with_writer_session` (the writers' lock, a fresh sign-in and an always-attempted sign-out) reads the user's own `keys/<id>.json` (`get_own_key`, `MAX_RECORD_BYTES`), parses it, and sets `revokedAt` to `clock::now()`, writing the record back with `put_key` as compact JSON: core's `DeviceKey` keeps unknown top-level fields in its `#[serde(flatten)]` map and every known field with the value it was read with, so only `revokedAt` changes. A record already revoked is left as it is and not written, so revoking twice keeps the first time. A missing record ("does not exist … `sweepky keys list` shows this identity's device keys") or one that does not parse is an error and nothing is written; a refused write is mapped by `write_error`. Revoking this install's own key is allowed, and the report then says to run `sweepky logout`, because giving an install a new device key is not part of this build.
- The per-command session, P2a's record (`session.rs`). `with_writer_session(ctx, async |signed| …)` takes the writers' lock, reads `login.json` and the identity it names (its key file alone is enough), checks the key is the pubky logged in, signs in with `PubkySigner::signin(CLIENT_ID)`, runs the body with a borrowed `WriterSession` (the session and the login state, no `Debug`), and then always attempts `signout()`, whether the body succeeded or failed, reporting a failed sign-out as a warning; the body's own result is returned. P2d adds the Ring restore branch. `with_writers_lock` (the lock plus the "waiting for another sweepky command" line) is what `login` holds. Its unit test runs on its own `EphemeralTestnet`: no login means the body never runs; a body that writes and then fails gets its error back, and a copy of its session can no longer write afterwards (the grant is revoked); the next call signs in afresh.
- Warnings and progress lines go to `Context::stderr`, a `StderrWriter` (a `Mutex<Box<dyn Write + Send>>`) that `main.rs` builds around standard error and the tests around a shared buffer, so a warning comes out before the action it warns about while the report is printed at the end.
- The end-to-end test (`tests/end_to_end.rs`), P2a's steps, which `logout` completes: one `#[tokio::test]` + `#[pubky_testnet::test]` function over `EphemeralTestnet::builder().with_http_relay().build()`, with `Network::injected(testnet.sdk(), "<relay>/inbox", the testnet homeserver)` and a temporary `SWEEPKY_HOME`. (1) `login --identity throwaway` signs up and logs in; a fresh client resolves the identity's pkarr record to the testnet homeserver; the config and `identities/` directories are 0700 and the key, details, `login.json` and `credential.lock` files 0600. (2) A second `login --identity throwaway` does not sign up again: it passes a signup token in a form the homeserver rejects with 400 before anything else, so a signup would have failed, and the details are unchanged. It reuses the device key: its report says so, `login.json` names the same device id, `device.key` holds the same bytes, and an anonymous listing of the identity's `keys/` holds exactly that one record. The test sends the listing's `GET` of the directory itself and reads the body under a cap of a 100-entry page, because `remote::list_dir` is private to the crate and an integration test cannot call it. (3) With the details file deleted, `login` rebuilds it from the key and the pkarr record, again without a signup. (4) With `signedUp` set to `false`, `login` signs up, gets 409 and records it as done. Nothing is written to standard error on the testnet. Step (1) also checks the shared tail: `login.json` names a device id; `device.key` is 0600 and exactly the 74-byte identity string; `keys/<deviceId>.json` is readable anonymously through a fresh client, read within `MAX_RECORD_BYTES` (the `Content-Length` and then every chunk checked against the cap), parses with `DeviceKey::from_json`, has `revokedAt` null and the label `sweepky-cli`, and its recipient is the recipient of the local `device.key`; `installs.json` (0600) lists the id under the owner; and the report carries the backup reminder naming the config directory. After step (4), `login.json` still names that first device id and it is the owner's only install: the later logins made no key. (5) `keys list` lists this install's key as in use, with no alarm. (6) The test publishes a second record, `keys/another-install.json`, for the throwaway, signed in with the identity's own root key, standing in for another install or an operator; it carries a field this build does not know. The library keeps its identity-file reader private, so the test reads the documented `sweepky-identity/v1` file itself into wiping buffers and signs in and out with the SDK. (7) `login --identity throwaway` keeps the same device id and its report raises the alarm for `another-install`, with `sweepky keys revoke another-install`. (8) `keys list` lists both, flags `another-install` as unknown with the alarm, and prints neither recipient. (9) `keys revoke another-install` sets its `revokedAt` and keeps every other field, the unknown one included, as an anonymous read shows; this install's record keeps `revokedAt` null, and `keys list` then shows `another-install` as unknown and revoked, with no alarm. (10) `circle create "Throwaway circle"`, then `circle add pubky<z32> --label "synthetic member"` of a key made at run time (`Keypair::random()`); an anonymous read of `circle.json` parses with `Circle::from_json` and lists the admin in `members`, then the member with its label; `circle show` lists the admin, marked `(admin)`, and the member; `circle remove` of the member's raw z-base32 removes it (the same key in the other spelling), and `circle show <admin>` then lists the admin only. (11) `logout` revokes this install's key, as an anonymous read of `keys/<deviceId>.json` shows (`revokedAt` set, the same recipient), and the throwaway's key and details, `device.key`, `login.json` and the owner's entry in `installs.json` are gone, while `credential.lock` stays; `keys revoke x` then fails with "not logged in". - "Revokes it" in Done when, P2a's reading: in the end-to-end test it is `keys revoke` of the second key the test publishes for the throwaway in step (6), not of the key `login` published. That key is left for `logout`, so the check after `logout` that this install's record has `revokedAt` set proves that `logout`'s own revoke ran, rather than passing because `keys revoke` had set it already. The same steps exercise the unknown-key alarm in `keys list` and at `login`.
- A `keys/` entry spelled with `..`, P2a's record. In the `pubky://` form, which the homeserver writes, `keys/../x.json` is no resource URL at all (the SDK's `ResourcePath` refuses `.` and `..` segments), so, like any line that breaks the protocol, it refuses the whole listing and `keys list` fails, rather than being skipped. In the `https://` transport form the URL parser resolves it to `/pub/sweepky/x.json`, outside `keys/`, so it is skipped and counted, and `keys/%2E%2E/x.json` is a plain name in a subdirectory, skipped too. `keys::tests::invalid_key_names_are_skipped_not_fatal` pins all three.
- `circle create|add|remove|show`, P2a's record (`circle.rs`). The arguments are read as text and checked before the lock: a pubky by core's `Pubky` parse (either spelling), then the SDK's `PublicKey` parse, which checks the Ed25519 point, every message fixed text; a name (`create <name>`) or a label (`add --label <label>`) must be 1 to 64 (`MAX_LABEL_CHARS`) characters, not only spaces, that `display::sanitize` gives back unchanged: no control, format, invisible or noncharacter, and no backslash, which the sanitiser doubles, so whatever Sweepky publishes in a circle shows as it was written. Then, inside `with_writer_session`, `get_own` reads `circle.json` (`MAX_RECORD_BYTES`), a pure `apply` parses it with `Circle::from_json`, changes it and writes it as compact JSON (refused over `MAX_RECORD_BYTES`, which no Sweepky would read back), and the session PUTs it, a refusal mapped by `write_error`. `create` writes `{"schemaVersion":1,"name":…,"admin":"<me>","members":[{"pubky":"<me>"}]}`, the admin in `members` too (P1a's carry-forward note), and refuses when any `circle.json` is there, one that does not parse included, because it may be the only copy. `add` and `remove` refuse, leaving the record as it is, when there is none (pointing at `create`), when core cannot parse it, and when its `admin` is not the signed-in pubky (compared by bytes): `is_in_roster` would count that other key as in the roster, and a rewrite would keep the claim. `add` finds the member by key bytes; when it is there, nothing is written unless `--label` brings a new label, which replaces the old one in place; otherwise a new entry goes last. `remove` refuses the admin and a key with no entry, and drops every entry of the key. Unknown fields at the top level and in each member survive both, through core's `#[serde(flatten)]` maps. `circle show [<admin>]` reads the `circle.json` of the given pubky, or of `login.json`'s, from public storage with no session and no lock, parses it with core and prints `Circle: <name>`, `Admin: <admin>`, `Members (<n>):` and one line per member (`  <z32>`, then ` (admin)` for the admin and `, label <label>`), the name and the labels through `sanitize` with `MAX_LABEL_CHARS`, the pubkys from the parsed keys; a record whose `admin` is not the pubky whose storage holds it gets a warning line. A missing `circle.json` is an error that names `circle create`. The lock serialises one install's commands; two installs of one admin changing the circle at once is last-writer-wins, as for a bounty ([01](../01-records-and-discovery.md#the-bounty-post)).
- `logout`, P2a's record (`logout.rs`), [02](../02-encryption-and-safety.md#device-keys)'s order, all under the writers' lock. (1) `login.json` is read (none is "not logged in, so there is nothing to log out of"), and a `device.key` that `login.json` does not record is refused before anything else, with nothing changed: logout cannot revoke a record without its id, and deleting that key and then the only identity that could revoke its record, which may be published, is what the order exists to prevent. Then a fresh sign-in with the identity. (2) This install's `keys/<deviceId>.json` is revoked with `keys revoke`'s read-modify-write (`keys::revoke_if_published`), every other field kept. Revoked already: left as it is, not written. Not on the homeserver (404): nothing to revoke, and logout goes on, because no sweeper can encrypt to a record that is not there (P2a's choice; `keys revoke` still refuses an id with no record). A record this build cannot parse is an error, as in `keys revoke`. A `login.json` with no device id (a login whose key write rolled back) has nothing to revoke. (3) The session is signed out, always, even when (2) failed; a failed sign-out is a warning on standard error and logout goes on. If the sign-in or (2) failed, logout stops here with every file as it was: "logout deleted nothing, and this install is still logged in …", pointing at `sweepky keys revoke <id>` from another install of the identity, after which this install's `logout` finds the key revoked already. (4) The identity is forgotten: `identities/<name>.json`, then `identities/<name>.key`, in that order so a failure in between leaves the key alone, which the next `logout` still signs in with; a failure here stops logout with the rest kept. (5) `device.key` (a missing one is fine: it is the way out `login` gives when that file is gone), `login.json` and the owner's whole entry in `installs.json` (`installs::forget_owner`, which writes nothing when there is no entry) are deleted, each tried even when one fails, and the error names what is left to delete by hand. `credential.lock`, other identities and other owners' entries stay. Every deletion is `private_fs::remove_private_file`, an unlink that never follows a link and does not overwrite the bytes, which on an SSD or APFS would not reach the old blocks anyway; the report says the files were deleted, not overwritten, and that sweeps encrypted to this install's key that were not pulled can no longer be opened. `retire` runs steps 2 to 5 with the revoke and the sign-out passed in as async closures over a generic session, lent to the first and moved into the second, so the unit tests run them against `FakeKeyStore` without a homeserver. `session::sign_in` and `WriterSession::sign_out` are crate-visible for it, because `with_writer_session` signs out only once its body returns, and logout's deletions must come after the sign-out and inside the lock. P2d adds the Ring branch to steps 3 and 4: revoke the grant, check that a restore gets a 401, and delete the saved token instead of an identity.
- The passphrase wrap, P2a's record (`sweepky-core`'s `crypto/passphrase.rs`; the CLI's `passphrase.rs`, which needs only core and `private_fs`, so `identity`, `state` and `device` read and write through it without depending on `session`). It wraps a dedicated identity's key file and `device.key` with the pinned `age` and its default features alone: `age::scrypt::Recipient` with `set_work_factor`, through `Encryptor::with_recipients`, to write, and `age::scrypt::Identity` with `set_max_work_factor` to read; no second key-derivation crate, no armor, no plugin. Not `Encryptor::with_user_passphrase`, which [02](../02-encryption-and-safety.md#device-keys) first named: it calibrates the work factor to about a second on the writing machine and does not say which it picked, so a fast machine could write a file above the read cap; 02 now says so. **Core.** `WorkFactor` holds a `log_n` from 1 to 20, checked when it is made, because age's `set_work_factor` panics on 0 and on 64 and above. `WRITE_WORK_FACTOR` is a fixed 18 (256 MiB, about a second) and `MAX_WORK_FACTOR`, the read cap, 20 (1 GiB), with a compile-time check that the write factor is at most the cap and the cap at most 22, above which age's own docs warn of hours and tens of GiB. `wrap_with_passphrase(plaintext, &SecretString, WorkFactor)` returns a `Result<Vec<u8>, PassphraseError>`, not a bare `Vec` as first planned, because age's encryptor is fallible and nothing here may panic; it refuses a secret over `MAX_SECRET_BYTES` (1 KiB) and an empty passphrase, and writes binary age with one scrypt stanza, exactly 182 bytes longer than the secret. `unwrap_with_passphrase(bytes, &SecretString)` returns a `Zeroizing<Vec<u8>>` after these checks, in order: the length against `MAX_WRAPPED_BYTES` (4 KiB, the CLI's read cap for both files), armor (refused by name), age's header parse, that the header holds one scrypt stanza and nothing else (`is_scrypt`, before the scrypt identity is made, so an X25519 file costs nothing), the stanza's work factor against the cap (age's own check, before it runs scrypt), the key (a wrong passphrase), then the payload, read into one buffer allocated at `min(length, MAX_SECRET_BYTES + 1)` that never grows. The cap is a private `unwrap_with_cap`, which the tests call at 10. `PassphraseError` holds no data, and age's errors are matched by variant, never formatted. `looks_wrapped(bytes)` is the test of a file's first bytes, `age-encryption.org/` or `-----BEGIN AGE ENCRYPTED FILE-----`, which neither plain format can start with. age's `Recipient::new` and `Identity::new` each run its calibration, one scrypt at 10 (about a millisecond in a release build), which cannot be skipped. **The flag.** A global `--passphrase-file <path>`, P2a's choice, meant for process substitution (`--passphrase-file <(pass show sweepky)`): the passphrase stays out of the argument list, the shell history and the disk, and standard input stays free for [P2b](P2b-cli-sweep.md)'s prompts. An interactive prompt that does not echo is deferred, because it needs a new crate or `unsafe` terminal calls. For every command but `init`, `main.rs` reads the file with `Passphrase::from_file` into `Context::passphrase` before it builds the network, and `run` refuses a command line with the flag whose context has no passphrase, so a caller cannot drop it and leave files written plain. The file is opened following links (Linux's `/dev/fd/63` is one); a directory is refused, and so is a regular file with any group or other permission bit, with the `chmod 600` that fixes it (a pipe is not checked); at most 1027 bytes are read into a wiped buffer that never grows. It holds exactly one line: the passphrase, then optionally `\n` or `\r\n`, and nothing after (a pass entry with notes needs `| head -n 1`), 1 to 1024 bytes of UTF-8, because age's scrypt takes text, kept exactly, spaces included; empty is refused. The passphrase is copied once, at its exact length, into a `SecretString`. `Passphrase` has no `Debug`, `Display`, `Clone`, `PartialEq` or serde impls (checked at compile time) and carries the work factor it wraps at, always `WRITE_WORK_FACTOR` outside the tests, whose `for_tests` constructor wraps at 10. No message quotes the passphrase or the file's content; each names the path. **Writing.** With the flag, `login` writes the two secret files it creates, a new identity's `identities/<name>.key` and a new `device.key`, wrapped (`passphrase::write_secret_file`, through `private_fs`: 0600, a temp file, then a rename); `<name>.json`, `login.json` and `installs.json` hold public values and are never wrapped. A file that is there already is never rewritten, so the flag neither wraps a plain file nor unwraps a wrapped one. The report names the files it wrapped and says every command that signs in or reads the key needs the flag again. **Reading.** Every secret file goes through `passphrase::open_secret_file`: a file that `looks_wrapped` is unwrapped with the passphrase and then read as before, so the format checks and the classifier run on the unwrapped content and a wrapped recovery file still gets its `Refusal`; any other file is read as plain. Each file says by its own first bytes whether it is wrapped, so a plain identity copied in beside a wrapped device key reads. A wrapped file read without the flag is a `NeedsPassphrase` error, a type of its own, "`<path>` is wrapped with a passphrase: give it with --passphrase-file `<file>`, such as --passphrase-file <(pass show sweepky), …". `state::read_identity` (in `login`, and in `session::sign_in`, so in `keys revoke`, `circle` and `logout` too) and `device::read_device_key` (the reuse branch) both read through it. The tests wrap at 10 and 11; the over-cap tests read with a cap of 10, or patch a stanza to ask for 21 or 40 and read at the production cap, and get the work-factor error at once, with a wrong passphrase too, which shows the cap is checked before any key is derived. The end-to-end test runs without the flag.
