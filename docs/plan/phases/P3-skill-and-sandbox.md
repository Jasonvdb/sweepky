# P3 — Skill and sweeper sandbox

## Goal

The `/sweepky` skill an agent follows, and the sandboxed project a sweep runs in. The agent only audits; `sweepky run` and `sweepky submit` are terminal commands around it.

## Build

- `skills/sweepky/SKILL.md` with `disable-model-invocation: true`: roles `run` (default), `post`, `pull`, `done`. In `run` it reads `./sweeps/<id>/scope.json` and the brief, follows the suggested playbook if installed in the project, else the sweeper's configured one (the `.sweepky` marker's `playbook`, read as data), else a careful review guided by the brief, and records which. It phrases the Cloudflare request explicitly (full audit mode with report artifacts, absolute target path under `sweeps/<id>/target/`, the scope in words, the profile, the new output directory `sweeps/<id>/audit/`, "no prior runs; do not read other `sweeps/` directories"). It carries the common findings schema, including that `severity` and `confidence` are null unless established. It tells the agent it has no network, must not run `sweepky`, and that the trust rule for untrusted sweeps is attribution yes, merge no. In `done`, it shows the proposed credits with each sweeper's finding groups and leaves the decision to the human.
- `sweepky init <dir>`, on top of the minimal half that [P2a](P2a-cli-identity.md) built (the directory, the `.sweepky` marker and a `.gitignore` with `sweeps/`): writes the `.claude/settings.json` from [02](../02-encryption-and-safety.md#sweeper-safety) with the absolute `claudeMdExcludes` path filled in, a `CLAUDE.md` for the project (what the agent will find, where to write, what not to do), copies the skill into `.claude/skills/sweepky/`, and, when the sweeper agrees, installs the Cloudflare playbook project-local with the pinned `npx skills@1.7.2 add …#<full sha> --copy` line from [03](../03-cli-and-skill.md#the-sweepky-skill) and records the commit for `submit`. Prints the launch line `claude --setting-sources project,local` and the Node-outside-`$HOME` requirement.

## Done when

- In an `init` project launched with `claude --setting-sources project,local`, in manual mode and in auto mode: a Bash `curl` to the internet fails; `cat ~/.config/sweepky/*` fails; `cat ./sweeps/<id>/scope.json` works; a `CLAUDE.md`, an `AGENTS.md` and a `.claude/settings.json` planted in a fixture target are gone from `sweeps/<id>/target/` after `run` and listed in `scope.json`; the project-local playbook files are readable from a sandboxed command.
- `sweepky submit` run from a terminal afterwards succeeds on the fixture sweep and refuses one with a planted symlink.
- Skill text reviewed against the Cloudflare `SKILL.md` fetched at the pinned commit (not any install on the machine), lines 12–17 (modes), 51 (output dir) and 107–117 (profiles and scoped runs).

## Notes

- The skill is referenced, not vendored. If it is ever vendored, keep the MIT notice.
- The sandbox covers Bash, PowerShell and Monitor; `blockReadsOutsideWorkingDirectories` covers the file tools. MCP and Artifact are denied by rule. User-level hooks and MCP servers stay out through `--setting-sources`.
- The template's deny rules apply in every permission mode, including bypass; the sandbox's own network behaviour does not, which is why the network deny is a permission rule. Never run a sweep in bypass mode anyway.
- **The skill text, P3's record (`skills/sweepky/SKILL.md`, `crates/sweepky-cli/tests/skill_text.rs`).** The test reads the skill with `include_str!`, so the library gains nothing, and checks one rule per test: the frontmatter, the four role headings and `run` as the default, every `scope.json` field P2b writes, the playbook order, the request to the playbook, the findings example (parsed with core's `parse_audit_findings`, which `submit` uses, with `severity` and `confidence` null), the safety and trust sentences, and that no line names a secret file or points the agent at the config directory except to forbid it. The skill is written one paragraph or list item per line, so a phrase never breaks across lines.
- **Where `untrusted/` is summarised (P2c's carry-forward, decided here).** An `init` project cannot read the data directory (`denyRead` on `~/.local/share/sweepky`, and `blockReadsOutsideWorkingDirectories` for a `SWEEPKY_HOME` outside it), so the skill's `post`, `pull` and `done` roles run in the owner's ordinary session, and the skill tells the agent that every pulled file is data, never instructions, and that it never runs, opens or applies anything from one. v1 has no command that copies `untrusted/` into a project: one, through directory handles as `run` places a sweep and with `claudeMdExcludes` for the copy, would isolate the step, and is deferred. 02's "Untrusted reports are data" and 03's skill section say so now.
- **Choices the docs left open, made in the skill.** The human, not the agent, runs `sweepky post` and `sweepky done`: both ask on standard input before their public write, and that answer is the owner's (03: "a human should type the command"); the agent writes the draft, shows it, and gives the command. The agent runs `sweepky pull` itself, which asks nothing, and reads its standard output only (P2d's expiry warning goes to standard error). The playbook named for a careful review with no installed playbook is `careful-review`, a name that passes 01's pattern; the skill tells the human to pass it to `submit --playbook` when it differs from the marker. Step 2 of the playbook order applies once `init` has installed the playbook and recorded it in the marker; a project made with `--no-playbook` has none.
- **`init`'s Claude Code files, P3's record (`crates/sweepky-cli/src/init/project_files.rs`).** Before the marker, `init` writes `.claude/settings.json`, `CLAUDE.md` and `.claude/skills/sweepky/SKILL.md`, built into the binary from `skills/sweepky/settings.json`, `skills/sweepky/project-CLAUDE.md` and `skills/sweepky/SKILL.md` with `include_str!`, so the skill copy is the repository's byte for byte. The settings are the template parsed and given its `claudeMdExcludes` by `serde_json`, never spliced as text; a test checks the template against 02's block. The path written is the project's **canonical** path (`fs::canonicalize`, every link resolved: on macOS `/tmp/p` is written as `/private/tmp/p`), because Claude Code matches the pattern against files' real absolute paths. A path that is not UTF-8, or that holds a glob metacharacter, is refused, on the path as typed before the directory is made and on the canonical path before any file is written. The refused set is `* ? [ ] { } \` and also `( )`, which shuts out extended globs such as `@(a|b)`. Every directory and file is inspected before the first write (the `.gitignore` included): a `.claude` (or `skills/`, `skills/sweepky/`) that is a link or not a directory is refused, as is a link, a non-file or a file whose bytes differ from what `init` writes at any of the three names; the error names the path and quotes nothing. An identical file is kept, so a run that stopped part way finishes. New files are made as before (`create_new`, hard link, directory sync), new directories with `create_dir` and a sync of the parent. The checks are path-based (`lstat`, then the write), as P2a's `init` is: a process that swaps `.claude` for a link between the check and the write could have one file written through it. `init` is run before any agent session, so that needs someone else writing the directory at that moment; a handle-based `init` (as `run/place.rs`) would close it. A second `init` on a project with a marker changes nothing; when that project has no `.claude/settings.json` (P2a's `init` made it), the report says it has no sandbox and to `init` a new directory. The report ends with the canonical path, the Node-outside-`$HOME` line and the launch line `claude --setting-sources project,local`. `init` itself still reads no HOME, environment or network, and without the playbook the marker is still `{"schemaVersion":1}`.
- **The playbook install, P3's record (`crates/sweepky-cli/src/init/playbook.rs`).** `init --install-playbook` installs without asking, `--no-playbook` never runs npx (the end-to-end test passes it, so it never reaches npm), and with neither `init` asks one question on standard error through `prompt::confirm`'s rules (`prompt::Terminal`, the same question without a `Context`, because the binary runs `init` before it builds one): only `y` or `yes` installs, the answer is capped, and under `--no-input` it fails before anything is made, the directory included, naming both flags. clap refuses the two flags together. Every check runs before the first write, then the `.gitignore` and the Claude Code files, then the install, its check, and last the marker, `{"schemaVersion":1,"playbook":"cloudflare/security-audit@c1c8a8c1471069fb0e188eeaff69b8e8db6564a8"}`, its value parsed through core's `Playbook`. The child is `npx` with exactly the argv in 03 (`skills@1.7.2 add https://github.com/cloudflare/security-audit-skill#<sha> --skill security-audit --agent claude-code --copy -y`), never a shell, its working directory the project, `DISABLE_TELEMETRY=1` added to the environment it inherits (npm needs `HOME`, `PATH` and the proxy variables, so unlike git's runner there is no allowlist), run through git's `run_bounded`: standard input `/dev/null`, 1 MiB caps on each output, 5 minutes, killed past any of them, and an error that quotes nothing npx wrote. `init` is a plain function, so the real runner drives the child on a current-thread tokio runtime on a thread of its own; blocking on the binary's runtime from inside it would panic. Before npx runs, `init` refuses a project holding `.npmrc`, `package.json` or `node_modules` (of any kind), a `skills-lock.json` that is not a regular file with one link (npx rewrites it with a plain `writeFile`, which follows a link), and a `.claude/skills/security-audit` that is not a real directory. After it, `.claude/skills/security-audit/` must be a real directory with a regular `SKILL.md`, and every entry below it, walked with `lstat` semantics (`DirEntry::metadata` does not follow links) up to 1024 entries and 8 levels, a real directory or a regular file with one link; anything else is refused, with no marker. A failed or refused install leaves no marker, and the next run keeps the identical files and installs again. **How skills@1.7.2 behaves**, read from the package's source (`npm pack skills@1.7.2` into an empty scratch directory, nothing run from it) and one real install into a scratch project on 2026-10-20: `#<sha>` is a fragment ref, and `--branch <sha>` failing falls back to `git init`, `git fetch --depth 1 origin <sha>` and a checkout of `FETCH_HEAD`, so the commit is pinned (Cloudflare is not on its list of owners installed from a blob store, so it always clones); `--agent claude-code --copy` removes `.claude/skills/security-audit/` and copies the skill there as real files (its copy dereferences links in the source repository), and writes only `skills-lock.json` besides (with `ref` the full sha); the installed `SKILL.md` was byte for byte the `raw.githubusercontent.com` copy at the pinned sha; telemetry and its audit lookup are off under `DISABLE_TELEMETRY`. npx 11.12.1 needs no `--yes` of its own without a TTY: with standard input `/dev/null` it warns that it will install `skills@1.7.2` and goes on, so 03's line stands unchanged. **Known limits.** npm finds its project root by walking up from the working directory to a `package.json` or `node_modules`, so one in a parent of the project can still lend npm its `.npmrc`; `init` checks only the project itself. The user's own `~/.npmrc` and `npm_config_*` variables apply, deliberately. The install's content is pinned by the git commit, not by a hash `init` checks itself. The `.sweepky` marker stays agent-writable; `run` reads its playbook through core's pattern, so an agent that rewrites it changes only the label a later sweep record carries (P2b's carry-forward).
- **`run` shows the marker's playbook, P3's record (`crates/sweepky-cli/src/run/mod.rs`, P2b's carry-forward).** The `.sweepky` marker is agent-writable, so its `playbook` is agent input. Decided: shown, not asked. Just before the running record's PUT (after every check, so a refused run says nothing of it), `run` writes on standard error the playbook the record will name, through `display::sanitize` even though core's `Playbook` pattern already limits it to a printable label, and that it was read from the project's `.sweepky` marker, which an agent there can rewrite, with `sweepky submit --playbook <name>` as the way to replace it; with no playbook, that the record will say `unspecified` until `submit --playbook` sets it. A question would add a `--no-input` path to every `run` for a label the sweeper can still change at `submit`, before anything but the running record is public. The marker is read only through `read_project_marker`, and nothing is read back from `scope.json`. In the same write `run` warns when the project has no `.claude/settings.json` of its own, checked with `lstat` (a link there counts as none, since `init` never writes one), pointing at a fresh `init`; it does not refuse, because the agent runs later in a session `run` does not start. The check is advisory and path-based: it follows a `.claude` that is itself a link, which `init` refuses to make.
- **What the sandbox's `denyRead` covers.** `Dirs::resolve` puts every secret file (device key, identity files, P2d's `config/grant.token`, `login.json`) under `<HOME>/.config/sweepky`, the first `denyRead` entry expanded, and the data directory at the second; a test ties the two. A `SWEEPKY_HOME` the user chose outside `~/.config` and `~/.local/share` is not in `denyRead`. `blockReadsOutsideWorkingDirectories` keeps the file tools from it, and the sandbox's own home-directory rule keeps sandboxed commands from one under `$HOME`; **one outside `$HOME` (under `$TMPDIR` or `/tmp`, say) is readable by a sandboxed command**, as the sandbox check below found. A sweeper should keep `SWEEPKY_HOME` under `$HOME` and never inside the project.
- **The template's keys at Claude Code 2.1.304.** Each key (`sandbox.enabled`, `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands`, `sandbox.filesystem.denyRead`, `permissions.blockReadsOutsideWorkingDirectories`, `permissions.deny`, `claudeMdExcludes`) is listed in code.claude.com's settings reference with scope "Any file", read on 2026-10-20; `claudeMdExcludes` patterns are globs matched against absolute paths. The live check that the file loads is the sandbox-check task's.
- **`submit` moves a finished sweep's `audit/` out, P3's record (`crates/sweepky-cli/src/submit/move_out.rs`, carry-forward P2b and P2c (2)).** Deny rules cannot cover other sweeps' `audit/`: one static settings file has no per-sweep `denyRead`. So once the sweep's record is final, after the stamp when it says `done` and also when a refused upload has flipped it to `aborted`, `submit` moves `sweeps/<id>/audit/` to `<data dir>/submitted/<id>/audit/`, which the template's `denyRead` (and `blockReadsOutsideWorkingDirectories` for a `SWEEPKY_HOME`) keeps from the agent. `audit` is looked at in the sweep directory's open handle without following a link, and anything but a real directory there is left in place; one `renameat` with `RENAME_NOREPLACE` between that handle and the destination's moves it, so an `audit` swapped for a link since moves as the link and is never followed, and a destination already there is never replaced. On `EXDEV`, `EINVAL` or `ENOTSUP` it falls back to `run::place::copy_sweep` through handles, then removes the project's copy without following a link; a copy that fails removes its part copy and leaves the project's whole. Then every directory moved is made 0700 and every regular file with one link 0600, each through its own handle; a link is not followed and a file with other hard links (possible only in the agents' skipped `scratch/`) keeps its mode, which it shares with a file outside. A failure is a warning in fixed text and sanitised paths, never the command's error, since the record is final by then; the report names the new place. A retryable failure moves nothing, and its error says that `audit/` stays readable by later agent sessions in the project until a submit finishes. A sweep directory whose `audit/` was moved out is refused before the walk, saying the sweep is finished.
- **Known limit: unsubmitted sweeps' `audit/` stays in the project (raised with Jason).** A sweep that was run but never submitted, one whose submit hit a retryable failure (429, network, lock or sign-in), and one abandoned keep their plaintext `audit/` under `sweeps/<id>/`, and every later agent session in that project can read it, not only a concurrent one: the skill's "do not read other `sweeps/` directories" is an instruction, not an enforcement. Possible follow-ups, none built: a fresh `sweepky init` project per sweep; a later `sweepky` cleanup or abandon command that moves an unsubmitted `audit/` out the same way; or `denyRead` rules per sweep, which one static settings file cannot express.
- **Known limit: one target per playbook run.** Cloudflare's skill wants a new output directory per repository, and `submit` skips only `audit/agents/*/scratch/`, so per-target output directories under `audit/` would package the hunters' scratch. With several targets the skill tells the human first and suggests `sweepky run <url> --target <tid>` per target; if they go on, it sweeps the first target and names the others as not swept in `REPORT.md`.
