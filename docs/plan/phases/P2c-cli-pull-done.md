# P2c — `sweepky-cli`: pull, open bounties and done

## Goal

`post --open`, `pull` and `done`, so an owner finds strangers' sweeps on an open bounty, reads every sweep and credits the sweepers who helped. This phase also lands the end-to-end test from [06](../06-verification-and-limits.md#verification), all but its Ring login parts. It builds on [P2a](P2a-cli-identity.md) for the network config and its watch list, the `--identity` login, the device-id list behind the unknown-key alarm, the writers' lock and the state directories; on [P2b](P2b-cli-sweep.md) for `post`, `run`, `submit` and the testnet test as P2b left it; on [P1a](P1a-core-records.md) for the feed parser, trust labels and `Bounty::mark_done`; and on [P1b](P1b-core-crypto.md) for decryption, manifest binding, finding groups and `propose_credits`. The Ring login follows in [P2d](P2d-cli-ring-login.md).

## Build

- **`post --open`:** finds the starting cursor on the owner's homeserver (non-live event stream, `reverse`, `limit 1` after the bounty PUT) and on every other watched homeserver (exponential then binary search with `limit=1`), and writes `bounties/<id>.discovered.json`.
- **`pull`:** roster polling with reverse paged listings, 404 as empty, conditional re-GETs of open bounties and `running` sweeps, cached homeserver resolution; the `/events/` watcher over the watch list through the SDK's HTTP client, 1000 per page, URI dedupe, DEL handling, re-fetch through pkarr-resolved storage, cursor advanced after each batch and persisted; trust labels from roster plus credits; unknown-key alarm; decrypt to `~/.local/share/sweepky/<bounty>/`; group findings by location keeping `reportedBy`; untrusted content into `untrusted/`; append accepted strangers' sweeps to `bounties/<id>.discovered.json`.
- **`done <bounty> [--credit] [--no-credit]`:** proposes credits from the groups, never including the owner (`--credit <own pubky>` is refused with a one-line reason), confirms interactively unless flags settle it, rewrites the bounty with `status: "done"`, `doneAt`, `credits`, preserving unknown fields. Last writer wins, deliberately.

## Done when

- The end-to-end test in [06](../06-verification-and-limits.md#verification) passes: identities A (owner), B (circle sweeper), C (stranger); the open bounty with its `discovered.json`; B and C running `run <bounty>` and `submit`; C found through `/events/`, labelled `unknown`, attributed but kept in `untrusted/`, and appended to `discovered.json`; the shared location grouped with `reportedBy` {B, C} and the shared-id pair kept apart; the injected unknown key making `pull` alarm; `done --credit <A>` refused; `done` proposing {B, C}; C at `known: 1` afterwards; Cloudflare-format and common-format sweeps both grouping; the later device key unable to decrypt; the second install of A decrypting the third sweep; the cursor surviving a restart.
- Logins in this test use `--identity` for B and C. Until [P2d](P2d-cli-ring-login.md), A also logs in with `--identity`; the final test in 06 has A on the Ring flow.
- This test extends the one [P2a](P2a-cli-identity.md) started and [P2b](P2b-cli-sweep.md) grew. [P2d](P2d-cli-ring-login.md) extends this same test with the Ring login parts rather than adding a second one.
- `cargo clippy -- -D warnings`, `cargo deny check` and `cargo nextest run` clean.

## Resolved questions

- **Starting cursor.** `/events/` has no "latest" shortcut: `reverse` is parsed and ignored, a timestamp cursor must match a row exactly, `limit` caps at 1000, and there is no max-id endpoint, so paging from zero on production is not viable. Resolution above: the owner's own event stream gives the event id of the bounty PUT; other homeservers are binary-searched once with `limit=1`.

## Notes

- **Roster reads (the network half of `pull`), in `remote.rs` and the `PublicRecords` seam.** Every request below goes through `remote::get_unredirected`, so a redirected answer is refused before its status or body is looked at, and every body is capped before it is buffered.
  - *Newest-first listings* (`list_dir_newest_first`, `PublicRecords::list_newest_first`) send `reverse=true` beside `limit=` and the cursor, and keep every `ListingParser` limit of P2a: line, page and total, with a page size of 1 to 1000. A listing past them is refused whole, newest first too; `pull` may raise `ListLimits` for a busy key but keeps them finite. A 404 is an empty directory.
  - *Watermark.* P2c reads 01's "paging by cursor until an id already seen" as: stop at the first file of a record whose id is at or below the newest id already seen for that member and directory, and never ask for the next page. Every file of a record counts (`<id>.json`, `<id>.discovered.json`, `<id>.age`), so a file added later under an id already seen, such as a sweep's `.age`, is not listed again; `pull` learns of it from the record's conditional re-GET. A writer can backdate an id, and that record then stays unlisted. This is a known limit, not a bug: the listing is a hint, like the feed, and bounded either way.
  - *Conditional re-GETs* (`get_public_if_changed`, `PublicRecords::get_record_if_changed`) send the tag the record's last answer gave as `If-None-Match`: 304 is unchanged (no body read), 404 is absent, 2xx is the record (at most `MAX_RECORD_BYTES`) with its new tag. An `ETag` is kept only when it is 1 to 128 bytes of visible ASCII (`!` to `~`); anything else counts as no tag. With no tag, nothing is compared and a 304 is an error. No message quotes a tag, and its `Debug` prints only its length.
  - *Packages* (`get_package`, `PublicRecords::get_package`) are read at most `MAX_CIPHERTEXT_BYTES`; a larger `Content-Length` is refused before a byte is read, and a body with no length at the chunk that would cross the cap.
- **Pull's local state (`pull/state.rs`, paths in `dirs.rs`).** Two files in the data directory, each `{schemaVersion: 1, owners: {<owner z32>: <entry>}}`, one entry per owner so a later login of another owner on the same `SWEEPKY_HOME` keeps its own; owners, homeservers and members are compared by key bytes, in either spelling.
  - `<data dir>/feed-cursors.json`, capped at 64 KiB: an owner's entry is `{cursors: {<homeserver z32>: "<event id>"}}`, the shape of `discovered.json`'s `cursors`, inside an object so a newer Sweepky can add fields beside them. `set` stores a cursor after a batch, `lower_to` keeps the lower of the kept cursor and a new one (a bounty whose starting cursor is behind), and `drop_owner` removes one owner's entry.
  - `<data dir>/poll-state.json`, capped at 4 MiB: an owner's entry is `{watermarks: {<member z32>: {bounties: "<id>", sweeps: "<id>"}}, bounties: {<bounty URL>: {status, open, credits, etag}}, sweeps: {<sweep URL>: {bounty, targets, status, etag, pulled, refused?}}, discoveredEtags: {<own bounty id>: <tag>}, acceptedSweeps: {<own bounty id>: [<sweep URL>]}, deletedSweeps: [<sweep URL>]}`. A tag is kept as `remote::ETag` and read back through the same check as a server's (1 to 128 bytes of visible ASCII); a file holding any other is refused.
  - Both go through `private_fs`: 0600 in the 0700 data directory, written to a new temp file, synced, renamed and the directory synced; a link, a loose mode or a file over its cap is refused before it is read, and malformed JSON in fixed text that quotes none of it. A write reads the file again and replaces this owner's entry alone, and one that would pass the cap is refused with the file left as it was. Unknown fields are kept at the top, in each owner's entry and in each watermark and summary. They hold public keys, ids, cursors, URLs, statuses and tags, no secret. Nothing here locks: a caller that must not lose an update to a concurrent `pull` holds the writers' lock around the read and the write.
  - What the poll state holds comes from other people's records, and a status, the credits and the targets are as long as a record makes them, so `pull` bounds how many records it reads a run and what a record may carry into a summary (roster polling, below); the cap keeps the file finite, and is the backstop for how many summaries it holds.
  - Pulled bounties go under `<data dir>/<bounty id>/` (03's `<bounty>/`), strangers' sweeps in its `untrusted/`. Each holds an owner check, written when `pull` first makes the directory, so a later login of another owner on the same `SWEEPKY_HOME` never mixes bounties. A bounty id is 13 characters of `0-9` and upper-case `A-Z`, and no other name in the data directory is, in either case (each is shorter or has a `-` or a `.`), so the two never collide, even on a file system that ignores case.
- **The starting cursor on the owner's homeserver (`sweepky_core::parse_event_stream`).** 01 says "a non-live SDK event stream". `post --open` sends that stream's request itself, `GET /events-stream?user=<owner>&reverse=true&limit=1&path=/pub/sweepky/bounties/<id>.json`, through `remote::get_unredirected` with a cap of `MAX_EVENT_STREAM_BODY_BYTES` (64 KiB), and reads the answer with core's `parse_event_stream`. It does not call the SDK's `EventStreamBuilder::subscribe`, which at pubky 0.16.2 returns a `Pin<Box<dyn Stream>>` that takes a futures crate to read (`futures-util` is in the graph at 0.3.34, but no futures crate is a direct dependency), reads with no byte cap unless `max_event_bytes` is set, sends its request outside `get_unredirected`, and quotes the server's text in its parse errors. The endpoint and the query are the same, so 01's wording stands, and no dependency is added.
  - The answer is SSE as pubky-homeserver 0.16.2 and axum 0.8.9 write it: `event: PUT` or `event: DEL`, `data: pubky://<z32><path>`, `data: cursor: <event id>`, `data: content_hash: <base64>` for a PUT only, then a blank line, with axum's default keep-alive, the empty comment `:`, while the stream is idle. Each event becomes a `StreamEvent` (`op`, `url`, `cursor`) in a `StreamPage`.
  - A body over 64 KiB is refused whole with `FeedError::TooLarge`, which holds numbers only; every line has the feed's cap, `MAX_FEED_LINE_BYTES`; the work is linear in the body.
  - Tolerated: comments, `\r\n` endings, a last event with no blank line after it, later `data:` lines with an unknown prefix, and the SSE fields `id`, `retry` and unknown names. The content hash is never read, so a DEL needs none.
  - Skipped and counted as malformed: an event whose first `data:` line is not a URL `PubkyUrl` accepts; a missing, non-canonical or second cursor (every `data:` line that starts `cursor:` is a cursor line); a missing, unknown or second `event:` type; a line over the cap; a field line that is not UTF-8.
  - Known limit: the SSE standard drops a last event the stream ends in the middle of; this parse keeps it, so a body cut inside its cursor line would read as a smaller cursor. That trusts the homeserver no further, since it can send any cursor anyway, and a smaller starting cursor only makes `pull` read more of the feed.
- **The events seam and the starting-cursor search (`events.rs`).** `EventsFeed` is the seam through which `post --open` and `pull` read a homeserver's public events, with no session. `HomeserverEvents` is the real one: it asks each homeserver at `https://<homeserver z32>/…`, which the SDK's HTTP client resolves through pkarr, as the SDK's own event stream does, and sends every request through `remote::get_unredirected`. The unit tests use a fake. Any status but 2xx is an error that names the status alone, a 404 and a 400 included; a 429 is fixed text that says to wait and try again.
  - *A page* (`EventsFeed::page`) is `GET /events/?cursor=<c>&limit=<n>`, with `n` from 1 to 1000, the body capped at `MAX_FEED_BODY_BYTES` and parsed by core's `parse_feed`. A page with more events than `n` breaks the protocol and is refused (P1a's carry-forward), so `n` bounds the re-fetch work one page can cause.
  - *The owner's latest event* (`EventsFeed::latest_event`) is the stream request above, its body capped at `MAX_EVENT_STREAM_BODY_BYTES` and parsed by core's `parse_event_stream`. The `path` filter is the bounty's own file, not `bounties/`: the 0.16.2 homeserver matches a file's path exactly (`PathFilter`), so no other bounty written at the same time can stand in for it. Only a PUT of exactly that file, its owner compared by key bytes, is an answer. A DEL, another file, no readable event and more than one event are errors in fixed text. 01's "Starting cursor" now names the file.
  - *The head search* (`find_head`) asks for cursor 0, then 1, 2, 4 and so on until a page is empty, then halves the gap between the last cursor before the head and the first at or past it. A head between 2^(m-1) and 2^m takes 2m + 1 requests, and no answer can make it send more than 125. It never asks for a cursor above 2^62: the 0.16.2 homeserver binds a cursor as a Postgres `BIGINT` with `i64::try_from(..).unwrap()` (sea-query-sqlx 0.8.1), so one above `i64::MAX` would make its handler panic, and a feed that claims events past 2^62 is refused. Only a page that holds an event or a cursor counts as before the head. A page of only malformed lines is not caught up, so `pull` stops at one, but the search counts it as at or past the head, so a broken answer can only lower the cursor it finds, never lift it past an event. Events written while the search runs may fall below that cursor; a sweep is written more than once (`running`, then its `.age` and `done`), so its later events are still seen.
  - *Paced, not inside the burst.* 01 and 06 said the search fits inside the `/events/` burst. It does not: production allows 3 requests a second with a burst of 10, and a head near 10^7 takes about 50 requests. `find_head` takes its pace as a parameter: `SEARCH_PACE` (350 ms) before each request after the first 5 for production, so such a search takes about 15 s, and zero in the tests. A 429 stops it with the message above. 01's "Starting cursor" and 06's `/events/` row now say so.
- **`post --open` (`post/open.rs`).** The draft, the pinning, the size check, the preview and the question are a closed `post`'s; `--open` sets the record's `open` to `true` and changes nothing else in it, and the preview and the report say "open: sweeps from anyone are read and labelled by trust". After the yes, in this order: `login.json` is read for the owner and their homeserver; every watched homeserver but the owner's is searched with `find_head`, outside the writers' lock, so a paced search or a person never holds it; then, under the lock with a fresh session, once `login.json` is seen to say what it said before the search: the bounty PUT; when the owner's homeserver is on the watch list, its `/events-stream` read for the bounty's own file, whose PUT event is the cursor there; the `discovered.json` PUT, compact `{schemaVersion: 1, sweeps: [], cursors: {<homeserver z32>: "<event id>"}}` with one cursor per watched homeserver; the local `feed-cursors.json` update; and the sign-out. So the lock covers the sign-in, the two PUTs with the one stream read between them, the local update and the sign-out. The local update is in it because it reads, changes and writes a file `pull` rewrites too (`pull/state.rs`: a writer that must not lose its update to a concurrent `pull` holds the lock).
  - *The owner's homeserver comes from `login.json`*, so this step needs no resolver seam and makes no pkarr lookup of the owner; `pull`'s roster polling adds `ResolveHomeserver` later. An identity that moved homeservers since its login has its stream read on the old one, which fails after the bounty PUT; logging in again records the new one.
  - *An owner whose homeserver is not on the watch list* gets no cursor for it, and `pull` does not watch it: the same known gap as 01's "a sweeper on a homeserver not on the watch list is not seen". The watch list stays what 00 locks.
  - *The local cursor is min(old, new)* (`FeedCursors::lower_to`), so an earlier open bounty's unread events are never skipped; `discovered.json` holds the bounty's own cursors. `pull` drops an owner's cursors once none of their bounties is open, so a stale low cursor does not linger; a post made before that drop replays from the older cursor, bounded by `pull`'s pages per run.
  - *Failures.* Before the bounty PUT (no login, a search error, a 429 among them, a changed login), nothing is posted and the error says so. After it, every error names the bounty's URL and says not to post it again, since a second `post` is a second bounty. A refused `discovered.json` PUT is `write_error`'s fixed text, and the local cursors are stored anyway. A failed stream read stops before either: without the owner's cursor the set is not complete. `discovered.json` needs no size check of its own: under 80 bytes a watched homeserver, it stays far under `MAX_RECORD_BYTES` for any watch list Sweepky has.
  - *For `pull`:* an open bounty of the owner's with no `discovered.json` still needs one. After a refused PUT, the local cursors are there to write it from. After a failed stream read there are none: the owner's stream for the bounty's file, read again, still gives the PUT's event while the record is not rewritten, but another watched homeserver can only be searched again, later than the bounty, so a sweep written there in between would be missed. That takes a stream read failing right after the PUT it follows, with a watch list beyond the owner's homeserver; it is a known limit.
- **The key-alarm check's bounds (`keys::key_alarms`), P2a's second open limit.** P2a left the check reading up to 1000 records of up to 1 MiB each, one after another. P2c keeps the sequential reads and the per-record cap, which is the record format's (`MAX_RECORD_BYTES`), so a smaller one would be a format question, and adds a budget across the whole check: 8 MiB (`KEY_RECORDS_BUDGET_BYTES`). A real key record is a few hundred bytes, and one with a post-quantum recipient stays under a few KiB; `keys/` is the owner's own directory, written only by the owner's installs or by whoever holds their grant or runs their homeserver, so anything near the budget is itself a sign that someone wrote there. A record is read only while the budget still has room for one at the per-record cap, and a read that fails counts as a whole one (a body with no length is refused only at the chunk that crosses the cap), so the reads together never pass the budget. No conditional re-GETs: the check must see the current bytes.
  - The check either reads every listed record within those bounds or fails with a typed `keys::KeyCheckError`, never a shorter list of alarms: `TooManyKeys` (a listing past `ListLimits::DEFAULT`, refused by the parser or counted again by the check before any record is read), `OverBudget`, `Listing` (any other listing failure) and `Read` (a record under a known id whose read failed, which could hold any key; under an unknown id a failed read is that id's alarm, as [02](../02-encryption-and-safety.md#who-can-read-a-sweep) has it, since only a revoked record settles it). Its own text is fixed, with numbers and a device id at most; a failed listing or read keeps `remote`'s error, fixed text and a status, as its cause. A record that is gone or does not parse stays as P2a had it: no sweeper running this build encrypts to it, so it alarms only under an unknown id.
  - `login` prints a failure as the warning it printed for a failed listing before, pointing at `keys list`; `pull` prints it as an alarm. `keys list` reads through the same `list_keys`, so the reads never disagree: past the listing limits or the budget it fails with the same error, and a record whose read failed is a warning there beside the rest of the listing, since that is where `login`'s warning sends the owner.
- **Roster polling (`pull/roster.rs`, `pull/resolve.rs`).** `poll_roster` reads public records alone, through `PublicRecords`, with no session and no lock, and brings the poll state up to date in memory; writing it back is the caller's.
  - *The roster* is the `circle.json` in the owner's own storage, and counts only when its `admin` is the owner, compared by key bytes: anyone can put any file in their own storage. No circle is the owner alone; one that names another admin, or that cannot be read, is a warning and the owner alone too, which errs on the side of less trust. The first 32 keys are polled (`MAX_MEMBERS`, 01's "a circle of under ~30"), the admin first and then each member once, with a warning past them. The roster handed back holds those keys alone, so the trust labels and the feed agree that a key cut from the circle is outside it this run.
  - *Homeservers, once a run.* P2c's reading of "cached homeserver resolution": `pull` is one short process, so the cache (`Homeservers`, in front of the `ResolveHomeserver` seam, whose real implementation is `Pubky::get_homeserver_of`) lasts one run. That is one lookup per key, and one more after a read of that key fails (`after_failed_read`), on top of the SDK's own 60 s transport cache and pkarr's cache. The lookup is the gate before any request: every read goes to `_pubky.<key>`, which the SDK resolves itself, so a cache kept on disk would save no lookup. A key whose pkarr record names no homeserver, or whose lookup fails, is skipped with one warning that names it, and stays in the roster: unreachable is not untrusted. 01's resolve bullet now says that hourly re-resolution is for a poller that keeps running, such as the board.
  - *Each key, in order.* First its records in the poll state that can still change, its open bounties (status `open`) and its `running` sweeps of the owner's bounties, newest first, at most 32 (`MAX_REREADS_PER_MEMBER`), each read with its stored `ETag` as `If-None-Match`: a 304 leaves the summary as it was, a 404 drops it, and a new answer updates it, keeping `pulled` and the fields a newer Sweepky added. Then `bounties/` and `sweeps/`, listed newest first down to the key's watermark there. Of the records listed, those the poll state does not hold yet are read oldest first, at most 16 bounties and 32 sweeps a run (`MAX_NEW_BOUNTIES_PER_MEMBER`, `MAX_NEW_SWEEPS_PER_MEMBER`), with a warning past them, and the watermark moves up to each one as it is read. So what a cut or a failure leaves unread stays above the watermark and is listed again next run, and a record once read is at or below it and never read as new again. A 404 on a listing is an empty directory, never an unreachable key, and sets no watermark.
  - *What is kept.* A summary of each bounty, and of each sweep of one of the owner's bounties. A member's sweep of another owner's bounty is read once, when it is new, and nothing of it is kept: the watermark that passes it is what remembers it, so no later listing names it and nothing reads it again, running or not. Circle members sweep each other's bounties all the time, so keeping those summaries would grow the poll state with every run. A record whose summary would carry more than Sweepky writes, a status over 32 bytes (`MAX_STATUS_BYTES`; the longest Sweepky writes is `running`), more than 128 credits (`MAX_CREDITS`) or more than `MAX_TARGETS` targets, is skipped like one that does not parse. `done` should write no more than `MAX_CREDITS` credits.
  - *Faults skip, they do not stop, and each is a warning.* A record over `MAX_RECORD_BYTES` (`remote::BodyTooLarge`, or core's `from_json`), one that does not parse and one that carries too much are skipped, and the watermark passes them; one read again that no longer parses keeps the summary it had, since a newer Sweepky's record may parse once this build is updated. A read that fails otherwise (a listing refused, a status, a network error) ends that key's poll for the run, since its reads all go to one homeserver and each could wait long; the key is looked up again once, and the warning says so when its record now names no homeserver.
  - *What it returns* (`RosterPoll`), from the poll state, so a record unchanged since an earlier run counts as much as one read now: the roster, the owner's own bounties, the roster's sweeps of them, every bounty of the roster as a `CreditedBounty` (each once, from the state's map, so `trust_labels` counts each record once: P1a's carry-forward), and the warnings. Those name keys, paths core built, counts, and `remote`'s and core's fixed text, never a record's title, status or label, so nothing printed holds a stranger's text.
  - *Known limits.* `PublicRecordReader` lists within `ListLimits::DEFAULT`, so a key with more than 1000 files above its watermark in one directory (some 500 sweeps between two pulls) has that directory refused whole, with a warning, every run. A record named by an id in the future moves the watermark there, so that key's later records stay unlisted until their ids pass it, as a backdated one stays unlisted. A homeserver that keeps failing one read ends that key's poll at that read every run. The poll state grows with the roster's bounties and the sweeps of the owner's bounties: bounded per run by the read limits and per summary by the carry limits, with the file's 4 MiB cap as the backstop, which a hostile key in the roster could reach; the write is then refused and the caller says so.
  - 01's listing bullet now names `bounties/` and `sweeps/` as what `pull` lists, and says `keys/` is read where it is used: `pull` reads only the owner's own, for the alarm; a member's is read by whoever encrypts to that member (`submit`, for a bounty's owner).
- **The host policy for other people's homeservers (`pull/resolve.rs`), P2b's carry-forward** ("reuse the policy for anything that contacts a stranger-named host"). A key's pkarr record names its homeserver, and the homeserver's own record names where it is, so whoever holds a key, a stranger or a circle member, chooses where `pull` connects to read it. `CheckedHomeservers` is a `ResolveHomeserver` in front of another, so `Homeservers` and the roster poll take it unchanged, and a refused key is skipped with the one warning that names it, as an unreachable one is. `ResolveHomeserver::homeserver_of` now answers with an `Unreachable` rather than an error, so the reason reaches that warning with no text of the resolver's.
  - *Where it applies.* On production alone (`NetworkKind::Production`): the testnet's homeservers are on loopback by design, and an injected network is a testnet a test started. Never for the owner, and never of the homeserver `login.json` records for the owner, whose record is not read: the owner chose it. A key on that homeserver still has its own `_pubky` records checked, as below.
  - *What it reads.* Through the SDK's own pkarr client (`PubkyHttpClient::pkarr`, with `CacheFirst`, the policy the SDK resolves with before each request), the key's record and its homeserver's. No new dependency: pkarr 8.1.0 is reached through pubky's `pkarr` re-export, and simple-dns 0.12.0 through pkarr's `dns`.
  - *What passes.* Every `_pubky` HTTPS or SVCB record of the key targets that homeserver, written as the SDK's signup writes it (its raw z-base32, compared as text). The SDK's storage requests (`https://_pubky.<key>/…`) use every `_pubky` record, while `get_homeserver_of` gives only the first, so a second one is refused rather than left unchecked. The homeserver's record gives somewhere to reach it: an HTTPS or SVCB target that is a domain, or `.` beside an A or AAAA record. With none, or no record, the key is `HomeserverNotFound`, skipped like one with no homeserver. Every A and AAAA record in it, under any name, passes `targets::host::is_public`. Every domain target passes `check_host` through the `ResolveHost` seam, at most 4 of them (`MAX_HOMESERVER_DOMAINS`: pubky-homeserver writes one, and each costs a lookup bounded only by the system resolver). No target is one pkarr reads as another key (`PublicKey::try_from`, which also takes `www.<key>` as `<key>`); the SDK would follow it, and the policy does not. SVCB address hints are not read: the SDK connects to the A and AAAA records.
  - *Fails closed.* Anything else is `NotPublic`, whose text, like every `Unreachable`'s, is fixed and quotes no record, domain or address. A domain whose lookup fails or gives no address is refused too.
  - *Once a run.* A homeserver's verdict is kept for the run, refusals included, so the production homeserver is checked once however many keys share it. A key's own record is read at each of its lookups, from pkarr's cache.
  - *Known limit: the check is advisory.* The SDK resolves pkarr and DNS again inside each request, so a stranger who answers differently the second time is not caught: DNS rebinding of a domain target, or a pkarr record republished once pkarr's cached copy expires (its time to live is held to 5 minutes at the least). Before the request the SDK may also send its own `GET /info` to the homeserver, and probe its direct addresses when it has a domain too; both go where the records the check read point, while they hold. The reads the check guards are capped GETs through `remote::get_unredirected`, which refuses a redirected answer only after reqwest has followed it: P2b's redirect limit. 06's known limits say so.
- **The open-bounty feed watcher (`pull/feed.rs`).** `watch_open_bounties` runs after the roster poll, reads public records and events alone, with no session and no lock, and returns the feeds' starts, the strangers' sweeps it accepted and the deletions it confirmed (`FeedWatch`), which the `discovered.json` write turns into the public write.
  - *Which bounties.* A bounty takes strangers' sweeps when the poll state's summary says `open: true` and status `open`. A stranger's sweep of a done or closed bounty is not added. With none open, `pull` sends no feed request, reads no `discovered.json`, and drops the owner's entry from `feed-cursors.json`: no sweep could be accepted, so nothing is missed, and a later `post --open` stores new cursors. The poll state keeps a `discovered.json` tag for an open bounty alone.
  - *One cursor per owner and homeserver, not per bounty.* A sweep record names its bounty, so reading from the lowest start serves every open bounty on that homeserver, and a sweep cannot name a bounty from before it existed.
  - *What `discovered.json` lists, first.* Each open bounty's file is read from the owner's storage with the tag of its last answer as `If-None-Match`. A new answer gives its cursors, and each sweep it lists that this install has neither accepted nor confirmed deleted, by a sweeper outside the roster, is confirmed as a feed's `PUT` is (below), at most 256 a run (`MAX_LISTED_SWEEPS_PER_RUN`), with a warning past them. A listed sweep whose record is gone (404) is a confirmed deletion. The tag is kept only once every sweep the file lists is settled, so a file with sweeps still to confirm is read whole again next run. This is how a second install of the owner sees what the first discovered: its own cursor may start past those events (06's second install of A).
  - *Where each feed starts* (`Start`, with its `StartSource`). At the local cursor; else at the lowest cursor the open bounties' `discovered.json` give that homeserver; else at its head, found with `find_head`, with a warning. A head search that fails skips that homeserver this run, with a warning. A start that did not come from the local file is stored there at once, lowered in as `post --open` does, so the next run starts there even if this one reads no page of that feed, and a `discovered.json` answered with a 304 is never needed for its cursors.
  - *Pages.* 1000 events a page (`FEED_PAGE_SIZE`), at most 10 pages per homeserver a run (`MAX_FEED_PAGES_PER_RUN`, production's `/events/` burst), with a warning when the last one read was full. A page counts as full by its lines, events and malformed lines together, since a line this build does not read still counted against the homeserver's limit. A page with more events than asked for is refused by the events seam; one with no cursor (events or malformed lines without one), or whose cursor is at or below the one asked for, stops that homeserver's feed with a warning in fixed text. Nothing on such a page is acted on, its cursor is not stored, and it is not asked for again in the run.
  - *A batch.* Of a page, the sweep records alone, each once with its last operation (core's `sweep_records`, deduplicated by URL), of sweepers outside the roster. A `PUT` is read from the sweeper's own storage through `PublicRecords`, once their homeserver resolves through the run's `Homeservers` (the host policy on production), never from the feed's host, at most `MAX_RECORD_BYTES` and within the roster poll's carry limits (`roster::fetch`), with the summary's tag as `If-None-Match` only for a sweep already accepted. It is accepted when the record names one of the owner's open bounties; a sweep accepted before has its summary brought up to date whatever its bounty's status now, and is not accepted again. A `DEL` is looked into only for a sweep this install accepted, and drops it only on a 404; a record still there leaves everything as it was.
  - *Stored after each batch.* The poll state is written, then the cursor moves from the one the batch was asked after to the page's (`FeedCursors::advance`). A sweep accepted is in the poll state's file before the cursor moves past its event, so a run stopped between the two reads the page again next run and accepts nothing twice. `advance` moves the cursor only while the file still holds the one the batch started from: a cursor `post --open` lowered meanwhile for a new bounty, or one a concurrent `pull` moved on, is kept, and the feed stops for the run with a warning. Nothing here locks, so this narrows the race with another writer to the moment of the write, not the whole run.
  - *Faults skip, they do not stall.* A sweeper whose homeserver does not resolve, or a read of whose storage fails, is read no more that run, with one warning (a failed read looks the key up again, as the roster poll does). A record that does not parse, or carries too much, is skipped with a warning. The cursor still moves on: a stranger can make their own reads fail, and that must not stop the owner's feed. Only a failure of the local files is an error. Warnings name keys, core-built URLs and paths, numbers and `remote`'s and core's fixed text, never a feed's or a record's text.
  - *Known limits.* A sweeper on a homeserver not on the watch list is not seen (01). If one install's local cursor is ahead of the starting cursor of another install's newer open bounty, the first sees that bounty's strangers only through its `discovered.json`, once the other install pulls. A stranger's sweep whose read fails is seen again only at a later event of its record or through a `discovered.json` listing.
- **Storing what `pull` decrypted (`pull/store.rs`).** `store_sweep` writes one opened sweep into the data directory, from the `PackageFiles` core's `into_files` gives and a compact copy of the findings taken before the split (`CompactFindings::of`, since `into_files` consumes them). The caller says whether the sweep is trusted.
  - *Layout*, under the data directory: `<bounty id>/owner.json`, the owner check (`{schemaVersion: 1, owner: <z32>}`); `<bounty id>/<sweeper z32>-<sweep id>/` for a trusted sweep and `<bounty id>/untrusted/<sweeper z32>-<sweep id>/` for an untrusted one, each holding the package's files at their own paths (`findings.json` pretty-printed among them) and `.sweepky/findings.json`, the compact copy; and `staging/.pull.<pid>.<nanos>.<n>.tmp/`, one store's staging. A sweeper's key is 52 lower-case characters and a sweep id 13 of `0-9A-Z`, so a sweep's name is never another entry's, in either case.
  - *Checked before anything is written*, refusing the whole sweep with fixed text that names no path: a part of a path that starts with `.` (`.git/config`, `.claude/settings.json`, `.vscode/…`), which tools read as their settings (P1b's carry-forward); two paths equal once folded to lower case (`README.md` and `readme.md`, `FINDINGS.json` beside `findings.json`), a file where another path has a directory, or one directory spelt two ways; more than 4096 files and directories together, or a path of more than 32 parts. The caps are `submit`'s walk's (`MAX_ENTRIES`, `MAX_DEPTH`): `audit/` is the walk's first level and a package's paths are relative to it, so no package `submit` built passes them.
  - *Staged, then moved in one step.* The sweep is written into a new staging directory, then moved to its place with `renameat` and `RENAME_NOREPLACE` (`RENAME_EXCL` on macOS), relative to directory handles, so it is there whole or not at all and nothing at the name, a link included, is replaced. The staging directory is removed whatever happens, so a failed write leaves no part of a sweep. A bounty's directory is made the same way the first time, its owner check inside, so it never exists without one. A file system that cannot promise not to replace (`EINVAL`, `ENOTSUP`) or a staging directory on another one (`EXDEV`) gets `run`'s handle-only copy (`run::place::copy_sweep`); its errors name the entries it copies, so `pull` passes on fixed text instead.
  - *Through handles that follow no link*, with `run::place`'s and `submit::walk`'s calls, which this step only made `pub(crate)`: each directory on the way (the bounty's, `untrusted/`) is looked at with `statat(AT_SYMLINK_NOFOLLOW)`, opened with `O_DIRECTORY | O_NOFOLLOW` and `fstat`ed against the look; every new directory is `mkdirat` and every new file `O_CREAT | O_EXCL | O_NOFOLLOW`. A link or anything but a directory at the bounty's directory or `untrusted/`, and anything but a directory where the sweep goes, is refused and nothing is written through it. `O_EXCL` and `mkdirat` are the backstop for names the lower-case fold does not join but the file system does (two Unicode normalisations on APFS, a case pair Rust's `to_lowercase` keeps apart): the second write fails, and the sweep with it.
  - *Owner-only from the start*: directories 0700 and files 0600 in the call that makes them, never `chmod`ed. Each file is synced as it is written, each directory once it is full, and the directory moved into after the rename, so a sweep `pull` records as pulled survives a crash.
  - *Once.* A sweep already stored, as trusted or as untrusted, is `Stored::AlreadyThere` and left as it was: where a sweep goes is decided when it is first stored, and a later change of its sweeper's label does not move it. Regrouping takes trust from the label of the day, not from where the files are.
  - *One owner per bounty directory.* A store or a read for an owner the owner check does not name is refused: a bounty id is the owner's own, so another owner on the same `SWEEPKY_HOME` could hold the same one.
  - *The compact copy* exists because the pretty `findings.json` can be longer than `Findings::from_json`'s 16 MiB cap. It is serde_json's compact form, counted first and then written into a `Zeroizing` buffer of exactly that length, capped at `MAX_PACKAGE_BYTES`: findings out of a package within that cap fit it unless they hold numbers serde_json writes back longer (`1e15` as `1000000000000000.0`), and such a sweep is refused rather than stored without its copy. `read_stored_findings` reads it back through `private_fs::read_private_file` with the same cap, checked before a byte is read, after checking each directory on the way is not a link; the parse's error quotes nothing.
  - *Sealed content.* The files' bytes stay in `Zeroizing` buffers until written, each wiped as its turn ends. Nothing written is printed or logged, and no message names a package's path.
  - *Known limits.* A stored sweep takes up to its package's attachments (within 32 MiB), the pretty `findings.json` (within core's 128 MiB) and the compact copy (within 32 MiB) on disk; how many are stored a run is the opening step's cap. Every file and directory is synced, so a sweep of 4096 entries costs as many syncs. On the copy fallback, a second `pull` storing the same sweep at the same moment is an error rather than `AlreadyThere`, and the copy is neither one step nor synced: a crash in the middle of it can leave part of a sweep, without its compact copy (`.sweepky/` is copied last), which a later store takes as `AlreadyThere`. A store killed outright (`kill -9`) leaves its staging directory, inside the 0700 data directory, as `run` does. `submit` still packages every UTF-8 file under `audit/`, one at a path with a part that starts with `.` included, and `pull` refuses such a sweep whole, for every owner: a playbook that leaves a dotfile in `audit/` makes its sweeps unreadable until `submit` skips those paths with a warning, as it skips a path `AttachmentPath` refuses.
  - *For P3.* The sandbox template `init` writes denies reads of `~/.local/share/sweepky` (02), which is where these files land, `untrusted/` included. 02 and 03 ask an owner who pulls open-bounty sweeps to have their agent summarise `untrusted/` inside an `init`-style project with the same deny rules, and that agent cannot read them there. P3 must decide how the agent reaches them, for example a command that copies one bounty's `untrusted/` into the project, through handles as `run` places a sweep, or a narrower deny rule.
- **Opening each sweep (`pull/open.rs`).** `open_sweeps` runs after the roster poll and the feed watcher and opens what their poll state says is waiting: a sweep of one of the owner's bounties the roster poll has read, whose record says `done`, neither `pulled` nor `refused`, by a key of the roster or accepted for that bounty from the feed. `running` sweeps wait for a later pull and `aborted` ones are skipped (P2b's carry-forward); a stranger's sweep of a closed bounty is never accepted, so never opened. Writing the poll state back is the caller's.
  - *Each sweep, one at a time*, once its sweeper's homeserver resolves through the run's `Homeservers` (the host policy on production), from that sweeper's own storage alone: its record read again, which must still say `done`, name the bounty being pulled and name at least one target, each one the bounty has in a kind this build reads, all before the package is fetched; its `.age` through `PublicRecords::get_package` (`remote::get_unredirected`, at most `MAX_CIPHERTEXT_BYTES`), its length checked again before core sees it; `open_package` with this install's key, the `SweepRef` the record and the package were fetched from (never a URL from the feed, a record or the package) and the record just read; then what binding leaves to `pull`: every commit in the manifest's `targetShas` is the one the bounty pins for review under `KnownTarget::reviewed_commit` (a pull request's head, any other target's `rev`), as `submit` writes them. The ciphertext is dropped before the split. Then the compact copy of the findings, `into_files`, the store's path check (`store::check_paths`, now `pub(crate)` so a package the store refuses is told apart from a store that failed) and `store_sweep`: a roster key's sweep among the trusted, anyone else's in `untrusted/`. The package is consumed by the split and its files by the store.
  - *The device key* is read with `device::read_device_key` and the context's passphrase only when a sweep is waiting; a wrapped `device.key` without `--passphrase-file` is `passphrase::NeedsPassphrase`, and an install with none is an error that says to log in. It is lent to `open_package` alone, never printed, cloned or compared, and dropped once the run's opens are done.
  - *A fair order, within caps per run.* Of a bounty's waiting sweeps, the roster's go first, then everyone else's; in each group sweepers take turns, every sweeper's oldest first, then every one's second, each turn in upload order (sweep ids are creation times). At most 4 of one sweeper's are opened for a bounty a run (`MAX_OPENS_PER_SWEEPER`) and at most 16 of a bounty's (`MAX_OPENS_PER_BOUNTY`); what is left waits for the next run, with one warning that counts it. The per-sweeper share limits flooding by one key: a stranger holding 50 done sweeps takes at most 4 turns a run, and one turn before every other sweeper has had theirs. The circle's turn first keeps a flood of throwaway keys from delaying circle members; it can still delay other strangers, whose turns it shares. A sweeper read no more this run takes no turn. The caps bound a run's memory too, since a package may be 32 MiB and its parse several times that.
  - *Settled, or tried again.* Stored (written, or already there from a run whose poll state was not written) is `pulled: true`. Refused for a reason every later run would meet again is `refused: true`, never fetched again, with a warning in fixed text: a record gone, no longer read, no longer `done`, naming another bounty or targets the bounty does not pin; a package missing (a warning, for a `done` record), over the cap (refused before `open_package`), not encrypted to this install's key ("not encrypted to this install's key (sealed before this install's key was published, or to another install)", the unit form of 06's later device key), not decrypting otherwise, not a package, not bound, swept at other revisions; findings whose compact copy, pretty `findings.json` (`PackageError::FindingsFileTooLarge`) or paths the store refuses. Without that flag, a broken or hostile sweep would cost a download every run and hold its sweeper's share, and the bounty's turns, for ever. A sweeper who cannot be reached or whose read fails is read no more that run (a failed read looks the key up again), and a store that fails leaves its sweep waiting; both are tried again next run. `refused` is written only when true, so a poll state from before it reads and writes back as it was. Only this install's own key is an error; every other fault is a warning, which names keys, core-built URLs and numbers with core's and `remote`'s fixed text, never a byte of a record or a package.
  - *Known limits.* The manifest has no sweep id (01), so a sweeper's own package uploaded again under another of their sweep records, for the same bounty and targets, still binds there, and is stored once per record. A sweep refused for good is not tried again by a later build that would read it. A store that fails on a package fault the path check cannot see (two names the file system takes as one, which `O_EXCL` refuses) is tried again each run. A flood of throwaway stranger keys whose reads keep failing takes the strangers' turns each run, as one with sweeps that open does until they are all stored.
