# P4 — The landing page and the board

## Goal

A static, read-only SPA: a landing page that explains Sweepky and invites owners and sweepers in, and the board where anyone watches bounties, sweeps and credits. No sign-in, no decryption, no writes, no feed scanning.

## Build

- Scaffold: `pnpm create vite web --template react-ts`; add `@synonymdev/pubky`, `react-router`, `zustand` at the exact versions in [03](../03-cli-and-skill.md#dependencies); `tsconfig` `lib` includes `esnext`. Load Inter Tight in the page.
- `VITE_PUBKY_TESTNET=1` → `Pubky.testnet()`, opt-in only; the production build asserts it is unset.
- Routes: `/` (landing), `/board`, `/b/:owner/:id`, `/s/:sweeper/:id`, `/circle`.
- Tokens, type, buttons and section pattern from the pubky-app design reference in [04](../04-board.md#design-reference-pubky-app), copied by hand into the app's CSS from the pinned commit. One accent (`--brand`); `--destructive` only for `aborted` and "unreachable".
- Polling store (30 s) per [04](../04-board.md#live-ness): cached homeserver resolution, reverse paged listings with 404 as empty, conditional re-GET of non-terminal records, open bounties through `bounties/<id>.discovered.json`, every request with `credentials: 'omit'`.
- Trust badge per sweep (`circle` / `known N` / `unknown`) computed from the roster plus `credits` on done bounties from trusted owners (roster members in v1), ignoring a credit that names the bounty's owner; `open` marker on bounties; done bounties show their credited sweepers; credits received on the Circle page; "not browser-reachable" for members whose homeserver has no ICANN HTTPS endpoint. The trust-badge unit test loads [`fixtures/trust-labels.json`](../../../fixtures/trust-labels.json), the file [P1a](P1a-core-records.md)'s Rust test loads. It passes the badge function the whole `bounties` list, so the function itself, not its caller, drops open bounties and bounties from owners outside the roster. For every `expected` entry the test asserts the label, and the `bounties` and `owners` counts behind "credits received" on the Circle page.
- Visual direction from [04-board.md](../04-board.md#visual-direction): floor plan, detectors, swept rooms, rooms going dark when done, hollow unknown sweepers; the board's intro strip and empty state.
- Landing page per [04](../04-board.md#landing-page-): six sections, the hero showing the live floor plan (or the empty state) from the board's store, `#post` and `#sweep` anchors, Open Graph tags in `index.html`, the install block linking to the README until a release channel exists.
- All motion stops under `prefers-reduced-motion: reduce`.
- `/health.json`; no `X-Frame-Options` or `frame-ancestors` that excludes vibes.pubky.app; nothing essential in `localStorage`.

## Done when

- `pnpm build` and `pnpm test` clean (unit tests for the trust-badge rule against `fixtures/trust-labels.json`, the listing pager and the record reducer).
- Playwright or manual against the testnet: the public view shows a `running` → `done` sweep transition within one poll, a stranger's sweep appearing with the `unknown` badge after the owner's `pull` has published it to `discovered.json`, and the bounty flipping to done with its credits and the stranger's badge becoming `known 1`.
- The network log shows every request sent without credentials and nothing written; the board never requests `/events/`; apart from the font, the landing page requests nothing but what its hero's store reads.
- Against an empty testnet, `/board` and the landing hero both show the empty state, with no sample rooms.
- The landing page and the board render at 375 px and at desktop width with no horizontal scroll, are keyboard navigable, and show no motion under reduced-motion emulation.
- The verifier traces every claim on the landing page to [00](../00-overview.md), [02](../02-encryption-and-safety.md) or the known limits in [06](../06-verification-and-limits.md#known-limits-say-them-in-the-readme), and finds none that a known limit contradicts.

## Notes

- pubky-app is read at its pinned commit for reference only; nothing in `web/` imports, vendors or fetches it at build time, and none of Pubky's or Synonym's logos or illustrations ship.
- The board writes nothing. If a later phase adds E4 (reading in the browser), that is where sign-in and keys arrive.
- The pkarr relay under `Pubky.testnet()` is `http://<host>:15411`; resolved. Production uses the SDK's default HTTPS relays.
- Scaffold: `create-vite` 9.3.1's `react-ts` template without its oxlint, demo assets, counter and Vite and React logos. The template asks for TypeScript ~6.0.3; `web/` keeps 03's 7.0.2 (the native compiler), which accepts the template's options as they are. The dev dependencies the scaffold brings are now pinned in 03's Web line. `tsc -b` checks three projects: the app (`lib` ESNext and DOM, `strict`, `noUncheckedIndexedAccess`), the unit tests (the app's settings plus Node's types) and `vite.config.ts`. `pnpm test` runs vitest in Node over `src/**/*.test.{ts,tsx}` only, and CI's web job builds before it tests.
- Testnet switch: `vite.config.ts` reads the mode's `.env` files and the shell's `VITE_` variables through `loadEnv` and fails a production build when `VITE_PUBKY_TESTNET` is defined at all, empty or `0` included. At run time `src/config/network.ts` picks the testnet only for exactly `1` in a bundle that is not a production one.
- Inter Tight comes from Google Fonts, with a system fallback stack. Its stylesheet is loaded with `crossorigin`, so the request carries no cookies, like every other request the app sends.
- Records: `web/src/records/` ports core's rules for keys, ids, paths, `pubky://` URLs and the four records the board reads, and puts the CLI's caps in `limits.ts` under their Rust names (`MAX_RECORD_BYTES`, `MAX_STATUS_BYTES`, `MAX_CREDITS`, `MAX_TARGETS` on sweeps, `MAX_LISTING_LINE_BYTES`, `MAX_PAGE_SIZE`, the page-bytes rule, the 1024-byte path). A parser refuses what core refuses, except what `JSON.parse` hides or a field it does not check: a repeated key (the last wins), nesting past serde_json's 128 levels, an escaped lone surrogate in an unchecked field, and a `schemaVersion` of `1.0`. The CLI skips such a record and the board shows it. A listing line goes through the same `pubky://` path rules, so a line with a space, `?` or control character is refused, where the CLI's SDK percent-encodes it and skips the entry; Sweepky's own entries never hold one.
- Network: `web/src/net/` is the board's one network path, a `Transport` seam (`transport.ts`) over the SDK (`sdkTransport.ts`). It does not use `publicStorage`: at 0.16.2 its `get` and `list` build their requests with `cross_request`, which sends `credentials: 'include'` in a browser (`pubky-sdk/src/actors/storage/core.rs` and `list.rs`), so 04's Stack and Live-ness now say `pubky.client.fetch` on `resolvePubky` URLs. `client.fetch` refuses `pubky://` URLs, adds a `pubky-host` header (so a CORS preflight goes first), sets `credentials: 'include'` only when the caller gave none, and builds its `Request` from the caller's own init, so every `GET` goes out with `credentials: 'omit'`, `redirect: 'error'` (as the CLI refuses a redirected answer) and the cache mode the caller asks for. A listing's query is the CLI's `page_url`: `limit=<n>`, `reverse=true`, then `cursor=<the last entry's pubky:// URL>`, through `URLSearchParams` so a cursor cannot add a parameter. Bodies are bytes under a cap, 1 MiB a record and `limit` × 4098 a listing page: a `Content-Length` over it is refused before anything is read, a streamed body at the chunk that crosses it, and the rest is cancelled. A 404 is an absent record or an empty listing; any other status, or a thrown error, is a failure with fixed text and at most the status, never the server's body, a URL or the SDK's message (its fetch errors carry the browser's text). The conditional re-GET is `cache: 'no-cache'`: the browser revalidates with the validators in its own HTTP cache and a 304 reaches `fetch` as the cached 200, so the board keeps no ETags. The SDK's `PkarrError` "No HTTPS endpoints" is "not browser-reachable", which a key with no pkarr record also gets; `getHomeserverOf` answering `undefined` is "no record" and a throw "lookup failed", both shown as unreachable. `sdk.ts` loads the SDK with a dynamic import, `Pubky.testnet()` or `new Pubky()`: its browser entry inlines the 2.5 MB WASM as base64, so its chunk is 3,404 kB, and `vite.config.ts` sets `chunkSizeWarningLimit` just above it. Unit tests use a fake SDK and never load it.
- Listings: `web/src/net/listing.ts` ports the CLI's newest-first listing (`ListingParser::page`, `read_listing`, `ListOrder::NewestFirst`) over the `Transport` seam: `ListLimits::DEFAULT` (100 a page, at most 1000 entries in 11 pages), every page `reverse=true` with `cache: 'no-cache'`, the stop at the first file of a record at or below the newest id seen, the same refusals in the same order with the CLI's fixed text (the transport's `tooLarge` is `PageTooLarge`), and a 404 as empty. Lines are split at byte 0x0A, measured in bytes after one `\r` is dropped, decoded as strict UTF-8 with a byte-order mark kept, and trimmed of Unicode White_Space as Rust's `trim` does, not by `String.prototype.trim`, which strips U+FEFF and keeps U+0085. Two differences from the CLI, both on lines no Sweepky writer produces: lines go through `parseListingLine` (see Records; it also reads a `pubky://pubky<z32>/` line, which the SDK refuses), and a path with a `.`, `..` or empty segment is refused as not a resource in both forms, as the SDK refuses it in a `pubky://` line, where the CLI's `url` crate resolves dot segments in an `https://` one.
- Polling: `web/src/store/poller.ts` is one pass, `boardStore.ts` runs it every 30 s (a zustand 5 `create` store whose state is the reducer's, with the scheduler, clock and transport loader passed in). The store polls only while a view subscribes: the first subscriber starts it, the last to leave stops it, so the landing hero and the board share one poll, and with no circle selected it loads nothing and sends nothing. A pass, in order: the admin's homeserver lookup when due (an admin that cannot be reached ends the pass, and `boardStatus` says so); `circle.json`, on every pass, so a roster change shows within one poll; then each roster key, at most 4 keys at a time and each key's requests one after another: its lookup when due, its re-reads, `bounties/`, then `sweeps/`. A key's first failed read ends its pass, as in `pull`. The caps are `pull/roster.rs`'s: the first 32 roster keys, the admin first (the admin alone when `circle.json` names another admin); per key and pass at most 16 new bounties, 32 new sweeps and 32 re-reads, shared as `reread_shares` and `next_turn` share them (done bounties at most 8, in rotation; open bounties and `running` sweeps half each of the rest); a `done` or `aborted` sweep is never read again. A lookup is due before a key's first, an hour after the last, and on the next pass after a failed read of its storage or a failed lookup; "no record" and "not browser-reachable" wait the hour, as a new lookup cannot change them sooner and the pkarr relays are rate-limited per IP. A key that cannot be reached stays in the roster. Every `GET`, `circle.json`, listings, first reads and re-reads alike, is sent with `cache: 'no-cache'`, so the browser's heuristic cache never answers with a stale listing or record. The hourly cache only decides which keys are polled and what reachability the Circle page shows: `client.fetch` on `_pubky.<key>` URLs still resolves through the SDK's own transport cache (about 60 s) and pkarr's, as P2c says for the CLI, so it neither routes requests nor cuts relay traffic.
- Discovered sweeps: `web/src/store/discovered.ts` decides what is due and `poller.ts` reads it, last in each roster key's share of a pass, with `cache: 'no-cache'` like every other `GET`. A bounty with `open: true` and status `open` has its `bounties/<id>.discovered.json` read on every pass. Once it is `done`, its file is read only in a pass that read the bounty itself: the pass that first sees it done (a fresh load, or the re-read that saw it flip), then whenever the done-bounty rotation re-reads it. `pull` writes the file for open bounties only, but 04 says a closed tab misses nothing, so a tab opened after the bounty was done reads the list once and shows the same sweeps per target as one that watched it. A bounty with `open: false` has no file the board reads. The reducer keeps the last good list when a file fails or does not parse, and keeps it whatever the bounty's status. The file's `cursors` are ignored, and nothing reads `/events/`. The list is parsed by `records/parse.ts` under the 1 MiB cap, its sweeps as sweep record URLs by `records/urls.ts`; as in core, a list naming anything else is refused whole, so no such entry is ever read and the last good list stands. After every roster key, the strangers' sweeps the held lists name are read from each sweeper's own storage, at most 4 sweepers at a time: of each list only the first 256 sweeps by keys outside the roster (`MAX_ACCEPTED_PER_BOUNTY` in `pull/feed.rs`); a sweep by a roster key, the owner's own included, is left to that key's listing, as `pull` does. Like a member's, a stranger's sweep is read again while `running` and never after `done` or `aborted`. Per pass at most 32 strangers' sweeps are read for the first time and 32 read again, across all bounties and apart from the members' budgets; past a cap each pass starts its share `turn × 32` round the list, `turn` being the pass's time over the poll interval, so every sweep is read within a bounded number of passes with no position stored. A stranger's first failed read, or no endpoint a browser can reach, ends that stranger's reads for the pass and fails neither the bounty nor its owner.
- Design tokens: `web/src/styles/` holds the hand-copied pubky-app values in `tokens.css` (the one file with colour literals, each value as 04 lists it, plus pubky-app's md radius and `xs`/`sm` shadows), `base.css` (type, a `--foreground` `:focus-visible` ring, fluid layout primitives, the destructive mark, the global reduced-motion rule), `buttons.css` and `sections.css`; `components/Button.tsx` and `Section.tsx` render them. Alpha fills are `color-mix(in srgb, <token> N%, transparent)`. `styles.test.ts` holds every text pair the CSS draws to 4.5:1 through `contrast.ts` (oklch through OKLab to sRGB with Ottosson's matrices, clamped per channel, alpha composited over `--background`); clamping is not the browser's chroma reduction, so the results are close, not exact. `--destructive` text measures about 4.4:1 on a card, so no rule colours text with it: `.state-mark--aborted` and `.state-mark--unreachable` are a dot beside a `--foreground` label, held to 3:1 as a non-text element. `--muted-foreground` on `--secondary` is about 3.8:1, and the test refuses any rule that draws it.
- App shell: `src/router.tsx` holds 04's five routes and a `*` not-found view inside `components/Layout.tsx` (a skip link to `<main id="main">`, Sweepky's own mark from `components/Mark.tsx`, also `public/favicon.svg`, a links-only `<nav>`, a "Built on Pubky" text link to https://pubky.org and MIT in the footer). `main.tsx` serves them with `createBrowserRouter` and `RouterProvider` from `react-router/dom`; tests render a `createMemoryRouter` with `react-dom/server`. `App.tsx` hands the board's one store and the circle choice down through React context (`useBoard(selector)`, `useCircle()`). `/b/:owner/:id` and `/s/:sweeper/:id` take a key raw or `pubky`-prefixed and a canonical id, and render the not-found view for anything else. The circle: `config/circle.ts` reads `?circle=` once per page load, over the build-time `VITE_SWEEPKY_CIRCLE`, both through `records/pubky.ts`; an invalid query value, or an invalid default, is ignored with a notice in the layout, and unset means no circle (the store sends nothing; the layout says "No circle selected"). A `?circle=` that chose the circle is added to every internal link by `components/CircleLink.tsx`, before any fragment (`/?circle=<k>#sweep`); the default needs no query. Route views are thin placeholders over the store until their own tasks fill them.
- Board page: `routes/Board.tsx` draws the intro strip, the floor plan (or the empty state), sweeps in progress, the ticker, sweeps today and recently done bounties from the selectors, at a clock that moves on every minute so a sweep fades to "left" and "today" rolls over without a new record. The strip's dismissal is the app's one use of browser storage (`components/introDismissal.ts`, one key, every access in `try`/`catch`, any failure read as "not dismissed"); its dismiss control and the "?" that restores it are buttons. The ticker (`components/Ticker.tsx`) moves only when its newest event happened after the page opened: the list is mounted afresh under a new key and runs a one-shot CSS animation, so the history the first polls bring in never moves it, and under `prefers-reduced-motion` (read through `matchMedia`, absent in Node) the class is not set at all. When the admin cannot be reached (no record, a failed lookup or not browser-reachable), the board shows a notice with the destructive `.state-mark--unreachable` dot beside "Unreachable", the word and mark the Circle page is to use for an unreachable member, so its task takes them from here. Record times render through `components/RecordTime.tsx`, which draws nothing for a time no `Date` can hold (an id can encode one past year 275760, and printing it throws).
- Circle page: `routes/CirclePage.tsx` draws `circleMembers` (the admin first, at most `MAX_MEMBERS`, as the reducer keeps the roster) through `components/MemberRing.tsx`: a dial with one node per member and a card per member with its circle.json label through `StrangerText`, homeserver, last activity, credits received (`trust.bounties` from `trust.owners`, as `trustLabels` counts them) and reachability. Last activity is the newest time any held record of the member gives (`createdAt`, `doneAt`, `startedAt`, `finishedAt`); its age sets the brightness: within a day `bright`, a week `lit`, 30 days `dim`, else or with no records `dark`. Brightness is a `--foreground` node, never text colour, and the card's "Last activity" says the same in words. "unreachable" (no record or a failed lookup) has the destructive mark beside it; "not browser-reachable" stays muted and says the browser can only use ICANN HTTPS endpoints; neither leaves the ring. The dial is drawn from 64rem up; narrower, the cards are a one-column list. With no circle selected, or an admin the browser cannot reach, the board's notice shows.
- Landing page: `routes/Landing.tsx` draws 04's six sections from `landing/copy.ts`, where every claim carries `sources` (`<file>#<anchor>` in 00, 02 or 06's known limits) and `landing.test.tsx` checks each anchor is a heading of that file and that no copy says "private". 04's draft cards that traced to none of them ("plan windows reset", "most code gets one set of eyes") were reworded and 04's table updated. The hero is the board's compact `FloorPlan` and `StatusNotice` from the same store, so an empty or unreachable circle shows the empty state. The install block and the Known limits link go to the README's `Install` and `Known limits` sections (the latter carries 06's list word for word, which the test compares) through one `REPO_URL` constant; the repository is not public yet, so those links do not open for visitors until it is. `/#post` and `/#sweep` are scrolled to by `landing/scrollToHash.ts`, a layout effect keyed on the location's hash and key with `behavior: 'auto'`, which leaves smoothness to base.css's `scroll-behavior` (off under reduce). react-router 8.4.0's `<ScrollRestoration>` does scroll to a hash, but it stores positions in session storage and takes over scrolling on every route, so it is not used. The link preview's cover is `public/og-cover.svg`, rendered to `og-cover.png` with headless Chrome (the command is in the SVG's `<metadata>`).
- Browser checks: `web/e2e/` holds Playwright specs that `pnpm e2e` runs on the installed Google Chrome (`channel: 'chrome'`, so nothing is downloaded and `playwright install` is never run); neither `pnpm test` (vitest's `include` is `src/` only) nor CI runs them, though `tsc -b` type-checks them with `vite.config.ts` in `tsconfig.node.json`. Playwright starts `vite` with `VITE_PUBKY_TESTNET=1` on port 5179 and stops it at the end. Each spec opens a new random circle. `layout.spec.ts`: `/`, `/board` and `/circle` at 375×812 and 1440×900 with `scrollWidth` no wider than the window; Tab from the top reaching every visible link and button in document order with an outline drawn; no `document.getAnimations()` under reduced-motion emulation; the intro strip's Run a sweep landing on `/?circle=<k>#sweep` with `#sweep` in view. `network.spec.ts`, with a cookie planted for `localhost` and the font hosts: no request to another origin carries `Cookie` or `Authorization` (own-origin requests do carry the cookie, which the spec checks so the rule cannot pass blind), every method is `GET`, `HEAD` or `OPTIONS`, no URL holds `/events`, the landing's other origins are only the two font hosts and the testnet relay, and the dev server sends no `X-Frame-Options` or `frame-ancestors`. A random key has no pkarr record, so the store never reaches a homeserver: these specs see only relay lookups and fonts, and cannot see a homeserver read sent with credentials. The e2e-testnet checks cover that. The spec answers the relay origin itself with a 404 (a key with no record) through `page.route`, because Chrome reports a request's cookies only once it is sent: with no relay listening, the lookups fail before that and the credentials rule would pass whatever the app did. So the specs need no testnet, and never touch one that is running.
- Hosting (post-approval): Vercel needs a rewrite of every path to `index.html`; Cloudflare Pages treats a project without a `404.html` as a SPA. Deployment protection must be off so the Vibes health cron gets a 200.
