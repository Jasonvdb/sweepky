# P2d — `sweepky-cli`: login through Pubky Ring

## Goal

`login` option A, the default: the Pubky Ring sign-in through a loopback page. This phase also completes the end-to-end test from [06](../06-verification-and-limits.md#verification) with its login-option parts, its check that two writers can share one saved Ring token, and its check that `logout` leaves the saved token unable to restore. It builds on [P2a](P2a-cli-identity.md) for the network config with the relay URL, the shared tail of `login`, `logout`, the config directories, the writers' lock and the capability constant, and on [P2c](P2c-cli-pull-done.md) for the end-to-end test.

## Build

- **`login` (option A, default):** `PubkyGrantAuthFlow::builder(caps, signin, "sweepky-cli").relay(cfg.relay).client(...)`, never the convenience constructor; capabilities exactly `/pub/sweepky/:rw` with the trailing slash; default grant format, no encryption scopes. A one-page loopback site (random port and path, one flow, timeout) with the QR, a copy-link button and live status, opened in the default browser; the same URL and a terminal QR as fallback. The page is a static HTML string with the QR rendered server-side as SVG by `qrcode`, no JS framework. After approval: check the granted capabilities include write on `/pub/sweepky/`, else sign out with a clear message; store the SDK's exported grant token in a 0600 file; show the expiry (two years) and warn within 30 days of it on later runs.

## Done when

- Both login options covered in the same test, as in [06](../06-verification-and-limits.md#verification): loopback page fetched (QR and link present, status "waiting"), relay host asserted local (the authorization URL's relay is the testnet relay), in-process approval (`PubkySigner::approve_auth`), status flip (to "approved"), the resulting grant writing a record (its `keys/<deviceId>.json`), a narrowed approval refused (read-only through `approve_auth_with_capabilities`, with the expected message), a recovery file passed to `login` rejected, wrong loopback path 404.
- These parts run in the test that [P2c](P2c-cli-pull-done.md) landed, with A and A's second install switched to the default Ring flow; B and C stay on `--identity`.
- In A's first install, which holds one saved Ring token, two writer commands run concurrently and both succeed: `circle add` of a synthetic pubky the test uses nowhere else, and `keys revoke` of the key the test injected under A's `keys/`. The writers' lock runs them one at a time, so neither loses its bearer to the other's restore ([02](../02-encryption-and-safety.md#device-keys)). Afterwards `circle.json` lists the new member and the injected key has `revokedAt` set. Both commands run after the checks P2c landed and before `logout`, so they change no group, credit or label the test asserts.
- After `logout`, restoring the Ring token that A saved at login returns 401.
- `cargo clippy -- -D warnings`, `cargo deny check` and `cargo nextest run` clean.

## Resolved questions

- **Client id.** The SDK validates only non-empty and up to 253 characters; Ring shows it as the app name on the approval screen and in its grant list. It is `sweepky-cli`, and it never changes between releases because saved sessions are compared against it. The board uses a different id in E4 so the two grants are distinguishable in Ring.

## Notes

- The SDK's convenience constructor sets no relay, so a testnet login through it would post its approval through the production relay ([03](../03-cli-and-skill.md#two-ways-to-log-in)).
- The authorization URL carries the relay channel secret, so it is never logged or written to disk ([03](../03-cli-and-skill.md#two-ways-to-log-in)).
- [P2a](P2a-cli-identity.md) unit-tests the recovery-file rejection. The end-to-end check here passes a recovery file to `login` itself, because [06](../06-verification-and-limits.md#verification) lists that check with the login options.
- The SDK hands the grant token back as a plain `String`; move it into a `SecretString` at once and write the 0600 file from that ([03](../03-cli-and-skill.md#rust-conventions-teaching-notes-keep-in-code-comments)).
- **A Ring login's local state** (`state.rs`, `ring/token.rs`). These are local files, not [01](../01-records-and-discovery.md) records.
  - `login.json` gets the kind `ring`: `{"schemaVersion": 1, "kind": "ring", "pubky": "<z32>", "homeserver": "<z32>", "grantExpiresAt": <unix seconds>, "deviceId": "<id>"}`. It has no `name`. `deviceId` appears once the shared tail has published the key, and unknown fields are kept, as for the `identity` kind. `grantExpiresAt` is the grant's `exp` as the homeserver reports it with the session. It is a public value, kept as a number so that a later run compares it with the clock without parsing a date. It is shown as RFC 3339 through `RecordTime::from_unix_seconds`, and a time past the year 9999 shows as "after 9999-12-31T23:59:59Z". No secret is ever added to `login.json`.
  - `<config>/grant.token` holds the SDK's exported string (`export_local_secret`) exactly, with no newline. For the bare grant Sweepky asks for it starts `pubky-grant-credential-v1:`; the unit test's synthetic token of that shape is 581 bytes. The file is 0600 in the 0700 config directory, written through `passphrase::write_secret_file` (a temp file created 0600, synced, renamed over the old file, then the directory synced). It is wrapped with the `--passphrase-file` passphrase when one is given, as [02](../02-encryption-and-safety.md#device-keys) allows for the Pubky credential.
  - Reading it goes through `read_private_file` and `open_secret_file`. The file must be at most 4 KiB (`MAX_WRAPPED_BYTES`), checked on its `lstat` before the open; links and files with a group or other permission bit are refused. The token must then be at most 1 KiB (`MAX_SECRET_BYTES`, so every token taken can also be wrapped), start with `pubky-grant-credential-`, and be printable ASCII only. The prefix check matters because `restore_session` tries anything without it as the secret of a cookie session. Every refusal is fixed text that names the file and quotes none of it.
  - The SDK's `String` is moved into a `Zeroizing` buffer and copied once into a `SecretString`. `GrantToken` has no `Debug`, `Display`, `Serialize`, `Clone` or `PartialEq`.
- **The granted-capability check** (`ring::grants_sweepky_write`, pure). One granted capability must both cover `/pub/sweepky/` and allow write. Coverage is the SDK's `scope_covers_path`: `/pub/:rw` and `/:rw` count, while `/pub/sweepky/keys/:rw`, the file scope `/pub/sweepky:rw` and `/pub/sweepkyx/:rw` do not. `/pub/sweepky/:w` counts and the read-only `/pub/sweepky/:r` does not. pubky 0.16.2 does not re-export the SDK's `Action` type, so write is matched by its letter `w` through the SDK's `From<&Action> for char`; naming `Action::Write` would need a direct pubky-common dependency, which is not pinned.
- **The sign-in page** (`ring/page.rs`, pure). `render_page(link, status_path, nonce)` returns the whole page as one HTML string; the loopback server makes the status path and the nonce and serves the page.
  - It holds the authorization URL's QR code as an inline SVG at qrcode's medium error correction, with qrcode's `<?xml ...?>` prolog taken off through `strip_prefix` (an SVG without it is refused in fixed text, never a panic); a copy button worded "Copy the link to paste into Ring on your phone", which copies with `navigator.clipboard.writeText` (127.0.0.1 is a secure context); the link as text in `<code id="auth-link">`; what is asked for, `/pub/sweepky/:rw` and `sweepky-cli`; and the status line `<p id="status" data-status="<status path>">`, which starts as "waiting for approval in Pubky Ring". Every value is escaped as HTML (`html_escape`: `&`, `<`, `>`, `"`, `'`) as it goes in.
  - It loads nothing (no script, stylesheet, image or frame, no form) and holds no web address but the SVG namespace and the link. Its one `<script>` and one `<style>` carry the nonce, and no element has an inline event handler or a `style=` attribute; the SVG uses only presentation attributes. So it needs no more than `script-src 'nonce-N'; style-src 'nonce-N'; connect-src 'self'`, and the server's policy can leave everything else at `'none'`. `render_page` refuses a nonce that is not CSP's base64 (one or more of `A-Za-z0-9+/-_`, then up to two `=`) and a status path that is not one `/` then only `A-Za-z0-9/-_.~` (so neither `//host` nor `/\host`), each in fixed text.
  - The script is a constant, the same for every flow; it takes the status path from `data-status` and the link from `auth-link`, so nothing from the flow is written into script text. About once a second it fetches the status path as it is (`cache: "no-store"`), whose body is one `ring::page::SignInStatus` word: `waiting`, `approved`, `refused` or `expired`. It shows each with `textContent`, never `innerHTML`, and stops on any word but `waiting`, or after five failed fetches in a row ("the terminal stopped answering; it shows how the login ended").
  - `approved` is worded as Ring's approval only: "approved in Pubky Ring; the terminal finishes the login, so you can close this tab". The granted-capability check and the write of `keys/<deviceId>.json` come after it, and that write can still fail with a 403 (the signup token forbids the path) or a 507 (quota); the terminal says so, the page does not. `refused` is "Sweepky refused this approval; the terminal says why", and `expired` asks for `sweepky login` again.
  - `terminal_qr(link)` draws the same link in block characters, two rows of modules per line, at the lowest error correction, so a 400-character link fits an 80-column terminal. Light modules and the quiet zone are blocks and dark ones blank, as `qrencode -t UTF8` draws them, which reads as dark-on-light on the usual light-on-dark terminal; the link printed beside it covers a terminal where that does not hold. A link too long for any QR version is refused in both QR codes with the fixed "the Pubky Ring sign-in link is too long for a QR code", which quotes none of the link.
- **The expiry notice** (`ring::expiry_notice`, pure, with the time as an argument). With more than 30 days left it says nothing. With 30 days (2,592,000 seconds) or less it warns, naming the expiry in RFC 3339 and `sweepky login`. At or past the expiry it gives the expired form. The arithmetic is checked, so any pair of times, `0` and `u64::MAX` included, is safe.
- **The loopback server** (`ring/loopback.rs`). `LoopbackServer::bind(link)` listens on `127.0.0.1:0`, an address and never a name lookup, so the system picks a free port. The path and the CSP nonce come from the SDK's CSPRNG (`Keypair::random().secret()`, 32 bytes each, written as 64 lower-case hex digits by the branch-free `identity::hex_digit`; pubky re-exports no random-bytes function). The path is kept in `Zeroizing` buffers and never logged or written to disk. The page is `render_page(link, "/<path>/status", nonce)`. `url()` gives `http://127.0.0.1:<port>/<path>`, a secret like the authorization URL. `serve(status, deadline, limits)` takes the server by value, so a server serves one flow and is never re-armed, and it reads the flow's `SignInStatus` from a tokio `watch` channel (tokio's `sync` feature, which pubky already turns on, so it adds no code).
  - It answers `GET /<path>` with the page (`text/html`) and `GET /<path>/status` with the status word (`text/plain`). The request target is compared with both in constant time: the lengths first, then an XOR of every byte pair folded into one value through `std::hint::black_box`. The compiler does not promise constant time, so this is a best effort. Everything else is refused with fixed text that quotes nothing from the request: another path, a prefix of the real one, the real one with a suffix or a query, `/`, `/status`, `/favicon.ico` and the absolute form get 404; a Host other than `127.0.0.1:<port>`, or none, gets 421; a method other than GET gets 405 with `Allow: GET`; a head that is not UTF-8, whose request line is not `<token> <target> HTTP/1.1`, with a header line that is not `<token>:<value>`, or with two Host headers gets 400; a head over 8 KiB gets 431.
  - Every answer carries `Cache-Control: no-store` (the page holds the relay channel's secret, so it stays out of the browser's disk cache), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Connection: close` and `Content-Security-Policy: default-src 'none'; script-src 'nonce-N'; style-src 'nonce-N'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`.
  - Bounds: at most 4 connections at once, each its own task in a `JoinSet`, with the rest waiting in the listen backlog, so an idle preconnect never holds up the page; one request per connection, its head read into a fixed 8 KiB buffer; 5 s per connection for the head and the answer together (`Limits::DEFAULT`). The parser uses `split` and `get`, never an index, and a test feeds it every cut of a valid head and 20,000 short runs of arbitrary bytes.
  - **When it stops (deviation from 03's first wording).** 03 said the server exits on approval, but the page's status can only flip if the page is still served after approval. So once the status is final (`approved`, `refused` or `expired`), the server stops as soon as one connection has served that final word, or 5 s (`Limits::linger`) after the status turned final if nobody asks, and always at the flow's deadline. It also stops at once when the status sender is dropped while the status is still `waiting`, since the flow can then never end. On the way out it aborts every connection still open and waits for their tasks, so none is left running; dropping the `serve` future aborts them too, through the `JoinSet`. 03's hygiene line now says so.
  - **Known limit.** Any local user or process can connect to `127.0.0.1`. The random path is the defence. The Host check refuses a web page that rebinds its own name to `127.0.0.1` (DNS rebinding), because its requests carry that name as the Host.
- **Opening the page (`browser.rs`; a new `Context` field, deviation from P2c's carry-forward, which had `Context` unchanged).** `Context` gains `browser: Browser`, which says how `login` opens the loopback page: `Browser::System` in the binary, `Browser::None` in the unit tests and for the end-to-end test's throwaway, B and C, and `Browser::Notify(sender)`, which hands the page URL to a test that plays Ring and fetches the page itself, so no test opens a real browser. `System` runs `/usr/bin/open <url>` on macOS and `xdg-open <url>` (found on `PATH`) elsewhere, the URL one argv entry and never a shell string, with standard input, output and error on `/dev/null`, and waits up to 5 s for it. A failed start or a failed exit is a warning line on standard error that names the failure and never the URL, not an error, so the terminal link and QR still finish the login; an opener still running after 5 s counts as started and is left running, since some `xdg-open` setups wait for the browser they start. The page URL is never logged; only the flow's stderr fallback prints it.
  - **Known limit.** The opener gets the page URL as an argument, so for the moment it runs any local user can read it with `ps`. The URL works only on the loopback address and for one flow, and the random path is already the defence against local users (see the loopback server's known limit).
- **The approval (`ring/flow.rs`, `sign_in_with_ring(ctx, timeout)`).** It builds the flow as `PubkyGrantAuthFlow::builder(&caps, AuthFlowKind::signin(), client_id()?)` with `.relay(Url::parse(settings.relay_url()))` and `.client(ctx.network.pubky().client().clone())`, the capabilities parsed from `SWEEPKY_CAPABILITY`, and never calls `.approval_format()`, so the link is a bare grant: `caps=/pub/sweepky/:rw`, `cid=sweepky-cli`, a `secret`, no `af` and no `epk`. `clippy.toml` bans the two convenience constructors that set no relay, `pubky::PubkyGrantAuthFlow::start` and `pubky::Pubky::start_grant_auth_flow` (a temporary call to each was flagged; the builder's `GrantAuthFlowBuilder::start` is not). Then it binds the loopback server for the link, writes the fallback to standard error (what is asked for, the page's URL, the terminal QR code and the link), opens the page through `Context::browser`, and runs the server and `tokio::time::timeout(timeout, flow.await_approval())` side by side in one task with `tokio::join!`, the status going to the server through the `watch` channel.
  - **Endings.** No approval in time, or the SDK's `AuthError::RequestExpired`: the status turns `expired` and the error is `no approval from Pubky Ring within <10 minutes>; run `sweepky login` again`. An approval whose server-reported capabilities fail `grants_sweepky_write`: the status turns `refused`, the session is signed out (which revokes the grant on the homeserver), and only then is the error returned, the fixed `ring::flow::NARROWED_GRANT` ("… Sweepky needs write on /pub/sweepky/, so it signed out again and saved nothing; approve the full request in Ring, or log in with `sweepky login --identity <name>` instead"), or a variant saying to revoke `sweepky-cli` in Ring when the sign-out failed. Any other SDK error goes through `remote::request_error` and drops the status sender while still `waiting`, which stops the server at once; the page then says the terminal stopped answering. The granted capabilities are only compared, never printed.
  - **Timeout.** `LOGIN_TIMEOUT` is 10 minutes. pubky 0.16.2 sets no deadline of its own on the wait: its relay listener long-polls the inbox with no timeout (`HttpRelayInboxChannel::poll(client, None)`, retried on each of the relay's ~25 s 408 answers, an error after three other failures in a row), and `RequestExpired` comes only when the listener stops without a message. The relay's ~5-minute TTL applies to an approval stored and not yet collected, which the flow collects at once. So the 10 minutes is Sweepky's bound alone, and no SDK TTL caps it. The server's deadline is the timeout plus one `Limits::linger`, so a page still open when the time runs out can read `expired`.
  - **The writers' lock is not held while the flow waits.** A human can take minutes to scan, and every other command on the install would wait that long for the lock and then fail. The `login` command takes the lock after `sign_in_with_ring` returns an approved session.
  - **Secrets.** The link and the page's URL appear on standard error and on the page only; every error is fixed text (tests check that neither the link nor its `secret` value is in one). `GrantAuthFlowState` and `save_local` are never used, and neither the flow nor the session is ever printed with `Debug`. The SDK itself logs the relay channel through `tracing` (`cross_log!`) at info level; Sweepky installs no subscriber, so nothing prints it.
  - **The unit tests** run on an `EphemeralTestnet` with its HTTP relay, with `test_support::RingStandIn` as Ring (a keypair signed up on the testnet, approving with `PubkySigner::approve_auth` or `approve_auth_with_capabilities`, and listing its grants through `GrantManager::list` with its own root session) and `test_support::RingPage`, which takes the page URL from `Browser::Notify`, fetches it with `loopback_get` (a raw `TcpStream` GET, read capped at 1 MiB within 10 s), un-escapes the link and resolves `data-status` against the page URL. The end-to-end test needs its own copy, because `test_support` is crate-private.
- **The end-to-end test's login-option steps** (`tests/end_to_end.rs`, where P2b's A logged in). Before A logs in, `login --identity <path>` of a recovery file the SDK makes at run time (`create_recovery_file` under `#[expect(clippy::disallowed_methods)]`) is refused by name, and A's config directory is not made. The test holds A's keypair as Ring would, signs it up on the testnet and gives A's two contexts `Browser::Notify`. A's first `login`: the page has its QR code and link, its `data-status` URL answers `waiting`, a wrong path gets 404, the link's `relay` is the testnet relay (host and port) and its `caps` exactly `/pub/sweepky/:rw`; a read-only `approve_auth_with_capabilities` makes the login fail with `NARROWED_GRANT`, the page says `refused`, and neither `login.json` nor `grant.token` exists. A's second `login`: `approve_auth`, the status flips to `approved`, the report shows the expiry, `grant.token` is 0600, `login.json` is a `ring` login as A, and A's `keys/<deviceId>.json`, read anonymously, holds `device.key`'s key. Every later write as A's root key (the bounty rewrites, the injected key) signs with that keypair; the throwaway's still read its identity file. A2 logs in with a second approval by the same keypair, so P2c's identity-file copy is gone. The stand-in reads the page with a raw `TcpStream` GET capped at 1 MiB within 10 s, as `test_support::loopback_get` does.
- **The `login` command (`ring/login.rs`).** `login::login` hands a missing `--identity` to `ring::login::login`; `--homeserver` or `--signup-token` without `--identity` is refused first, in fixed text that quotes neither value, before any file is read or request sent. A Ring login asks nothing on standard input (the approval happens in Ring), so `--no-input` does not stop it (03 says so).
  - **Before any request**, files only: with no `login.json` (a first Ring login), nothing may be at `device.key` (`device::refuse_unrecorded_device_key`, P2a's "never replaces" rule and text, now shared with `create_device_key`). Only the path is checked, so a wrapped key file stops the login the same way without `--passphrase-file`. A `grant.token` that no `login.json` records (an orphan) is noted. An `--identity` login, or a kind this build does not know, is told to `logout` first or use another `SWEEPKY_HOME`; a Ring `login.json` is a re-login (below). After a Ring login, `login --identity <name>` is refused by P2a's plan rule (only the identity logged in may log in again).
  - **After approval**, with the lock not yet taken: `as_grant().session_info()` gives the pubky, the homeserver (`login.json`'s `homeserver`) and `grant_expires_at`, and `export_local_secret()` is mapped straight into `GrantToken::from_exported` in the same statement. A failure here signs the grant out.
  - **Under the writers' lock** (`save_grant`, generic over `KeyStore` with the sign-out passed as an async closure, as `logout::retire` does): the checks above again (another login may have finished meanwhile); `grant.token` written (0600, wrapped with `--passphrase-file`, replacing an orphan whole); then P2a's shared tail unchanged (`login::record_login_and_check_keys`) with the grant's session, which publishes `keys/<deviceId>.json` as the capability probe and writes `login.json` as a `ring` login last. Any failure under the lock, or of the lock itself, signs the grant out (revoking it), and a tail failure puts `grant.token` back as it was (removed, or the replaced token written back; see the re-login and orphan bullets below); the tail rolls back its own `device.key` and install entry as in P2a. So `login.json` never names a Ring login whose token is not on disk. On success the session is dropped, not signed out, since signing out revokes the grant; later commands restore it from the token. The session is owned by a small `GrantKeyStore` for this, because `SessionKeyStore` only borrows one and the sign-out takes it by value.
  - **The report**: pubky and homeserver, the token's file, the expiry in RFC 3339 and that it is two years from approval, P2a's device-key lines with the backup reminder, the wrapped files (the grant token and `device.key`) with `--passphrase-file`, and the key check. Only the files this run wrote are listed as wrapped, so a re-login, which reuses `device.key`, lists the token alone. What became of the grant replaced (a re-login's, or an orphan's): "Revoked the earlier sweepky-cli grant …", nothing when it was already revoked or expired, or a warning that it may still be listed in Ring and to revoke the older `sweepky-cli` grant there. Neither the token nor the link is ever printed.
  - **Logging in again through Ring (re-login).** The way past a grant revoked in Ring or about to expire (02's "revoke it in Ring and log in again", and the advice of the 30-day warning), without losing the device key and so the sweeps encrypted to it. It follows P2a's plan rule: only the pubky `login.json` names may log in again. Before the flow, files only: `login.json` is a Ring login; `device.key` is read and unwrapped as the reuse will need (`login::read_recorded_device_key`, so a wrapped key without `--passphrase-file` stops it with P2a's `NeedsPassphrase` text before there is anything to scan, and a missing one with P2a's restore hint); and `grant.token` is read (`read_grant_token`, same rule). Under the writers' lock, after approval: (1) the files are read again, and what is on disk now decides (a login or logout that finished during the scan makes this a re-login or a first login); the approving pubky must equal `login.json`'s, compared as bytes; another pubky is refused in fixed text naming only `login.json`'s pubky, nothing local is written, and the new grant is signed out; (2) the new token is written (0600, wrapped with `--passphrase-file`), the old one held in its `GrantToken` (a `SecretString`); (3) P2a's shared tail runs its reuse branch (`login.json`'s `deviceId` kept, so `reuse_device_key` reads its own record back and refuses a revoked or replaced one with nothing changed; a missing record is published again); (4) the tail writes `login.json` with the new grant's `homeserver` and `grantExpiresAt`, every other field, unknown ones included, kept; (5) only then is the old grant revoked through `ring::revoke_grant` (restore from the held token, nothing done with the session, sign-out, a second restore that must get 401). A `grantExpiresAt` already past sends no request; a first restore that gets 401 is a grant already ended, and the report says nothing about it. Any other failure in step 5 is a warning telling the user to revoke the older `sweepky-cli` grant in Ring, never an error, since the new login works. A failure in steps 2 to 4 writes the old token back (wrapped with `--passphrase-file` when one is given) and signs the new grant out, so `login.json` and the token it records stay as they were. The device key is never replaced or deleted.
  - **An orphan `grant.token`** (no `login.json`) is read under the lock before the new token replaces it, and once the new login is saved its grant is revoked the same way, with the same warning when that fails or the orphan cannot be read (wrapped without `--passphrase-file`, or not a token). A first login whose tail fails writes the orphan back, or removes the new token when the orphan could not be read. The restore of a replaced token checks nothing about the session it gets, since it is only signed out, and an orphan's grant may be another pubky's.
  - **Known limit.** A crash (a kill or a power loss) after `grant.token` is written and before the tail writes `login.json` leaves an orphan token whose grant is still live and listed in Ring. Nothing local names it, so `logout` has nothing to log out; the next Ring login on this install revokes it as above, or the user revokes the older `sweepky-cli` grant in Ring.
  - **Tests.** On the testnet (Postgres through `TEST_PUBKY_CONNECTION_STRING`): a re-login as the same pubky keeps `deviceId` and `device.key`'s bytes, reports the reuse, and the new token restores while the old one, copied before, gets 401, with Ring listing one `sweepky-cli` grant; a re-login after the old grant was signed out elsewhere succeeds with nothing said about it; a re-login approved by another pubky is refused in fixed text, leaves `login.json`, `grant.token` and `device.key` unwritten, and that pubky lists no `sweepky-cli` grant; an orphan holding a live grant's token gets 401 after the new login. Offline: a wrapped `device.key` without `--passphrase-file` stops the re-login before the flow; a revoked own record refused by the reuse branch puts the old token back, leaves `login.json` and `device.key` unwritten and signs the new grant out once.
  - `NOT_LOGGED_IN` names both `sweepky login` (Pubky Ring) and `--identity`, and the wrapped-files report says every command but `init`, `keys list` and `circle show` needs `--passphrase-file` again.
- **The Ring writer session (`session.rs`).** `session::sign_in`, and so `with_writer_session`, matches `login.json`'s kind: `identity` signs in with the identity's key as in P2a, unchanged; an unknown kind is refused as before; `ring` restores. All of it runs under the writers' lock, because each restore mints a fresh bearer for the grant and the homeserver drops the one before it (a test keeps a clone of one session's handle and sees it refused after the next restore).
  - **Before any request**, in order: `clock::now_unix_seconds()` (so a clock before 1970 is refused in words before the SDK's own clock read, which panics on one); `ring::refuse_expired_grant`, which refuses a `grantExpiresAt` at or past now, in the expired notice's own text, and a Ring `login.json` with no `grantExpiresAt`; then `grant.token` through `read_grant_token` (`open_secret_file`, the 4 KiB file cap and the 1 KiB token cap), a missing file refused in fixed text naming both files. The token is a `GrantToken` (a `SecretString`), exposed only as the `&str` that `Pubky::restore_session` takes, and wiped when dropped.
  - **The restore** maps its error through `ring::restore_error`: a 401 or 403, or the SDK's authentication error (an expired or mismatched stored grant), is the fixed `GRANT_NOT_ACCEPTED`, which says to run `sweepky login` again; anything else is `remote::request_error`'s fixed text. The SDK's own text is never shown.
  - **The check** (`ring::check_restored_session`, pure): the restored grant's `session_info()` must give `login.json`'s pubky (compared as bytes), the client id `sweepky-cli` exactly, and capabilities that pass `grants_sweepky_write`; each refusal is a fixed text. The server's values are only compared, never printed. A session that fails is dropped, not signed out.
  - **The end of the session.** `WriterSession` records its kind. `with_writer_session` ends it with `WriterSession::end`: an identity session is signed out, always attempted, as in P2a; a Ring session is only dropped, never signed out, because signing out revokes the grant every later command restores from (a test checks that Ring still lists the one `sweepky-cli` grant and the token restores again). `WriterSession::sign_out` stays explicit for `logout`, where revoking the grant is the point.
- **The expiry warning on later runs (`lib::run`, `ring::expiry_warning`).** Printed once per command, as `warning: <notice>` on standard error, by `lib::run` before it dispatches every command but `init`, `login` and `logout` (`shows_expiry_notice`, an exhaustive match). It reads `login.json`'s `grantExpiresAt` and the clock only: no token, no passphrase and no network, so it comes before any network read and works offline. A `login.json` that is missing, broken or not a Ring login, or a clock that cannot be read, prints nothing, since the command reports its own error. `with_writer_session` and `sign_in` never print it, so `run` (two sessions) and a `pull` that writes `discovered.json` still print one line. A read-only command with an expired grant prints the expired form and still runs; a writer command is refused before the restore.
- **`logout` for a Ring login (`logout.rs`, `ring::revoke_grant`).** P2a's steps 3 and 4 for the grant, in [02](../02-encryption-and-safety.md#device-keys)'s order, all under the writers' lock. First, files and clock only: `login.json`'s `grantExpiresAt` at or before now (`ring::expired_grant_at`) is a grant already dead, and no request is sent with the token. Otherwise `ring::revoke_grant`, a crate-private helper the re-login step reuses, runs (1) a restore from `grant.token` (`session::restore_saved_grant`, the writer session's restore and checks, but telling a 401 apart as `Restored::Refused`); (2) with that live session, the revoke of this install's `keys/<deviceId>.json` (`keys::revoke_if_published`, as for an identity); (3) the sign-out, which revokes the grant (`WriterSession::sign_out_checked`, whose failure is returned, not a warning); (4) a second restore, which must get a 401. Its outcomes are `Revoked` (a 401 after the sign-out), `AlreadyRevoked` (the first restore got a 401) and `NotConfirmed` (the sign-out failed, or the second restore was a session or another error). Only after `Revoked`, or for a dead grant once its key record allows it (below), are `grant.token` (in place of an identity), `device.key`, `login.json` and the owner's `installs.json` entry deleted, each through `private_fs::remove_private_file`, the token first. The report names the grant's end ("revoked … restoring the saved token now gets 401", "already revoked or expired", or "had expired, at <RFC 3339>"), `grant.token` and P2a's "deleted, not overwritten" lines. `credential.lock` and `pull.lock` stay; `feed-cursors.json` and `poll-state.json` are not touched. Every message is fixed text: no SDK words and never the token.
  - **Deviations from P2a's identity logout.** (a) A failed device-key revoke does **not** sign out: for Ring the sign-out revokes the grant, which would lock this install out of the key it could not yet revoke. The session is dropped, nothing is deleted, and the message says to run `logout` again, or to revoke `sweepky-cli` in Ring and the key from another install with `sweepky keys revoke <id>`. (b) A failed or unconfirmed grant revoke stops before the token is deleted (`GRANT_NOT_CONFIRMED`: run `logout` again, or revoke `sweepky-cli` in Ring), so a rerun can finish. (c) **A locked-out install** (an expired `grantExpiresAt`, or a first restore that got a 401) cannot restore a session, so it reads its own `keys/<deviceId>.json` anonymously from public storage through the capped public read (`device::PublicKeyReader::get_key`, which is `remote::get_public` with `MAX_RECORD_BYTES`, refusing a redirect) and parses it with `DeviceKey::from_json`. Revoked, or not published (404, P2a's `NotPublished`), or no device id recorded: it deletes the local files. Unrevoked: it stops, deletes nothing and names `sweepky keys revoke <id>` to run from another install. A read that fails (a request error, a body over the cap, a record that does not parse) stops in fixed text and deletes nothing. This is how 02's "revoked from another install with `keys revoke`" lets this install's logout finish. A Ring `login.json` with no `grantExpiresAt` is not taken as expired: logout tries the restore and the homeserver decides.
  - **Tests.** On the testnet: a Ring logout leaves `keys/<deviceId>.json` revoked with the same recipient (read anonymously), deletes the four files, keeps both locks and leaves the two state files byte-for-byte, and the token the test copied before logout then restores to an error whose status is 401 (Done when, unit level); a grant revoked before logout (the test restores and signs out the token) stops while the record is unrevoked and finishes once the test revokes it with the root key. With fakes through `retire_ring`'s four seams (restore, key revoke, sign-out, own-record read): the order of a success, each failure before the 401, the expired paths with no restore sent, the token deleted before the install files, and the unreadable own record.
- **The end-to-end test's last steps** (`tests/end_to_end.rs`, after P2c's last asserted `pull` on A1). Right after A's Ring login, the test copies `grant.token`'s content into a `Zeroizing` buffer, which no assertion quotes. Then, on A1 and its one saved token, `tokio::join!` runs `circle add` of a `Keypair::random()` pubky used nowhere else and `keys revoke` of the key the test injected under A's `keys/` (`added-by-the-test`); both succeed, an anonymous read of `circle.json` (through `Circle::from_json`) lists the new member, and the injected record has `revokedAt` set with every other field as it was. Each command restores its own session from the token, and the writers' lock runs them one at a time. Then A1's `logout` revokes A1's key record and the grant and deletes `grant.token`, `device.key` and `login.json`, while `credential.lock` and `pull.lock` stay 0600. Last, `restore_session` of the copied token fails with `pubky::Error::Request(RequestError::Server { status: 401, .. })`.
