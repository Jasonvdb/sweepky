# P1b — `sweepky-core`: encryption, envelope and groups

## Goal

The security half of `sweepky-core`, built on the records from [P1a](P1a-core-records.md): encryption, padding, manifest binding, the package envelope, secret handling, and finding groups with proposed credits. Everything here is tested without a network. No I/O in this crate.

## Build

- **Encryption:** age wrap/unwrap to N recipients; padding of the plaintext to size buckets before encryption; manifest-binding check on the decrypted envelope (sweeper, bounty, targets must match the record's path and contents); strict parsing of `age1…` recipients and `alg`; C2SP CCTV vectors.
- **Package envelope:** build the one-document package from an in-memory list of (relative path, bytes): `findings.json` → `findings`, every other UTF-8 file → `attachments` keyed by relative path, non-text entries reported for the CLI to warn about; and split it back out. No archive format, no compression. The directory walk and its safety rules are the CLI's.
- **Secrets:** `age::x25519::Identity` held directly (it zeroizes itself); `SecretString` for identity strings, passphrases and the grant token; `Zeroizing<Vec<u8>>` for buffers.
- **Groups:** combine several `Findings` into groups by location (file plus sink scope where present, else line proximity), with equal ids as a second hint; keep every raw record; `reportedBy: [sweeper, …]` per group in upload order; a `trusted` flag per sweep that decides whether its content enters the merged output while attribution counts it either way; `propose_credits(owner)` returns every sweeper other than `owner` who contributed to at least one group.
- **Fixtures:** synthetic run directories (one Cloudflare-shaped, reusing P1a's Cloudflare fixture, and one common-format) whose findings share one location under different ids, plus a pair sharing an id at unrelated locations, and one non-text file, under `fixtures/`.

## Done when

- Unit tests pass for: envelope → pad → encrypt → decrypt → files round-trip of the synthetic run dir, with one non-text file reported; the padding test asserting the final ciphertext length lands on the bucket; a recipient added after encryption cannot decrypt; manifest binding (wrong path or wrong sweeper rejected); strict recipient and `alg` parsing, bad ones rejected; the C2SP CCTV age vectors (hybrid ones skipped); grouping puts the shared location in one group with both reporters and keeps the shared-id pair apart, `propose_credits` returns both and leaves out the owner when the owner also reported it, and an untrusted sweep is attributed but not merged.
- `cargo clippy -- -D warnings` and `cargo deny check` clean.
- Public API documented with `///` and `cargo doc --no-deps` warning-free.

## Notes

- Keep `age` on default features: no `plugin`, no `ssh`.
- The crate must not depend on `tokio`, `reqwest` or `pubky`. The CLI owns the network.
- No secret type implements `Debug`, `Display` or `Serialize` in a way that prints the secret. Errors never include key material or plaintext.
- Sealed content gets the same care, which meets P1a's carry-forward. `Findings`, `Finding` and `Location` no longer derive `Debug`; theirs is written by hand and prints the type, the schema version and counts only (findings, locations in total, `extra` fields, unknown fields), then `..`: no text, no open string (`status`, `severity`, `confidence` and a location's `kind` are agent-written too) and no line number. `Manifest`'s prints its typed fields, which say no more than the public records (the sweep record and its path, and the revs the bounty pins), and of `extra`, whatever a newer client sealed, only its count. Each impl names every field with no `..`, so a field added later does not compile until someone decides whether it may print. Serializing is unchanged, and an `assert_eq!` on these types still works, but a failing one prints counts only.
- The recipient rules are P1b's choice where [02](../02-encryption-and-safety.md#who-can-read-a-sweep) says only "a strictly parsed recipient". `AgeRecipient` accepts a string only when, in this order: it is exactly 62 bytes, `age1` and then lower-case bech32 characters only (checked before anything decodes it); age's own parser accepts it (human-readable part, checksum, 32-byte length); age writes it back unchanged, which refuses set padding bits; and it is not one of the 14 `LOW_ORDER_RECIPIENTS`, the seven small-order X25519 u values of libsodium's list (0, 1, the two points of order 8, p − 1, p and p + 1), each with bit 255 clear and set. age 0.12.1's parser accepts upper case and all 14 of those, and `Encryptor::with_recipients` then panics ("Generated the all-zero esk"), so without the list a malformed key under an owner's `keys/` would crash a sweeper's `submit`. Recipients compare by their string, not by age's `==`, which reads keys modulo p with bit 255 ignored. The parse still accepts a string with bit 255 set, or a u value at or above p, that is not of small order: no real key is written that way, and the matching identity could not open a sweep encrypted to it, because age's key derivation uses the bytes as written. Since such a string never equals the real key's, a sweeper's key pinning (P2b) sees it as a new key.
- `DeviceKey::encryption_recipient` checks `alg` first (exactly `age-x25519`, case and whitespace included), then `revokedAt` (must be `null`), then the recipient. Its errors, and those of `AgeRecipient` and `DeviceIdentity`, hold no data, so they cannot carry input text or key material; age's own error text is dropped.
- The identity rules are P1b's choice too. `DeviceIdentity` holds `age::x25519::Identity` directly and implements none of `Debug`, `Display`, `Serialize`, `Deserialize`, `Clone` or `PartialEq` (a compile-time test checks it). Its string goes only into and out of a `SecretString`: `from_secret` accepts exactly 74 bytes starting with the upper-case `AGE-SECRET-KEY-1`, then age's parser, and trims nothing, so a trailing newline is refused. Two identities are never compared, so no constant-time comparison is needed. Identities come only from age's `Identity::generate` (the OS random number generator).
- Our own source and tests commit no literal age secret key: tests generate identities at run time. The vendored C2SP CCTV vectors are the one exception.
- The sealing limits are P1b's choice where 02 sets none. `PADDING_BUCKET_BYTES` is 02's 64 KiB, which is also age's chunk size, so a padded package is a whole number of chunks; an empty package pads to one bucket. `MAX_PACKAGE_BYTES` (in `schema.rs`, beside the other caps) is 32 MiB: at least `MAX_FINDINGS_BYTES`, a whole number of buckets, and above 16.2 MiB so the CCTV 257- and 258-chunk vectors (up to 16,847,065 bytes) decrypt. `MAX_RECIPIENTS` is 32 distinct recipients; a repeated one is dropped before counting, and P2b's per-owner cap must leave room for the sweeper's own key. `MAX_HEADER_BYTES` is 8 KiB: age 0.12.1's buffered header reader re-parses the whole header from its start for every line it reads, so a header of tiny stanzas costs time growing with the square of its size (6 s in a release build at 64 KiB, 96 s in a debug build; about 0.1 s at 8 KiB), and 8 KiB holds about 80 X25519 stanzas, one Diffie-Hellman each. It still holds the longest header `encrypt` writes (3,396 bytes to 32 recipients, checked at compile time) and every CCTV header (the largest is 3,184 bytes). `MAX_CIPHERTEXT_BYTES` is `MAX_HEADER_BYTES` + 16 + `MAX_PACKAGE_BYTES` + 16 × (`MAX_PACKAGE_BYTES` / 64 KiB) = 33,570,832 bytes; P2c uses it as its download cap.
- `decrypt` checks the length against `MAX_CIPHERTEXT_BYTES`, then searches only the first `MAX_HEADER_BYTES` + 4 bytes for `\n---`, the start of the MAC line. It is `HeaderTooLarge` only when the input is longer than `MAX_HEADER_BYTES` and has no marker there; a shorter input goes to age, which refuses it as `InvalidHeader`. age's errors map by stage, matched on the variant only, one to one onto CCTV's expected results: any error from `Decryptor::new_buffered` is `InvalidHeader`; from `decrypt()`, `NoMatchingKeys` and `DecryptionFailed` are `NoMatchingKey`, `InvalidMac` is `InvalidMac`, and the rest (the enum is `non_exhaustive`) `InvalidHeader`; an I/O error while reading the payload is `InvalidPayload`; a plaintext over `MAX_PACKAGE_BYTES` is `PlaintextTooLarge`. `decrypt` hands age the X25519 identity alone, so a hostile scrypt stanza costs no scrypt work.
- age's errors are never formatted. age builds its messages with i18n-embed, whose rust-embed (without `debug-embed`) reads age's locale files from the cargo registry at run time in a debug build, which would be file I/O from core and a panic where those files are missing. age also builds one such message itself, while reading, for a final chunk that is empty after full ones; `decrypt` refuses that payload shape (a length of k × 65,552 + 16 bytes for k ≥ 1 after the nonce) as `InvalidPayload` before reading, which changes no outcome, since such a payload is never valid. Only the file's writer can make that chunk authentic, so the CCTV vector `stream_last_chunk_empty` is what exercises it.
- `tests/cctv_age.rs` reads files at run time, set against the Goal's "No I/O in this crate": the library does none, and this test, an integration test that Cargo builds as a separate crate against the public API, is the one that does. It reads the C2SP CCTV age vectors vendored in `fixtures/cctv-age/`, all 147 files of `age/testdata` at CCTV commit `50a8ecf2a220f4c8bdc4f085789b8e85c26829e7`, byte for byte (0BSD, CC0 or Unlicense, so no attribution). `fixtures/fetch-cctv-age.sh` re-vendors them by hand; no test fetches anything. Their `AGE-SECRET-KEY-1…` lines are published test keys, which a secret scanner may still flag.
- How the CCTV vectors run is P1b's choice where 02 says only that they run. Every vector is in one group and each group's size is asserted exactly, so none is skipped silently. The 19 hybrid ones (an `AGE-SECRET-KEY-PQ-` identity) are skipped. The 36 armored ones, which CCTV allows ignoring, are asserted to be refused by `decrypt` at the header, since packages are binary and age's `armor` feature is not compiled in: 35 as `InvalidHeader`, and `armor_garbage_encoded` as `HeaderTooLarge`, because it inflates to an armored file whose first `\n---` is its END line, past `MAX_HEADER_BYTES`. The 24 scrypt ones run through `age::scrypt::Identity` with a maximum work factor of 16, so `scrypt_work_factor_23` is a header failure. The 68 X25519 ones run through `decrypt` with identities read by `DeviceIdentity::from_secret`, each expected result mapping to exactly one outcome: `Ok` with the plaintext's SHA-256 equal to `payload`, or `NoMatchingKey`, `InvalidHeader`, `InvalidMac` or `InvalidPayload`. Last, every vector, hybrid ones included, goes through `decrypt` with a key it was not written to and must be refused at the header without a panic.
- Two CCTV vectors are lenient. `stanza_missing_body` and `stanza_missing_final_line` expect a header failure, but age 0.12.1 still accepts stanzas without the short final body line, an older form, and decrypts them; age's own CCTV test makes the same exception. The test allowlists exactly those two and asserts that they still decrypt, so it fails if a later age starts refusing them.
- The CCTV test's dev-dependencies are not in 03's original table and were added to it: `sha2` =0.10.9, the release age uses at run time, for the `payload` hashes, and `miniz_oxide` =0.9.1, for the zlib-compressed vectors, inflated with a 32 MiB limit.
- `encrypt` takes only a `PaddedPlaintext`, writes binary age with no armor, and adds no recipient of its own and never a scrypt one. Plaintext lives only in `Zeroizing` buffers allocated once at their final size: padding copies the package into a buffer of the bucket's capacity (or, from `SweepPackage::to_padded`, serializes it straight into one), and decryption allocates `min(ciphertext length, MAX_PACKAGE_BYTES + 1)` up front and reads into it with its own loop rather than `read_to_end`, which grows its `Vec`. The buffer's fixed length is the read cap: when it fills, the plaintext is over the limit. age keeps buffers of its own that this crate cannot wipe: its encryptor's 64 KiB chunk buffer is freed unwiped, and its decryptor builds each chunk's buffer by shrinking a `Vec`, which may leave a copy behind.
- The package envelope follows 01's sweep package: `SweepPackage {schemaVersion, manifest, findings, attachments?}`, with unknown top-level fields kept in `extra`. `from_json` goes through `schema.rs`'s `parse_record`, the one record parse (the size cap, then `schemaVersion` alone, then the whole document), as P1a's carry-forward asks, but its cap is `MAX_PACKAGE_BYTES` (32 MiB), not the `MAX_RECORD_BYTES` the carry-forward names: that is 1 MiB, and the findings alone may be 16 MiB (`MAX_FINDINGS_BYTES`). The findings' own `schemaVersion` is checked by `SchemaVersion`'s deserialize, so a newer one there is a `Json` error, not `UnsupportedVersion`. JSON reads the padding as trailing whitespace, so a decrypted plaintext parses as it is. `attachments` is optional: a missing key or `null` reads as an empty map, and an empty map is left out when writing.
- Attachment keys are `AttachmentPath`s, P1b's choice where 01 says only "relative file name": `RepoPath`'s lexical check (at most 512 bytes; no empty, `.` or `..` component; no leading `/`, `-` or `:`; no backslash, control, bidi or line-breaking character) plus no trailing `/`. `Attachments`, the map, refuses `findings.json` (`FINDINGS_FILE`) as a key both ways in: from JSON, which rejects the whole package as a `RecordError` that quotes nothing, and through `insert` or `TryFrom` a map, which gives `PackageError::ReservedName`. So no package, parsed or built, holds two entries that split to `findings.json`; `audit/findings.json` is an ordinary attachment. A key JSON repeats keeps its later entry, as in the manifest's `targetShas`. What a lexical check cannot see stays with the code that writes the files (P2c): keys that differ only in case, `FINDINGS.json` beside the findings included, and symbolic links on the way.
- `to_padded` serializes twice: into a byte counter, which learns the length and refuses a package over `MAX_PACKAGE_BYTES` before anything is allocated, then into a `Zeroizing` buffer allocated once at the padded size (padding's crate-internal `PaddingWriter`), which refuses any write past the counted length, so it never grows; then it pads with spaces. `SweepPackage`'s `Debug` prints the schema version, the manifest and findings through their own redacting `Debug`, and counts for the attachments and unknown fields; `Attachments`' prints its length. There is no `Display`. The strings in a package, parsed or built (the findings' text and the attachments), are ordinary `String`s and are not wiped when dropped: only the byte buffers on the way in and out are (`SweepFile`, `PaddedPlaintext` and `Plaintext` on either side of age, and `PackageFiles`).
- Building and splitting a package are P1b's choices where 01 and 03 say only which file becomes what. `SweepPackage::build` takes the manifest and a `Vec` of `SweepFile`s, each a path relative to the directory the CLI chose to walk (P2b picks it, say `audit/`), `/`-separated as found, and its bytes in a `Zeroizing<Vec<u8>>`; it does no I/O. The file whose whole path is `FINDINGS_FILE` is the findings, read by `parse_audit_findings` (its 16 MiB cap and the recursion limit) with the manifest's playbook, so a Cloudflare array is converted under that playbook and a common-format document keeps its own. It is required (`MissingFindings`), and a malformed one is `Findings(ConvertError)`. Every other file is an attachment when its path is a clean `AttachmentPath` and its bytes are valid UTF-8 (`String::from_utf8`, which reuses the buffer). Otherwise it is left out, its bytes wiped, and listed in `BuiltPackage::skipped` as `BadPath` or `NotText` (the path is checked first), with its path as given and in input order, for the CLI to sanitise and warn about. A path given twice is `DuplicatePath`, never last-wins, `findings.json` included, checked before any file is read. The attachments' text is counted against `MAX_PACKAGE_BYTES` as it is read, and the assembled package's JSON once more, so a package `build` returns always pads (`TooLarge` otherwise). Until the package is assembled each text sits in a `Zeroizing`, so any error wipes them all, and a package refused for its size has its attachment texts zeroized; a returned package's strings are ordinary `String`s, as above. `PackageError` gained `MissingFindings`, `DuplicatePath { index }` and `Findings(ConvertError)`, so it is `Clone` but no longer `Copy`; no variant holds a path or content.
- `SweepPackage::into_files` consumes a package and returns `PackageFiles`, a map from `AttachmentPath` to `Zeroizing<Vec<u8>>`: `findings.json`, the findings as pretty-printed common-format JSON written into a buffer allocated once at its counted length, and every attachment's text, moved without a copy into a wiped buffer. The map type and `Attachments`' reserved name make every key unique, with `findings.json` exactly once; if an attachment ever sat at `findings.json`, the split would fail with `ReservedName` rather than pick one. The manifest and the unknown top-level fields are not files and are dropped. `SweepFile`, `SkippedFile` and `PackageFiles` print no path and no byte in their `Debug`: `SweepFile` and `PackageFiles` print a length, `SkippedFile` its reason.
- Manifest binding is P1b's reading of 02's authorship rule and of the Build line. `Manifest::check_binding(&SweepRef, &Sweep)` checks, in this order: that the manifest's `sweeper` is the owner of the path the record and the package were fetched from (`SweeperMismatch`, compared by key bytes, so either spelling of a key is the same sweeper); that its `bounty` is the record's, owner and id (`BountyMismatch`); and that its `targets`, the record's `targets` and the keys of its `targetShas` are one set, with no target listed twice in either list (`TargetsMismatch`; ids compare exactly, case included). The playbook and the timestamps are not compared: `submit --playbook` (P2b) may name another playbook than `run` wrote, and the times are the CLI's. `BindingError`'s three variants hold no data. The `SweepRef` must be the path the caller fetched from (the sweeper's own storage, `SweepRef::url` and `package_url`), never a value read from the feed, the record or the package. Every value compared is public, so plain `==` is right and no constant-time comparison is needed.
- What binding leaves to the caller (P2c): that the record's `bounty` is the bounty being pulled and that its targets are that bounty's, and, optionally, that the manifest's `targetShas` are the revisions the bounty pins, which needs the `Bounty` record. A known limit, not a format change: 01's manifest has no sweep id, so a package uploaded again under another of the same sweeper's sweep records, of the same bounty and targets, binds there too. Only that sweeper can write under their path, so a replay can repeat a sweeper's own package but never claim another sweeper's.
- `seal_package(&SweepPackage, &[AgeRecipient])` and `open_package(ciphertext, &DeviceIdentity, &SweepRef, &Sweep)` do each direction in one call, and P2b and P2c use them rather than the steps, which stay public. Sealing first checks the half of the binding that needs no record, the manifest's own targets (`SealError::TargetsMismatch`, P1b's choice where the task says only "pad and encrypt": such a package would fail every binding, so it is never uploaded), then pads (`SealError::Package`) and encrypts (`SealError::Encrypt`). Opening decrypts (`OpenError::Decrypt`), parses with `SweepPackage::from_json` (`OpenError::Record`), drops the wiped plaintext buffer, then checks the binding (`OpenError::Binding`), and returns the package only when all three pass. A refused package's strings drop unwiped, like every package's (above). The inner errors hold no data, and the outer messages leave them out, so a printed chain of sources shows each once.
- The run-directory fixtures are P1b's choice where the Build line names only their shape; `fixtures/README.md` says what each file holds. `fixtures/cloudflare/` is the Cloudflare-shaped one: P1a's `findings.json`, unchanged, plus `REPORT.md` and a `coverage-ledger.json` that Cloudflare's own ledger validator at the pinned commit accepts. `fixtures/common/` is the common-format one: `findings.json`, `REPORT.md`, `notes/triage.md`, and `capture.bin`, 16 bytes that are not UTF-8. Its `session-expiry-off-by-one` has the sink of Cloudflare's `auth-expiry-inclusive` (`src/auth/session.rs` line 88, `fn is_expired`), and its `auth-token-compare-timing` shares that Cloudflare record's id at an unrelated sink (`src/http.rs` line 12, `fn header`, where Cloudflare's is `src/auth/session.rs` line 120, `fn validate`). Each common finding has its sink as its only location. Both lines exist at every commit of `target-repo.git`; `make-target-repo.sh` does not check them, and the repository was not regenerated, which would change its pack bytes. The sweepers are B (`btyoe954`) for the Cloudflare directory and C, the stranger S3 (`qwujy4ep`), for the common one, under a bounty of A's, as in P2c's end-to-end test.
- `tests/run_dir_round_trip.rs` is the Done-when round trip, through the public API alone, which shows it is enough for P2b and P2c. For each directory: `SweepPackage::build` (the common directory's `skipped` is exactly `capture.bin` as `NotText`, the Cloudflare one's is empty); `seal_package` to an owner identity and the sweeper's, both generated at run time; `open_package` with each of the two against the matching `SweepRef` and `Sweep`; then `into_files`. Every text attachment comes back byte for byte and `capture.bin` never does. The common `findings.json` comes back equal to the fixture as JSON; the Cloudflare one equals `parse_audit_findings` of the fixture, and `to_cloudflare` of it equals the fixture value for value. The test reads the fixtures with `include_bytes!`, at compile time, so unlike `tests/cctv_age.rs` it does no I/O when it runs.
