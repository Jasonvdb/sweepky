# P2b — `sweepky-cli`: post, run and submit

## Goal

`post` for closed bounties, `run` and `submit`, so a circle member can sweep a closed bounty end to end on the testnet. It builds on [P2a](P2a-cli-identity.md) for the network config, the `--identity` login, the circle, the writers' lock, the config directories, the minimal `init` with its marker, and the testnet test; on [P1a](P1a-core-records.md) for targets, the Cloudflare converter and the bare fixture repo; and on [P1b](P1b-core-crypto.md) for the package envelope, padding and encryption. `post --open`, `pull` and `done` follow in [P2c](P2c-cli-pull-done.md).

## Build

- **`post <draft.json>` (without `--open`):** reads the bounty draft the owner or their agent writes (title, focus, brief, suggested playbook and unpinned targets; see the draft's note below) and checks every field; pins SHAs through a `TargetResolver` trait: the real one runs `git -c credential.helper= -c core.askPass= ls-remote` with `GIT_TERMINAL_PROMPT=0` (peeling annotated tags, storing full SHAs) and GitHub's unauthenticated REST API for PR head, base and merge base; the fixture one serves a bare repo under `fixtures/`. Refuses repos that are not anonymously readable. `title` and `brief` are shown for confirmation.
- **`run [<bounty-url>] [--target <tid>] [--circle <admin>]`:** must be run inside an `init` project; picks or checks the bounty (circle or `open`; `--circle` names the circle checked, see the notes on the checking half and on picking); writes `running`; fetches each target into `./sweeps/<id>/target/<tid>/` by exact SHA (https only, depth 2, no submodules, no LFS, credential helpers disabled; PR heads from the base repo's `refs/pull/<n>/head`); removes `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.claude/` and `.mcp.json` from the copy and lists them in `scope.json`; writes `scope.json`, the brief and `.sweepky/sweep.json` (sweep URL, bounty URL, target ids, playbook id from `init`); aborts if the SHA is not served.
- **`submit [--run-dir] [--playbook]`:** canonicalise; require a direct child of `<init dir>/sweeps/` with the marker; walk with `symlink_metadata`, accept regular files with one link only, skip `agents/*/scratch/` and `target/`, cap per-file and total size, print the list; detect Cloudflare output in `audit/` and convert; read the bounty, list the owner's unrevoked `keys/`, compare with the pinned set and warn on new keys (ask, or fail with `--no-input`); refuse an owner with no keys; pad, encrypt to those plus this install's key, upload `.age`, flip to `done` (or `aborted` on failure), handling 413, 429 and 507 with clear messages.

## Done when

- The testnet test from [P2a](P2a-cli-identity.md) continues, with targets from the fixture repo: A, the owner, creates a circle with B in it and posts a closed bounty; B, a circle member, runs it inside a minimal `init` project and submits a Cloudflare-format sweep.
- `submit` refuses a run directory holding a planted symlink and a hard link to `~/.config/sweepky/*`, as in [06](../06-verification-and-limits.md#verification).
- B's first `submit` pins A's key set, and a key the test then adds under A's `keys/` makes B's next `submit` warn.
- Two `submit`s by B, of two separate runs, run concurrently and both succeed, each taking the writers' lock in turn.
- `cargo clippy -- -D warnings`, `cargo deny check` and `cargo nextest run` clean.

## Notes

- The per-sweep marker `sweeps/<id>/.sweepky/sweep.json` that `run` writes is separate from the project's `.sweepky` marker that the minimal `init` writes.
- Until [P3](P3-skill-and-sandbox.md)'s `init` records a playbook, the playbook comes from `submit --playbook`. Meanwhile `run` writes the placeholder `unspecified` in the sweep record: core's `Sweep` needs a playbook when `run` publishes it, P2a's `init` records none, and `unspecified` passes 01's pattern, so no record format changes; `submit` replaces it from `--playbook`.
- `RepoName` ([P1a](P1a-core-records.md)) now refuses a host whose last label starts with a digit, not only one that is all digits: a URL parser or the system resolver reads the hex and mixed IPv4 forms (`127.0x1`, `0x7f.0x0.0x0.0x1`, `10.0.0.0xa`) as an address, every such form ends in a label that starts with a digit, and no top-level domain does. It is still a check of form: a DNS name that resolves to a private address passes it.
- The question plumbing, P2b's record (`prompt.rs`, `clock.rs`). `Context` gains `cwd`, the working directory, which `main.rs` reads with `std::env::current_dir()` so that only `main.rs` reads the environment, the working directory included (a working directory that has gone fails every command but `init` before anything is done); and `stdin`, a `StdinReader` around a `Mutex<Box<dyn BufRead + Send>>`, which `main.rs` builds around `BufReader::new(std::io::stdin())`, because `Stdin` is not `BufRead` and `StdinLock` is not `Send`, and the tests around a `Cursor`. The global `--no-input` stays on `Cli` and is not in the context: `run` hands it, as a `prompt::Prompting` (`Allowed` or `Forbidden`), to each command that asks, so a test gives it on the command line like any other flag. `prompt::confirm(ctx, prompting, question)` writes `<question> [y/N] ` to `ctx.stderr` with no newline and reads one line from `ctx.stdin` with `take(1025).read_until(b'\n', …)`, never an unbounded `read_line`: a line of more than `MAX_ANSWER_BYTES` (1 KiB, its ending included) is an error that quotes none of it, and nothing past its 1025th byte is read. `y` or `yes` in any ASCII case, once one `\n` or `\r\n` is taken off, is yes; anything else, an empty line and the end of the input included, is no. Under `Forbidden` it fails at once, with an error that names `--no-input` and the question, and writes and reads nothing. The caller sanitises any stranger's text it puts in a question. `clock::new_record_id()` is the id of a new bounty, sweep or device key: it asks `clock::now()` first, which refuses a clock before 1970 that `Timestamp::now()` would panic on, then returns `RecordId::from_timestamp(Timestamp::now())`; `device::new_device_id` is that id parsed as a `DeviceId`. Until `post` and `submit` call `confirm`, `prompt.rs` carries `#![cfg_attr(not(test), expect(dead_code, …))]`; the first caller removes it, because an unmet `expect` is a warning of its own.
- The git runner, P2b's record (`git.rs`). `post` and `run` run git only through `GitRunner`, behind a small `RunGit` trait of one `async fn run(&GitCommand) -> stdout`, used generically like `device::PublicKeys` so a test can record or fake invocations. Arguments go as an argv vector, never through a shell: options are `&'static str`s the code writes, and `git_argv` refuses an operand (URL, SHA, ref or pattern) that is empty or starts with `-`. Every run gets, before its subcommand, `-c credential.helper=` (an empty value resets the helper list, Apple git's bundled `osxkeychain` included), `core.askPass=`, `protocol.allow=never`, `protocol.https.allow=always`, `http.followRedirects=false`, `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `core.symlinks=false`, `submodule.recurse=false`, `fetch.recurseSubmodules=false`, `transfer.fsckObjects=true` and `advice.detachedHead=false`; `protocol.file.allow=always` is added only for the fixture source (`AllowedProtocols::HttpsAndFile`). The child's environment is cleared, then given exactly `PATH`, whichever of `HTTPS_PROXY`, `https_proxy`, `ALL_PROXY`, `all_proxy`, `NO_PROXY`, `no_proxy`, `SSL_CERT_FILE` and `SSL_CERT_DIR` were set (`main.rs` captures them into `Context::git_env`, a `GitEnv`, and does not read `TMPDIR`), `HOME`, `GIT_CEILING_DIRECTORIES`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GIT_LFS_SKIP_SMUDGE=1` and `LC_ALL=C`; standard input is `/dev/null`. `HOME` is `<data dir>/git-home-<new record id>/`, made 0700 through `private_fs` and refused if anything, a symlink included, is already there; a drop guard removes it with `remove_dir_all` (best effort; a process killed outright leaves it behind). `GIT_CEILING_DIRECTORIES` is the data directory: git runs in that private `HOME` by default, and without it git's search for a repository walks up from there, so a home directory kept in git (`~/.git`) would lend its `.git/config` (an `http.extraHeader`, a `url.<base>.insteadOf`) to every `ls-remote`; a data directory whose path holds a `:` is refused, because that list is `:`-separated. That variable is the one addition to the allowlist the task named; a command run in another directory (`GitCommand::in_dir`) must run in a repository it made, so the search stops there, or, for the fixture source's `merge-base`, in the fixture's bare repository, which git finds at that directory itself and so searches nothing above. Each run is bounded: standard output and standard error are read at the same time, each up to its own cap, under a timeout, and a child past any of them is killed and waited for (`kill_on_drop` as well). `ls-remote` gets 60 s, 1024 lines of at most 1024 bytes (so 1,049,600 bytes of standard output) and 64 KiB of standard error; `run`'s fetch gets 10 minutes. Killing git does not kill a helper it started (`git-remote-https`), which dies when its pipes close. A failed run is a `GitFailed` error: `git <subcommand> failed with exit status <n>`, fixed text, never git's standard error, which carries `remote:` text a server wrote; the error keeps that text only for `stderr_mentions`, a match against a fixed phrase, and its `Debug` prints its length. The `ls-remote` parser takes `<40 lower-hex>\t<ref>` lines (`HEAD` or under `refs/`, no control character, `^{}` lines included): SHA-1 only, so a SHA-256 repository is refused although core's `GitSha` also takes 64 hex characters. Minimum git: 2.32, for `GIT_CONFIG_GLOBAL` (an older git still finds no `~/.gitconfig` in the empty `HOME`). tokio's `process` and `io-util` features are named in the CLI's `Cargo.toml`; pubky already turns them on (it asks for tokio's `full` on every target but wasm), so they add no code.
- The host policy, P2b's record (`targets/host.rs`, a P1a carry-forward). v1 sweeps public repositories only, so a target's host is resolved and checked before any git contact, for every bounty, open or closed, and on both the `post` and the `run` path. `HttpsRemote::for_repo(repo, resolver)` is the only way to make the `https://<repo>` remote of a real target: through `host::check_host`, which GitHub's API host goes through too, it looks up the `RepoName`'s host and refuses, in fixed text that names neither the host nor an address, a failed lookup, an answer with no address, and an answer with any address that is not public, whatever the others are, since git connects to whichever it likes. git's network commands take only a `git::Remote`, which is an `HttpsRemote` or the fixture source's `LocalRemote` (its constructor is private to `targets/fixture.rs`; the tests of other modules have a `cfg(test)` one); every other command is built from a `LocalSubcommand` (`init`, `config`, `rev-parse`, `merge-base`, `checkout` and `rev-list` so far, a variant added as a command needs one; only the tests run `rev-parse`, so it alone carries a dead-code expectation), which never contacts a repository, so no URL a record or a server wrote reaches git unchecked. The lookup goes through `ResolveHost`, a trait of one async fn used generically like `RunGit`: `SystemResolver` calls `tokio::net::lookup_host((host, 443))`, the system resolver git's own lookup asks too, with no timeout of its own because the system resolver gives up by itself (tokio's `net` feature is already on through pubky, `cargo tree -e features -i tokio`, and is named in the CLI's `Cargo.toml`); the tests use `test_support::FakeResolver`. Public means: IPv4 outside 0/8 (0.0.0.0 included), 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, multicast 224/4 and 240/4 (255.255.255.255 included); IPv6 inside global unicast 2000::/3, which leaves out `::`, `::1`, the deprecated IPv4-compatible `::a.b.c.d`, `100::/64`, `fc00::/7`, `fe80::/10`, `fec0::/10`, `ff00::/8` and unassigned space, but outside 2001::/23 (IETF protocol assignments, Teredo 2001::/32 and benchmarking 2001:2::/48 among them; its few reachable anycast services serve no repository), 2001:db8::/32 and 3fff::/20 (documentation); and an IPv4-mapped (`::ffff:0:0/96`), NAT64 (`64:ff9b::/96`, what DNS64 answers for an IPv4-only host such as github.com) or 6to4 (`2002::/16`) address is exactly as public as the IPv4 address it carries. Limits: git resolves the name again when it connects, so DNS rebinding between the check and git's own lookup is not closed; `http.followRedirects=false` in the git runner stops a redirect to an internal host; and with `HTTPS_PROXY` set git asks the proxy to connect, so the check is of this machine's resolver, not the proxy's.
- The target sources, P2b's record (`targets/mod.rs`, `rev.rs`, `real.rs`, `fixture.rs`). `post` and `run` reach a repository only through `TargetResolver`, a trait of async fns used generically like `RunGit`: `resolve_rev` pins a revision to a full SHA, `pull_request` gives a pull request's base, head and merge base, `fetch_remote` names the remote `run` fetches from (a `TargetRemote`, an owned `HttpsRemote` or `LocalRemote`), `check_policy` applies the target policy with no network, and `protocols` and `git_runner` give the one `GitRunner` per command, allowed that source's transports and no others, which the git-running methods take back as `&impl RunGit`. A trait with async fns cannot be `dyn`, so `Context::targets` is a `TargetSource` enum (`Real`, `Fixture(FixtureTargets)`) that passes each call on with a `match`; `main.rs` only ever builds `TargetSource::Real`. `FixtureTargets` is public so that `tests/end_to_end.rs` can build it, and `#[doc(hidden)]`, with a doc comment saying it enables git's `file` transport; it maps a `RepoName` to a plain absolute path, so no URL encoding is needed, serves only the names it maps, and allows a pull request on any of them, so the fixture's `example.invalid` pull request works. `test_support::test_context` gives a fixture source that maps nothing. The policy that a `pr` target is `github.com/<owner>/<name>` lives in the source: the real source enforces it in `check_policy`, `pull_request` and `fetch_remote`. A revision is a `RevSpec`: git's `check-ref-format` rules with one level allowed (no `..`, `@{`, lone `@`, `~ ^ : ? * [ \`, empty part, leading or trailing `/`, part that starts with `.` or ends with `.lock`, or trailing `.`), plus at most 255 bytes, printable ASCII only (so no space and no control character; a branch with a non-ASCII name is given by its SHA), no leading `-`, and no abbreviated or upper-case SHA (four or more hex digits that are not a full lower-case 40-character SHA-1; a branch with such a name is given as `refs/heads/<name>`). Its errors name the rule, never the value. Pinning is one anonymous `ls-remote`: for a short name N the patterns `refs/heads/N refs/tags/N refs/tags/N^{}` (git 2.50.1 prints the peeled line only when `^{}` is a pattern), for `HEAD` `HEAD`, for a full ref name that name and its `^{}`. The pure `match_rev` compares whole names in Rust, since git matches a pattern against a ref's tail; it resolves a tag to its `^{}` line or, for a lightweight tag, to its own SHA, refuses a name that is both a branch and a tag with a message that asks for `refs/heads/…` or `refs/tags/…`, and refuses a listing that names one ref twice. A full SHA is accepted as given once `ls-remote <url> HEAD` succeeds, which proves the repository is readable. Any `ls-remote` that exits with a failure status is the one fixed refusal "the repository is not anonymously readable (Sweepky sweeps public repositories only)": git's `GitFailed`, and the standard error it keeps, is dropped, not wrapped. A timeout, a cap or a malformed listing keeps its own fixed text. The real source checks the host (`HttpsRemote::for_repo`) before any git run, on the pin path and on the fetch path alike, and asks for `AllowedProtocols::Https` alone; its pull request half reads GitHub's unauthenticated API (next note). The fixture source asks for `HttpsAndFile`; its pull request `<n>` is `refs/pull/<n>/head`, its base the commit `HEAD` names, and its merge base `git merge-base <base> <head>`, run read-only through the runner in the bare repository (`LocalSubcommand::MergeBase`). `test_support::RecordingGit` is a `RunGit` fake that records each run's argv (`git_argv`, with the protocols it was made with) and answers with a scripted exit status and output. Limits: `ls-remote` cannot show that a commit deep in history is served, so a full SHA the repository does not have passes `post`, and `run` aborts when its fetch by SHA fails; `ls-remote` does not say what a tag points at, so a tag of a tree or a blob pins that object, and `run` fails on it; and a network failure inside `ls-remote` (git's own lookup or connection) also reads as not anonymously readable, since every failure exit does.
- GitHub's API, P2b's record (`targets/github.rs`, `real.rs`). A `pr` target must be exactly `github.com/<owner>/<name>`: another host, a third path segment or a name ending in `.git` in any case (GitHub serves `r.git` as `r`, but `run` would fetch another URL) is refused in fixed text that quotes nothing, with no network, in `check_policy`, `pull_request` and `fetch_remote`. `RepoName` already holds each segment to `A-Z a-z 0-9 . _ -`, so the two go into the API's URL path as they are. `TargetResolver::pull_request` takes a `github: &impl GitHubApi`, a trait of one async fn, `get(url, cap)`, which gives a 2xx answer's body or `None` for a 404; the caller passes the SDK's HTTP client, `ctx.network.pubky().client()` (`impl GitHubApi for PubkyHttpClient`, a plain reqwest client with the user agent `pubky.org@0.16.2` for an ICANN host), the tests `test_support::FakeGitHub`, and the fixture source never asks it anything. The real source's `pull_request` runs: the policy; `api.github.com` through the host policy (`check_host`) before the first request; `GET https://api.github.com/repos/<owner>/<name>/pulls/<n>` for `base.sha` and `head.sha`; the repository's host check and one anonymous ls-remote of the base repository's own `refs/pull/<n>/head`, which must list exactly that head, or the pull request is refused with "the pull request moved while it was being pinned; try again" (and with its own fixed text when the ref is not listed); then `GET …/compare/<base>...<head>?per_page=1&page=2` for `merge_base_commit.sha`. The head is the base repository's pull request's `head.sha`, and nothing is read from the fork. Each request is anonymous, carries `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28`, goes through the redirect guard (next note) and is read under a 1 MiB cap. Page 2 at 1 commit a page leaves out the up to 300 changed files and their patches that page 1 carries and still carries `merge_base_commit`, checked against the live read-only API on 2026-10-19 (a one-commit pull request's page 2 has no commits and the same merge base), so the 16 MiB cap page 1 would need is not used. A status is mapped from the status alone, so an error answer's body is never read: 404 is "not found, or not public" (GitHub answers a private repository as a missing one), 403 and 429 say that for an anonymous request this almost always means the rate limit (60 requests an hour from one address) is used up, and to try again later, and any other non-2xx is "GitHub's API answered <status>". The parsers read only the fields they need into `#[derive(Deserialize)]` structs and skip the rest (an answer is read, never rewritten, so nothing is kept with `#[serde(flatten)]`), refuse a body over 1 MiB before parsing it, drop serde's error, whose text can quote the body, and hold every SHA to a full lower-case SHA-1 (`rev::is_full_sha1`). Limit: like every request through the SDK's client, whose builder sets no timeout, a GitHub request has none, so an answer that stalls waits until the command is interrupted.
- Redirects, P2b's record (`remote.rs`), the decision P2a left open: a request Sweepky sends itself refuses an answer that came through a redirect, and uses nothing of it. Those requests are each listing page (`fetch_page`), each public record read (`get_public`, moved from `public_storage().get` onto `request_async` of the resource's transport URL, the request the SDK's public storage sends, as `list_dir`'s already was) and GitHub's two reads, and all go through `get_unredirected`: `request_async`, the request's headers, `build_split` to keep the URL of the request the SDK built (it may have put an ICANN domain in place of a key, or rewritten a legacy homeserver's path), `execute`, and then the pure `check_not_redirected`, which compares the answer's URL with that one by scheme, host, port (`port_or_known_default`), path and query and refuses any difference in fixed text that names neither URL. Only then is the status looked at, by a callback given the status alone (so a redirected 404 is not an empty directory), and the body read under its cap. `BodyTooLarge` now says "the server's answer", since a body can be GitHub's. Limits, both out of scope here: pubky 0.16.2's client sets no `redirect::Policy`, so reqwest still follows up to 10 redirects and sends each redirected request, possibly to a host on the sweeper's network, and the guard refuses only the answer; and the requests the SDK sends on its own (sign-up, sign-in, sign-out and a session's reads and writes, `get_own` among them) still follow redirects. reqwest reports only the last URL, so a chain of redirects that comes back to the URL sent is not seen either.
- The bounty draft, P2b's record (`post/draft.rs`, `post/mod.rs`, `display.rs`). A deviation: the docs never said how a bounty's title, brief and targets reach `post`, so P2b gives it a draft file, `post <draft.json>` ([03](../03-cli-and-skill.md#the-sweepky-cli-v1)'s `post` row records it). A file suits a multi-line markdown brief and several targets, and keeps that text off argv, where clap would echo it in a usage error. Its shape is `{title, focus?, brief, playbook?, targets: [{id?, kind: repo|commit|pr, repo, ref?, paths?, number?}]}`, read with `deny_unknown_fields` at both levels, so a misspelt `paths` is an error instead of a sweep of the whole repository: a repo target takes `ref` and an optional `paths`, a commit target `ref`, a pr target `number`, and a field of another kind is refused; `ref` is required where it applies (no default to `HEAD`) and is a `RevSpec`. `playbook` becomes `BountyPlaybook {suggested, required: false}`. The draft is agent-written, so it is treated as a stranger's record. `read_draft` opens the path as given (a symlink or a pipe from process substitution works) and reads at most `MAX_RECORD_BYTES + 1` with `private_fs::read_up_to_cap`; `BountyDraft::parse` refuses more than `MAX_RECORD_BYTES` before parsing. serde's messages, which quote values, go through core's `RecordError`, so a fault of shape (an unknown, repeated or mistyped field, or bytes that are not JSON) is reported by kind, line and column alone; every other refusal names the field by its place, `targets[1].ref`, never by its content or the target's id, and gives a fixed reason (core's and `RevSpec`'s reasons never quote either). A missing field is named (`the draft has no title`, `targets[0] has no ref`), because the required fields are read as `Option`s too. Limits: the title 1 to 200 characters; the brief 1 character to 256 KiB (`MAX_BRIEF_BYTES`); the focus 1 to 64 characters, `security` when left out, an open label; the suggested playbook 1 to 512 characters (room for a URL); each refused when blank (only whitespace), P2b's addition. Every one of the four becomes public and core checks none of them, so each must be text the terminal sanitiser leaves unchanged: `display::sanitize` for the one-line fields and the new `display::sanitize_multiline` for the brief, which keeps `\n` and `\t` and escapes every other control (`\r` among them), bidi and invisible character, doubles a backslash and cuts by characters, as `sanitize` does. So a backslash is refused in all four, a markdown brief included (a regex or a Windows path has to be written another way), as `circle`'s names already refuse one. The refusal gives the line and column of the first such character and never the character: `display::first_changed_char` finds it with the same per-character rule the sanitisers use (`Layout::OneLine` or `MultiLine`), so the check and the sanitiser cannot disagree. `paths` entries are core's `RepoPath`s only, a lexical check (zero-width characters pass, as P1a's carry-forward notes), not held to the sanitiser rule. Targets: 1 to `MAX_TARGETS` (32, P2b's choice: each target costs a git run and a pull request two of the 60 requests an hour GitHub gives an anonymous address, so a draft cannot ask for unbounded work); ids default to `t<n>` by position, and two ids that are equal when ASCII case is ignored are refused, the carry-forward for one directory per target on a case-insensitive filesystem; an empty `paths` is refused, leaving it out means the whole repository. `post::prepare_bounty(draft, source, git, github, created_at)` then runs `check_policy` on every target before any network, pins each in turn through the `TargetResolver` (`resolve_rev` for repo and commit targets, `pull_request` for pr targets), names a failing target `targets[<n>]`, and builds the bounty with `Bounty::new`: status `open`, `open` false, `credits` empty, `reward` and `doneAt` null. Any failure, `NOT_ANONYMOUSLY_READABLE` among them, fails the whole draft and builds no bounty. A repo target with no paths gives the warning that a whole-repository sweep can outlast a 5-hour plan window, in `PreparedBounty::warnings`, for the publishing half to show before it asks. That half, the next note, shows the bounty through `sanitize` and `sanitize_multiline` and checks that the serialised bounty is within `MAX_RECORD_BYTES` before it asks, since a draft near every cap can build a longer one.
- `post`, P2b's record (`post/mod.rs`). `post <draft.json>` runs in this order: `read_draft`; `createdAt` (`clock::now`); one git runner from the context's target source for `prepare_bounty`, dropped, with its private `HOME`, before the question; the bounty written as compact JSON (`serde_json::to_vec`) and refused over `MAX_RECORD_BYTES` before anything is shown, because a draft within its own caps can still build a longer bounty (the pinned SHAs, the target ids and the fields `post` adds); the warnings and the preview on standard error; then `prompt::confirm` with "Publish this bounty, where anyone can read it?". The preview says the bounty is closed (sweeps from outside the circle are not read) and shows the title, the focus, the suggested playbook or "none suggested", every target as `Target::known` reads it back (its id, kind and repository, and its pinned SHA, or a pull request's number and its base, head and merge base, one a line; a repo target's paths one a line, or "the whole repository"), and the brief, each line of it behind a `  | ` gutter so that none can pass for a line of Sweepky's own. Every string a draft wrote, target ids, repositories and paths included, goes through `display::sanitize` (`sanitize_multiline` for the brief) with room for the longest the draft allows, although the draft's checks already hold the four text fields to what the sanitiser leaves unchanged: a `RepoPath` is a lexical check that lets zero-width characters through, and the preview takes a `Bounty`, which nothing makes a draft check first. Anything but `y` or `yes` (`n`, an empty line, the end of the input) is a report, "Not confirmed, so nothing was posted"; under `--no-input` the question fails after the preview, "nothing was posted: --no-input was given, …", so an agent can see what a draft pins without posting it. Neither takes the writers' lock or signs in. Only a yes makes the bounty's id (`clock::new_record_id`) and runs `session::with_writer_session`, so the lock covers the sign-in, the PUT and the sign-out and never waits on a person; the PUT is `publish`'s, to `/pub/sweepky/bounties/<id>.json`, a refusal mapped by `remote::write_error` (403 and 507 to `login`'s fixed messages, anything else to fixed text and the status, never the server's words), and the report ends with the bounty's `pubky://` URL (core's `BountyRef`) on a line of its own.
- `OwnStorage`, P2b's record (`own_storage.rs`), the write seam `post`, `run` and `submit` share: a crate-private trait of two `async fn`s, used generically like `device::KeyStore`: `put(path, bytes) -> pubky::Result<()>`, which hands the SDK's error back for the caller to map, and `get_own(path)`, the user's own file read as a record through `remote::get_own` with `MAX_RECORD_BYTES`, a 404 being `None`. Paths come from `sweepky_core::paths`. `SessionStorage`, the real one, borrows the `WriterSession` a `with_writer_session` body is lent, so it can neither keep the session nor sign it out. `test_support::FakeOwnStorage` keeps files by path, logs every path it is asked to write, and fails the writes of chosen paths, each with a given status and server text (`pubky::Error::from(RequestError::Server {..})`, as `FakeKeyStore` does), which the tests check no message repeats, or with a transport error, which it gets from a real request to port 1 of the loopback address, since reqwest's error type has no public constructor; `stop_failing` lifts them, so a test can run a command again, and `insert` puts a file in place unlogged. `submit`, which reads its sweep record back under the lock, is `get_own`'s first caller, so the dead-code expectation it carried is gone. With `post` the first caller of `prompt::confirm`, `display::sanitize_multiline` and the target sources, their dead-code expectations are gone; with `run`'s fetch the first caller of the git fetch and of `TargetResolver::fetch_remote`, so are `git.rs`'s module-wide one and the `allow` `fetch_remote` carried (an `expect` there would never have been met, because marking the method used made `TargetSource`'s own `fetch_remote`, which calls the two sources', a real use of it).

- The checking half of `run`, P2b's record (`run/mod.rs`, `run/select.rs`, `records.rs`, `init.rs`). A decision, because no doc said which circle a sweeper belongs to: `run` takes an optional `--circle <admin>` ([03](../03-cli-and-skill.md#the-sweepky-cli-v1)'s `run` row records it). **The project.** `run` must be run inside an `init` project: its working directory itself must hold the `.sweepky` marker, read through `init`'s own reader, `init::read_project_marker` (`lstat`, a regular file only, never a link followed, the inode checked on open, at most 64 KiB, `schemaVersion` at most 1), and no marker, a link, anything but a regular file, or a file that is not a marker is refused by its path, quoting none of the file. Only the working directory is looked at, never its parents as git does: a sweep's files go under `./sweeps/` of the project, so the command must run where they go. The marker gains an optional `playbook`, read from the space its unknown fields already took, as core's `Playbook` (01's pattern), so a bad one makes the file no marker this build reads, for `init`'s second run too; what P2a's `init` writes is unchanged, `{"schemaVersion":1}`, and P3's `init` writes the field. **The bounty URL.** The argument must be a bounty record's `pubky://` URL, the owner in either spelling, as `post` prints it, and the owner an Ed25519 point. Anything else is refused in fixed text that never quotes it: a sweep record's URL, another `pubky://` file, a malformed `pubky://` URL (core's reason), an `http(s)://` address, and, through `login`'s classifier (`identity::refuse_secret_material`), a pasted key, phrase or recovery file. The `pubky://` check comes before the classifier, which would take the URL's 52-character key for a raw secret. **Reading.** The bounty and its circle are read with no session through `PublicRecords` (`records.rs`), a crate-private trait used generically like `device::PublicKeys`: one required method, `get_record(owner, path)`, which `PublicRecordReader` sends through `remote::get_public` (pkarr, anonymous, a redirected answer refused, the body capped at `MAX_RECORD_BYTES`), and provided `get_bounty`, `get_circle` and `get_sweep` (and the listings, in the note on picking), written once so that the real reader and `test_support::FakePublicRecords` parse alike: the path from `sweepky_core::paths`, core's `from_json` (which refuses more than `MAX_RECORD_BYTES` again before parsing), a 404 as `None`, and bytes that do not parse as an error that names the path and the owner and quotes none of them. **Acceptance** (`select::accept`, pure): the status must be `open`; a `done` or unknown status is refused, the status unprinted. Without `--circle`, an `open: true` bounty is accepted from anyone and no circle is read, and a closed one is checked against its owner's own `circle.json`, the roster the owner's `pull` reads closed-bounty sweeps from, which must exist, name the owner as its `admin` (anyone can put any file in their own storage, so a roster counts only in its admin's) and list the sweeper. With `--circle <admin>`, that circle is read instead, for every bounty, open or closed, and must name that admin and list both the owner and the sweeper: the stricter check. Membership is `Circle::is_in_roster`'s, the admin or a member, by key bytes. Why this matches 00's trust row (whose bounties a sweeper works on: the sweeper's own allowlist, circle by default, plus the sandbox): circle membership is unilateral, so a stranger can list B in their circle, but with a URL the human who pastes it is the consent, the owner's roster naming B is the owner's side, and the sandbox bounds what a hostile bounty's targets can do; `--circle` gives the stricter check, and picking without a URL (the note on picking) defaults to this install's own circle. No refusal names the key `--circle` was given. **Targets** (`select::choose_targets`, pure): a bounty two of whose target ids are equal when ASCII case is ignored is refused whole, with or without `--target` (one pass keyed by the lower-case id, not a comparison of every pair). Without `--target`, every target `Target::known` reads is chosen; one of an unknown kind or a malformed one is skipped with a warning that names it by its id alone (and, for a malformed one, core's fixed reason); one the target source's policy refuses, such as a `pr` target off `github.com`, fails the run with its id and the hint that `--target` can name another, since the owner asked for it and this build will not sweep it; no usable target is refused, and so are more than `MAX_TARGETS` (32, `post`'s cap; P2b's choice, since each target is a fetch, so a stranger's bounty cannot ask one run for unbounded work). `--target <tid>` must be a `TargetId` and name one of the bounty's targets, of a known kind, well formed and within the policy; no refusal quotes it. Each chosen target keeps core's checked `KnownTarget`, from which the fetch and `scope.json` are built. **What it shows.** `CheckedBounty::summary`: the warnings, the bounty's URL, its title and focus through `display::sanitize` (room for `post`'s longest), why it may be run, and each target with its repository, sanitised, and the commit it reviews; never the brief, a stranger's markdown that the agent reads from the file `run` writes. The run command (its note below) is their caller, so the dead-code expectations `run/mod.rs`, `PublicRecordReader::new` and `ProjectMarker::playbook` carried until then are gone, and picking, which reads sweeps, removed the one `PublicRecords::get_sweep` kept.
- The fetching half of `run`, P2b's record (`run/fetch.rs`, `run/strip.rs`, `run/scope_file.rs`). **Where.** `SweepPaths` builds every path from the project's own path, which must be absolute and UTF-8 because `scope.json` names the paths under it as text, the sweep's `RecordId` and each `TargetId`, each a single ASCII path segment; no `RepoPath` or other record text is ever joined onto a local path, and a repo target's `paths` go into `scope.json` as data. `check_sweep_dir(project, id)` is the check the run command makes before it publishes `running`: `sweeps/` absent or a real directory (an `lstat`, a link or anything else refused through `private_fs::refuse_unless_dir`), and `sweeps/<id>` absent; it creates nothing. `fetch_sweep` makes the same check before any git runs, makes `sweeps/` if it is missing and then `sweeps/<id>/` with a plain `mkdir`, 0700 (P2b's choice, so no other user of the machine reads the audit before `submit` encrypts it), and holds a drop guard that removes `sweeps/<id>/` and all it holds unless the sweep finished, whether a step failed, returned early or the command was cancelled. The guard is best effort (a process killed outright leaves the directory, which has no marker for `submit` to accept); nothing else under `sweeps/` is touched, and flipping the record to `aborted` is the run command's job. **The git steps**, per target in `target/<tid>/`, all through the hardened runner: `init --quiet --template=`; `config core.symlinks false`, P2b's addition, so a checkout the agent runs in the copy later writes links as plain files too (the runner passes the same `-c` on every run); `fetch <remote> --depth=2 --no-tags --no-recurse-submodules --quiet <sha>…`, the URL an operand, so no remote is configured; `checkout --quiet --detach <reviewed commit>`, every link written as a plain file holding its text; and, for a commit target, `rev-list --parents --max-count=1 <sha>`, whose one line (the commit, then each parent, full SHA-1s, under the runner's 64 KiB cap, read without indexing) gives core's `CommitShape`, a merge at two parents or more, counted from the commit as fetched. The local steps get 60 s, the checkout 10 minutes like the fetch. Depth 2 for every kind, one fetch per target: a pull request's head and merge base come in the same fetch at depth 2, since the merge base is not in the head's depth-2 history once the pull request has two commits (the planner's note also offered a separate depth-1 fetch of the merge base; one fetch is simpler and costs one more generation). Against the fixture, M's fetch leaves `.git/shallow` listing B and T1, pull request 1's (F2 and B) F1 and A, and the root R's none at all: R has no parent, so its fetch holds its whole history and git writes no such file. **Which remote**: `TargetResolver::fetch_remote(kind, repo)`, the real source's policy and host check before it names an `HttpsRemote`, a pull request's being its base repository's. P2b reads "PR heads from the base repo's `refs/pull/<n>/head`" as: the head is fetched by its pinned SHA from the base repository, where `refs/pull/<n>/head` makes it reachable (GitHub serves a reachable commit by SHA), never from the fork, and not by the ref's name, which may have moved since the bounty was pinned. **Not served**: git's standard error is matched, for each pinned SHA, against `not our ref <sha>` (upload-pack's words in every protocol version for a commit it does not have or no ref of its reaches; checked against GitHub over https and the `file` transport on 2026-10-19), and that failure becomes the fixed "the pinned commit <sha> is no longer served by its repository …, so run stops rather than sweep another one", which drops git's error; any other failure, a server that takes no request by SHA at all among them (its commit may still be there), keeps the runner's fixed exit-status text under a general context. **Stripping** (`strip.rs`): 02's five names at every depth (Claude Code loads a subdirectory's `CLAUDE.md` on first read, and the fixture plants `src/auth/CLAUDE.md`) with case ignored, ASCII case plus the long s, U+017F, which APFS folds to `s` (`AGENTſ.md` opens as `AGENTS.md` there, checked on APFS); a real directory goes with `remove_dir_all`, anything else, a link included, with `remove_file`, and neither follows a link; entry types come from `DirEntry::file_type`, which describes a link itself, and only real directories are walked into, `.git` included, which holds no such name. The list is relative, `/`-separated, a directory with a trailing `/`, sorted, a part that is not UTF-8 written lossily; the names are the repository's, so they are only written into JSON, and sanitised if a later step prints them. A `git diff` the agent runs still shows a changed `CLAUDE.md`'s text: that is content to review, not instructions Claude Code loads. **`scope.json`**: `{schemaVersion, sweep, bounty, focus, suggestedPlaybook, profile, output, targets: [{id, kind, path, scope, stripped}]}`, P2b's shape for what 01 and 03 ask of it; every path absolute with a trailing `/`; `scope` core's `TargetScope`, built from the bounty's checked `KnownTarget`; `suggestedPlaybook` the bounty's suggestion or `null`; `profile` `standard`, P2b's default until a flag picks `quick`; `output` the absolute `sweeps/<id>/audit/`, which the `/sweepky` skill hands the playbook as its new output directory (01, 03), and which `run` does not create because the playbook wants a directory that is new; `schemaVersion` 1, P2b's addition, so the skill can tell a later shape. Its types are `Serialize` only, which a compile-time check holds, and nothing reads the file back. `brief.md` is the bounty's brief byte for byte. Both are written with `create_new` (`O_EXCL`, which no link passes) and synced (`private_fs::write_synced`). Limit: nothing bounds a target's size but the fetch's and the checkout's timeouts, so a huge repository can fill the disk.
- The run command, P2b's record (`run/mod.rs`, `run/marker.rs`). `run [<bounty-url>] [--target <tid>] [--circle <admin>]` runs in the order 00's loop (step 2) and 03's `run` row give, running then fetch, so neither doc changes. **Checks, writing nothing**: the `init` project (`require_project`, whose marker may name a playbook); the URL (`parse_bounty_url`), and without one a `--target` refused (the note on picking); `--circle` through `circle`'s own `parse_pubky` (core's parse, then the SDK's Ed25519 check, fixed text that quotes nothing); the sweeper, the pubky `login.json` names (`NOT_LOGGED_IN` without one); without a URL, the pick (the note on picking), whose bounty and target are then checked as a URL and a `--target`; `check_bounty` through `PublicRecordReader`, with no session; the summary on standard error; the git runner, made before anything is published, so a machine where git cannot run stops with nothing to undo; the sweep's id (`clock::new_record_id`); and `check_sweep_dir`. **Running**: `sweeps/<id>.json` as compact JSON, `{schemaVersion: 1, bounty, targets, playbook, status: "running", startedAt}`, the targets the chosen ids in the bounty's order, `startedAt` from `clock::now`, no `finishedAt`, which `Sweep::from_json` reads back equal; the playbook is the project marker's when it names one, else the placeholder (note above). It goes through `PublishRecord`, a crate-private trait of one `async fn publish(path, record)`, used generically like `RunGit`: the real `LockedSessionPublisher` runs each write in its own `session::with_writer_session` (the lock, a fresh sign-in, one PUT through `SessionStorage`, a sign-out), and the tests implement it for `test_support::FakeOwnStorage`, so the order is tested without a homeserver. A refusal is mapped by `remote::write_error`, never the server's words. Under the lock `login.json` is read again, and a session for another pubky than the one the bounty was checked for publishes nothing ("this install was logged in as another identity while run checked the bounty"). A refused running write ends the run: no git has run, no directory was made, and there is nothing to flip. **Fetch, outside the lock**: `fetch_sweep`, then the per-sweep marker, last. **Abort**: if the fetch or the marker fails, an unserved SHA among them, the sweep directory is gone (`fetch_sweep`'s guard; a failed marker write removes the directory itself, best effort, so no sweep is left without one) and the same record is published again with status `aborted` and `finishedAt`, under the lock once more. So the lock is held twice at most, each time around a sign-in, one PUT and a sign-out, and never while git runs. "Aborts if the SHA is not served" means that flip, and `aborted` is final: 01 re-fetches only `running` sweeps and 04 shows an aborted one struck; a new `run` makes a new sweep. The error is the failure behind "run stopped, and the sweep's public record now says aborted", or, when the flip fails too, behind "… could not be changed to aborted and still says running" and the flip's own error, which is `write_error`'s fixed text. **The marker** (`run/marker.rs`), separate from the project's `.sweepky` that `init` writes: `sweeps/<id>/.sweepky/sweep.json`, compact JSON and a newline, `{schemaVersion: 1, sweep, bounty, targets, playbook?}`, the sweep record's URL, the record's own bounty and targets, and the playbook the project's `init` recorded, left out when it recorded none; `schemaVersion` is P2b's addition, as in `scope.json`. `.sweepky/` is a plain `mkdir`, 0700, which fails if anything is at that name, a link included, and `private_fs::write_private_file` writes the file: a `create_new` temp file beside it, synced, renamed into place, the directory synced. Its type is `Serialize` only: `submit` reads the marker and must check it, since the agent can change any file under `sweeps/<id>/`. **Report**: the sweep's URL, for each target how many agent-instruction files were stripped (the names stay in `scope.json`, being the repository's), and what to run next in the project: `claude --setting-sources project,local`, `/sweepky`, then `sweepky submit --run-dir sweeps/<id>`. Limit: a command killed outright (`kill -9`, or Ctrl-C, which nothing here catches) during the fetch leaves the record `running` and the half-made directory, which has no marker.
- Picking a target, P2b's record (`run/pick.rs`, `records.rs`, `run/mod.rs`). `run` without a bounty URL (03's `run` row: "picks a target from the circle's open bounties with the fewest sweeps") reads public records alone, with no session, through `PublicRecords`, which gains a second required method, `list(owner, dir)` (the real one is `remote::list_dir` within `ListLimits::DEFAULT`: at most 1000 entries in 11 pages, the listing refused whole past them or when a page breaks the protocol), and the provided `list_bounties` and `list_sweeps`, the record ids a `bounties/` or `sweeps/` listing holds (an `<id>.discovered.json` or `<id>.age` dropped). **The circle**: the one `--circle <admin>` names, else this install's own, the `circle.json` in the sweeper's own storage; it must name the key that holds it as its admin and list the sweeper. With neither, the error says to give a bounty's URL or `--circle`, and no refusal names the key `--circle` was given. `--target` without a URL is refused before anything is read, P2b's choice: a target id names a target of one bounty, and picking picks the target. **Open targets**: of the first 32 keys of the roster (`MAX_MEMBERS`: the admin, then each member, once each by key bytes; a longer roster is cut with a warning), the newest 16 bounty records each (`MAX_BOUNTIES_PER_MEMBER`, by id, from the whole listing sorted, so the order a server lists in does not matter). A bounty counts when `select::accept` would accept it with its URL: status `open`, and open to anyone, or closed and in its owner's own roster that lists the sweeper (that `circle.json` read once at most), or under `--circle` with the owner and the sweeper both in that circle. Each of its targets that `select::choose_targets` would take as `--target` is a candidate, so a target of an unknown kind, a malformed one, one the source's policy refuses, and every target of a bounty with ids that collide when case is ignored or with more than `MAX_TARGETS` (which `post` never writes) are not. **The counts**, read only when there is a candidate: the newest 32 sweep records of each of the same keys (`MAX_SWEEPS_PER_MEMBER`). A `running` or `done` record adds one to each candidate it names by its bounty and id; an `aborted` one (it swept nothing), one of an unknown status, one naming another bounty and one naming more than `MAX_TARGETS` ids (no `run` writes that many) count for nothing, and a stranger's `sweeps/` is never read. The sweeper's own bounties and sweeps count as any member's. **The pick**: the fewest sweeps, then the older bounty, the lower record id (its creation time; `createdAt` is opaque text), then the target earlier in that bounty's order, then the lower owner key, so the order of reads never decides. **Faults skip, they do not stop**: a listing that cannot be read or breaks the protocol skips that key's bounties or sweeps with a warning that names the key and the fixed reason; records that cannot be read or parsed are skipped, with one warning per key and kind that counts them and gives the first reason; an owner's `circle.json` that cannot be read skips their closed bounties, with a warning. Only the circle picked from is needed. When no target is open, `run` stops, after the warnings, with "there is no open bounty to pick: …; give a bounty's URL to run one". **Then** `run` shows the warnings and "Picked target `<tid>` of the bounty `<url>`, the least swept of the `<n>` open targets read in the circle (sweep records naming it: `<k>`)", checked values alone (the title and focus follow, sanitised, in the check's summary), and checks the pick exactly as for its URL and `--target`, reading the bounty again, so what it sweeps is decided by the same code on fresh records. **Bounds**, P2b's choice since 01 sets none: at most 32 `circle.json`s, 512 bounty records and 1024 sweep records, each capped at `MAX_RECORD_BYTES` before it is parsed, and 64 listings, read one after another. Limit: `list_dir` lists oldest first, with no `reverse`, and refuses a listing past 1000 entries whole, so a key whose `sweeps/` holds more than 500 sweeps (a record and a package each), or whose `bounties/` holds more than 1000 entries, has them skipped with a warning; the reverse paging 01 asks of roster polling belongs with `pull` ([P2c](P2c-cli-pull-done.md)).
- The sweep directory, `submit`'s first half, P2b's record (`submit/mod.rs`, `submit/sweep_dir.rs`, `submit/walk.rs`). `collect_sweep(cwd, run_dir, sweeper)` finds and checks the directory, walks it and reads `audit/`'s files, giving a `SweepDir` (its path, the `SweepRef` its marker points at, and the open directory handle) and an `AuditFiles` (the `SweepFile`s, and a `listing()` of sanitised lines for the file list printed before encryption); the command (its note below) calls it, so the module-wide dead-code expectation the module carried until then is gone. **A departure from the Build line**, which says to walk "with `symlink_metadata`": the rule is the same, but the walk is relative to open directory handles, through rustix (`=1.1.5`, feature `fs`, safe API only; fd-lock already has it in the build with `fs` on, so it adds no code; 03's Dependencies table lists it). An entry is looked at with `statat(AT_SYMLINK_NOFOLLOW)`, the handle-relative form of `symlink_metadata`; a directory is opened with `O_DIRECTORY | O_NOFOLLOW | O_NONBLOCK`, a file with `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`; and each handle is `fstat`ed and must be what was looked at (kind, device and inode; for a file also one link and the same size, checked again after the read, which reads at most one byte past that size). The agent may leave a process racing `submit`, and a path-based `lstat` then `open` cannot stop a directory on the path being swapped for a link to `~/.config/sweepky/` between the two calls; a handle cannot be swapped, and `O_NONBLOCK` keeps a FIFO swapped in from blocking the open. 02's "`submit` trusts nothing" bullet and 03's `submit` row say so. **Where.** "Canonicalise" is read as: canonicalise the `init` project's path, then resolve nothing below it. `--run-dir` must end in `sweeps/<id>` (`.` parts and a trailing `/` drop out; `..` or any other ending is refused, in fixed text that quotes nothing), `<id>` a record id; the path before `sweeps` is the project, which `fs::canonicalize` resolves (the human gives it, and a link above the project is theirs) and which must hold `init`'s marker, read with `init::read_project_marker`. Then `sweeps` and `<id>` are each opened by handle without following, so a symlinked `sweeps` or sweep directory is refused, not resolved into another project, and the walk starts from the handle that was checked. **The marker** is a pointer only: `.sweepky/sweep.json` in the sweep directory, read through handles, a regular file with one link and at most 64 KiB, parsed with `deny_unknown_fields` as exactly `run`'s shape (`schemaVersion`, `sweep`, `bounty`, `targets`, `playbook?`, each of its core type), serde's error going through `RecordError` so nothing is quoted. Its `sweep` must name this login's pubky and this directory's own id (`sweeps/<id>.json`, which `SweepRef` holds it to); nothing else in it is used. **Without `--run-dir`** the working directory must be the project; of at most 4096 entries in `sweeps/`, those named as a record id that are real directories with a regular `.sweepky/sweep.json` and nothing at `.sweepky/submitted` are the candidates. A link is never a candidate and never followed. One is picked; none, or several, is an error that lists the waiting ids, or the submitted ones when none waits (record ids, which print as they are). The stamp `.sweepky/submitted`, which the command writes after a success, is agent-writable, so it only narrows the pick, and `--run-dir` ignores it. **The walk** covers the whole sweep directory except `target/` directly in it and `scratch/` directly in `audit/agents/<agent>/`, the place Cloudflare's skill gives each hunter and verifier for target-controlled output (`SKILL.md` line 66 at `c1c8a8c`, `<output-dir>/agents/<agent-id>/scratch/`, fetched read-only on 2026-10-19; `audit/` is that output directory). Neither is looked at, so not even a link there is refused. Everywhere else, a symlink, a FIFO, a socket, a device and a regular file with more than one link are refused, naming the entry by its path in the sweep directory, written lossily and sanitised. Only `audit/` is read, because 02 and 03 name it as the agent's output directory; `scope.json`, `brief.md`, the marker and the stamp are checked but not read. Each directory's names are sorted, so the files come back in the same order every time, relative to `audit/` (`findings.json`, `notes/triage.md`), in `Zeroizing` buffers moved into the `SweepFile`s without a copy. A file under `audit/` whose path is not UTF-8, which a package path must be, is checked, not read, and listed as left out (APFS takes only UTF-8 names, so that test runs on ext4 alone). A sweep directory with no real `audit/` is refused. **Caps**, P2b's choices, each checked against the `statat` before the open, so a file past one is never read, nor is anything after it: at most 4096 entries in all (`MAX_ENTRIES`; directories count, `target/` and each skipped `scratch/` as one), at most 32 directories deep (`MAX_DEPTH`; `audit/` is 1), at most 8 MiB per file (`MAX_FILE_BYTES`), `findings.json` at most `MAX_FINDINGS_BYTES` (16 MiB), and `audit/`'s files together at most `MAX_PACKAGE_BYTES` (32 MiB of bytes on disk; `SweepPackage::build` still refuses a package whose JSON, escapes included, comes to more). Limits: a hard link is seen only by its link count, so one whose other name was later removed reads as a plain file; the project marker is read by `init`'s path-based reader, which checks the inode it opens but would wait on a FIFO swapped in, as `run`'s does; and the walk sees the directory as it stands, so a racing process can still change a file's bytes in place between the two `fstat`s without changing its size, which only garbles what the agent itself wrote.
- The owner's keys and their pin, P2b's record (`submit/owner_keys.rs`, `pins.rs`, `dirs.rs`), the file [P2a](P2a-cli-identity.md) left to P2b. **The pins file** is `owner-keys.json` in the config directory, `{schemaVersion: 1, owners: {<owner z32>: [{deviceId, recipient}]}}`: per bounty owner, the device id of each key `submit` last encrypted a sweep to and the `age1…` key its record held, in device-id order. It is keyed by owner and holds the key, as `installs.json` does, because a device id means something only beside its owner and a known id's record can be rewritten; and it is exactly the set accepted last time, not every key ever seen. The fields a newer Sweepky adds are kept on rewrite (at the top, in every other owner's entry, and in an entry pinned again), and a recipient that fails the strict parse makes the whole file invalid, refused in fixed text. It goes through `private_fs` as every config file does: 0600 in the 0700 config directory, a temp file renamed into place and the directory synced, read with a 64 KiB cap (`MAX_PINS_FILE_BYTES`, room for about three hundred owners of one key each, or fourteen of 31) and refused when loose, a link or over the cap; a pin that would take it past the cap is refused and the file left as it was. **Reading the keys** (`accept_owner_keys`, through `device::PublicKeys`, so `test_support::FakeKeyStore` serves the unit tests; the fake gains an id listed with no record behind it and a read that fails): `list_key_ids` within `ListLimits::DEFAULT`, the ids deduplicated and sorted, and a listing of more than `MAX_KEY_RECORDS` refused before any record is read (128, P2b's choice; revoked records count, since each is read too); then each record through `get_key` (capped at `MAX_RECORD_BYTES`) and `DeviceKey::from_json`. A revoked record drops out quietly, checked before `encryption_recipient`, so a revoked key of another `alg` is quiet too. The unrevoked records `encryption_recipient` accepts are the owner's keys, and only it turns a record into a recipient. A record listed but gone, one that does not parse (over the cap included), one of another `alg` and one whose recipient fails the strict parse are skipped, each with a warning on standard error that names its device id and gives core's fixed reason. A record whose read fails (a failed request, a refused redirect, the real reader's over-cap answer) stops the check, P2b's choice: skipping it would shrink the pin on a network fault, so the key would read as new when it came back, and would send a sweep the owner could not open on that install. An owner with no usable key is refused (nobody could read the sweep), and so is one with more than `MAX_OWNER_KEYS`, `MAX_RECIPIENTS` − 1 = 31, counted by record before the encryptor's dedupe, so this install's own key always fits. **The check** (`check_pin`, a pure function of the pin and the keys): no pin is first use, pinned without a word; every key pinned, its device id and its key alike (plain `==`: both are public), is unchanged, or shrunk when a pinned key is gone (revoked, removed or no longer usable), which rewrites the pin without a word; any other key is new, a new device id or a known one whose record holds another key. New keys are named by their device ids in a warning ("…published or rewritten since it last submitted to them: keys/<id>.json, …"), then `prompt::confirm` asks "Encrypt this sweep to the new keys as well?": yes re-pins the current set, anything else gives `None` and changes nothing, and under `--no-input` the question fails at once with the warning as the error's context, so the error names the ids. Since the pin is what was accepted last time, a key revoked and later rewritten as unrevoked warns again. Nothing printed holds a recipient, a label or any other text of a record. **The lock**: the check and the question run outside the writers' lock; the command calls `AcceptedKeys::write_pin` inside it, which writes only when the pin differs, through `pins::pin_owner_keys`, which reads the file again there and replaces this owner's entry alone, so a concurrent `submit` to another owner keeps its own. The third Done-when item is checked in its unit form against `FakeKeyStore`: the first check pins silently and a key added afterwards warns. The end-to-end test now checks its first half, B's first `submit` pinning A's key set; the key the test adds under A's `keys/` to make B's next `submit` warn is still to come. The command calls `owner_keys` and `pins`, so the dead-code expectation that covered them is gone.
- The submit command, P2b's record (`submit/mod.rs`, `submit/manifest.rs`, `sweep_dir.rs`, `remote.rs`). `submit [--run-dir <dir>] [--playbook <name>]` runs in this order. **Checks, writing nothing**: `--playbook`, refused first through `login`'s classifier (`identity::refuse_secret_material`), since a raw key in z-base32 or hex passes 01's playbook pattern and the record is public, then parsed as core's `Playbook`, both refusals in fixed text that quotes nothing; the sweeper, the pubky `login.json` names (`run`'s `logged_in_sweeper`, now `pub(crate)`); `collect_sweep`, the sweep directory and `audit/` (the note above); the sweep's own record through `PublicRecords::get_sweep`, read with no session as anyone would see it, which must exist and say `running` (`done` is "submitted already", `aborted` is final and says to start a new sweep with `sweepky run`, an unknown status is left alone, unprinted); and the bounty it names, from its owner's storage, which must exist. A bounty that is no longer `open` is a warning, not a refusal, P2b's choice: the sweep was run while it was open, and its owner can still read it. **The playbook** (`manifest::final_playbook`): `--playbook` when given; else the record's own, unless it is still `run`'s placeholder `unspecified` (`run::UNSPECIFIED_PLAYBOOK`, now `pub(crate)`), which is refused with a message asking for `--playbook`, before anything is built or written. **The manifest** (`manifest::build_manifest`, pure): the sweeper is this login; `bounty`, `targets` (in the record's order) and `startedAt` are the record's, never the marker's or `scope.json`'s; `targetShas` maps each target to `KnownTarget::reviewed_commit` of the bounty's target of that id (a pull request's head, a repo or commit target's `rev`); `finishedAt` is now; `extra` is empty. A record not `running`, one that names another bounty than the one read, and a bounty with no well-formed target of a known kind under one of the record's ids are refused, naming the target id alone. **The package**: `SweepPackage::build(manifest, audit.files)`; when `findings.json` was Cloudflare's, a line says it was converted, and each file it left out gets a warning naming it by its path under `audit/`, sanitised with room for `AttachmentPath::MAX_LEN`, and why (not UTF-8 text, or a path a package may not hold). **The owner's keys**: `accept_owner_keys` (the note above), outside the lock; a no to its question is the report "Not confirmed, so nothing was encrypted or uploaded; …" and writes nothing; under `--no-input` it is the error. **Then** the file list, the walk's `listing()` under a heading, on standard error; this install's own key, the public half of `device.key` read through `device::read_device_key` (unwrapped with the context's passphrase when the file is wrapped), the `DeviceIdentity`, which holds the secret, dropped as the function that read it returns; and `seal_package` to the owner's keys plus that one, at most `MAX_RECIPIENTS` because the owner's are at most one fewer. The package, sealed content in ordinary strings, is dropped as soon as it is sealed. **Under the writers' lock with a fresh session** (`with_writer_session` through the `FinishSweep` seam, which the tests implement for `FakeOwnStorage`, as `run` does its `PublishRecord`): `login.json` must still name the sweeper (else nothing is uploaded); the record is read back through `OwnStorage::get_own` and must still say `running`, for the same bounty and targets; the pin is written (`AcceptedKeys::write_pin`); `sweeps/<id>.age` is PUT; and the record read back is PUT again as `done`, with the manifest's `finishedAt` and the final playbook, every other field kept, those a newer Sweepky wrote included, through `run`'s `put_record` and `record_bytes` (now `pub(crate)`). `sha256` is left unset: 01 does not say what it is a digest of. So the lock is held around the sign-in, the pin write, the two PUTs and the sign-out, and never while the question waits on a person. **What a failure leaves**: every check above, a declined pin and an owner with no usable key change nothing; so do a failure to take the lock or sign in ("… still says running, so run submit again"), a transport error and a 429 on the `.age` PUT, which leave the record `running` with no flip, so `submit` can be run again (the pin may be written by then, which is local). A homeserver that refuses the package itself, a 413, a 507 or any other non-2xx answer but 429 (a 403 and a 5xx included, P2b's choice: an answer is the homeserver's word on the package, only a 429 asks to come back later, and the outcome stays a function of the status alone), flips the record to `aborted`, with `finishedAt` and the final playbook, under the same lock, and `aborted` is final, as 01's polling rule (only `running` sweeps are re-fetched) and 04's struck display assume: a new `run` is the retry, and a later `submit` of that sweep is refused saying so. A flip that fails too is said in the error, "… could not be changed to aborted and still says running (<the flip's error>)", before the refusal. A `done` PUT that fails after the `.age` went up leaves the record `running` and says so; a rerun seals and uploads again. **The messages** (`remote::upload_error`): 413 "the homeserver refused the upload (HTTP 413): the package is too large for this homeserver", 429 "… (HTTP 429): rate limited; try again later", 507 "… (HTTP 507): storage quota full, so there is no room for the package", anything else `write_error`'s (403's signup-token message, or the status alone), and a transport error `request_error`'s "network error (…)": fixed text and the status, never the server's words or the URL. **The stamp**, after the lock: `SweepDir::stamp_submitted` makes an empty, 0600 `.sweepky/submitted` with `openat(O_CREAT | O_EXCL | O_NOFOLLOW)` through the sweep directory's open handle, so it is never written through a link; anything already at that name counts as the stamp; a failure to stamp is a warning, since the sweep is done by then. **The report**: the sweep's URL, the `.age`'s size, how many of the owner's keys it was sealed to, and the playbook: checked values and counts alone. Nothing printed holds a byte of a finding or an attachment, a package or a server's words.
- Open, for [P3](P3-skill-and-sandbox.md): how an agent gets the human's confirmation for `post`. The answer is a line of standard input, and an agent running `post` from its Bash tool has no terminal there, so it reads the end of its input, which is no, and posts nothing (or fails under `--no-input`). But nothing stops an agent from piping `y` in itself, so the answer proves nothing about who gave it, and the confirmation 01 asks of the human is only as good as the skill's instructions. P3, which writes the skill's `post` role, settles it: for example by refusing to read the answer when standard input is not a terminal (`std::io::IsTerminal`, no `unsafe`), or by the skill handing the command to the human to run.
- Under `--identity` each command signs in afresh ([03](../03-cli-and-skill.md#two-ways-to-log-in), "Session per command"), so the two concurrent `submit`s hold separate sessions. This check shows only that the lock lets both finish; the lock unit test in [P2a](P2a-cli-identity.md) shows that it serialises them. The case the lock exists for, two commands sharing one bearer, needs a restored Ring token, so [P2d](P2d-cli-ring-login.md#done-when) checks it. That is why this check rewords the former P2 item "Two `submit`s run concurrently under one grant both succeed (the lock serialises them)".
