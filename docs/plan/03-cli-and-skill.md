## The `sweepky` CLI (v1)

A global `--testnet` flag (or `SWEEPKY_TESTNET=1`) selects the testnet client, the testnet HTTP relay (`http://localhost:15412/inbox`), the testnet homeserver as the default for `--identity` and as the default watch list. Without it the CLI talks to production. `SWEEPKY_HOME=<dir>` overrides the config and state directories so a script can run several identities side by side. A global `--passphrase-file <file>` names a file holding one line, the passphrase that wraps this install's secret files with age's scrypt recipient: `login` writes the identity file and device key it creates wrapped with it, and every command that reads a wrapped file needs it again. It takes a path, not the passphrase, and is meant for process substitution (`--passphrase-file <(pass show sweepky)`), which keeps the passphrase out of the argument list, the shell history and the disk, and leaves standard input free. An interactive prompt that does not echo is deferred: it needs a new crate or `unsafe` terminal calls. A global `--no-input` makes a command that would ask a question fail instead, saying what it would have asked: `post` asks the human to confirm a bounty's `title` and `brief` before it publishes them, `submit` asks before it encrypts to keys the owner added since the last submit, and `done` asks before it publishes credits its flags do not settle. Without the flag, the question goes to standard error and its answer is one line of standard input, read with a cap; only `y` or `yes` goes ahead.

| Command | Does |
|---|---|
| `login [--identity <name>] [--homeserver <pk>] [--signup-token <code>]` | Default: Pubky Ring, via a sign-in page the CLI opens in the browser. `--identity` creates a dedicated identity instead. See [Two ways to log in](#two-ways-to-log-in). Either way it generates this install's age key and publishes `keys/<deviceId>.json`. That first write is the check that this identity may write under `/pub/sweepky/` on its homeserver: a 403 means its signup token forbids the path (production's free IP-verified tokens allow only Paykit and Bitkit paths), a 507 means its quota is full; both abort with that explanation and suggest a dedicated identity. Then it reminds the user to back up `~/.config/sweepky/`. With `--passphrase-file`, the identity file and device key it creates are written wrapped with that passphrase |
| `logout` | Marks this device key revoked, then revokes the grant (or forgets the identity), then deletes the local files |
| `init <dir>` | Writes the sandbox settings and a `CLAUDE.md` for a sweeper project, a `.gitignore` with `sweeps/`, copies the `/sweepky` skill into `.claude/skills/`, and offers to install the Cloudflare playbook project-local at the pinned commit |
| `circle create\|add\|remove\|show` | Roster admin |
| `keys list\|revoke` | This identity's published device keys; `list` alarms on ids this owner's installs here, the ones that share this config directory, did not create ([02](02-encryption-and-safety.md#who-can-read-a-sweep)) |
| `post <draft.json> [--open]` | Reads the bounty draft, a JSON file the owner or their agent writes: `{title, focus?, brief, playbook?, targets: [{id?, kind: repo\|commit\|pr, repo, ref?, paths?, number?}]}`, with no other field allowed. A file holds a multi-line markdown brief and several targets, and keeps them off the command line, where clap would echo them in a usage error. The draft is untrusted: it is read up to the 1 MiB record cap, every error names a field or a position and quotes nothing, and the title, brief, focus and suggested playbook must be text the terminal sanitiser leaves unchanged ([P2b](phases/P2b-cli-sweep.md#notes) has the limits). Pins SHAs with an anonymous `git ls-remote` (every credential helper disabled, so a private repo fails instead of passing through saved credentials); for a PR, reads head and base from GitHub's unauthenticated API and stores the merge base; refuses non-public repos. Then it shows the bounty, sanitised, on standard error (title, focus, suggested playbook, each target with its pinned SHAs, and the brief) and asks before it writes `bounties/<id>.json`; only a yes signs in, and the report gives the bounty's `pubky://` URL. For an open bounty (`--open`, which changes the record's `open` field and nothing else), it finds the starting feed cursors after the yes, writes `bounties/<id>.discovered.json` with them and no sweeps right after the bounty, in the same session, and keeps them in the data directory for `pull`, never raising a lower one kept there ([P2c](phases/P2c-cli-pull-done.md#notes) has the order) |
| `run [<bounty-url>] [--target <tid>] [--circle <admin>]` | Terminal command, before the agent, run in the `init` project's own directory. Without a URL picks a target from the circle's open bounties with the fewest sweeps: of the open bounties of the members of this install's own circle (or the one `--circle` names), within fixed bounds, the target their sweep records name least, which it then checks and sweeps as for its URL and `--target` ([P2b](phases/P2b-cli-sweep.md#notes) has the rules and the bounds); with a URL, checks that the bounty's status is `open` and that it is marked `open` or its owner's own circle lists this sweeper. `--circle <admin>` names the circle checked instead, for any bounty: both the owner and the sweeper must be in it ([P2b](phases/P2b-cli-sweep.md#notes) records why). `--target` sweeps one target instead of every one this build can, and needs a URL. Writes `running`, fetches the pinned target into `./sweeps/<id>/target/<tid>/` (https only, exact SHA, depth 2, no submodules, no LFS), strips the repo's agent-instruction files, writes `scope.json`, the brief and, last, the per-sweep marker `sweeps/<id>/.sweepky/sweep.json`, all first in a staging directory under the data dir, then moved into the project whole. If the fetch or the marker fails, nothing reaches `sweeps/` and it flips the record to `aborted` |
| `submit [--run-dir <dir>] [--playbook <name>]` | Terminal command, after the agent. `--run-dir` names the sweep directory as `run` printed it, `sweeps/<id>`; without it, `submit` must run in the `init` project's own directory and picks the one sweep directory there that has a marker and no `.sweepky/submitted` stamp. Reads the marker to know which sweep it completes; walks the sweep directory under the rules in [02](02-encryption-and-safety.md#sweeper-safety), relative to open directory handles rather than by path, so nothing can be swapped in between a check and an open ([P2b](phases/P2b-cli-sweep.md#notes) has the caps); builds the package (one JSON document: manifest, findings, text attachments), converting Cloudflare output in `audit/` when detected; checks the owner's key set against the one pinned in `owner-keys.json`, and when a key is new warns of it by its device id and asks before it goes on (under `--no-input` it fails instead); encrypts to the owner's unrevoked keys plus its own; uploads `.age`; flips to `done` (or `aborted`). The manifest's bounty, targets and `startedAt` come from the sweep's own public record, which must say `running`, and each target's SHA from what `run` fetched, kept in the data directory, never from the sweep directory; a sweep whose bounty changed its targets since is refused. `--playbook` names the playbook the manifest and the `done` record carry; without it the record's own is kept, and a record that still names `run`'s placeholder `unspecified` is refused. The upload and the flip run under the writers' lock with a fresh session: a homeserver that refuses the package (413, 507 or any other non-2xx) flips the record to `aborted`, which is final, and a 429 or a network error leaves it `running`, to submit again ([P2b](phases/P2b-cli-sweep.md#notes) has the messages) |
| `pull` | Takes no argument and asks nothing. Reads the login and this install's device key before any request (a wrapped key needs `--passphrase-file`); then roster polling (reverse listings paged by cursor, 404 as empty, conditional re-GET of open bounties and `running` sweeps); the check of this owner's `keys/`, which alarms on unknown keys and, as loudly, on a check that cannot finish; the events-feed watcher for open bounties; decrypts each new `done` sweep to `~/.local/share/sweepky/<bounty>/`, untrusted content into `untrusted/`; groups findings by location, recording every sweeper per group; appends discovered sweeps to `bounties/<id>.discovered.json`, under the writers' lock and only when a file's sweeps change. The report gives the cursor each events feed was read from and where that came from, and each sweep's trust label, status and where it was stored, sanitised, never a finding ([P2c](phases/P2c-cli-pull-done.md#notes) has the order and the report) |
| `done <bounty> [--credit <pubky>]… [--no-credit <pubky>]…` | Rewrites the bounty with `status: "done"`, `doneAt` and `credits`. With no flags it proposes every sweeper whose done sweep contributed to at least one finding group `pull` wrote and asks for confirmation; the flags add or drop names, and it asks unless they name every proposed sweeper. Two sweepers in the same group are both proposed. The owner's own pubky is never proposed, and `--credit` refuses it ([P2c](phases/P2c-cli-pull-done.md#notes) has the rule and what it shows) |

Nine commands. There is no `watch`: the board is the live view, `pull` prints the state it finds, and the open-bounty homeserver watch list is a config entry. There is no `dev` group: `login --identity` doubles as the testnet stand-in for Ring. There is no `confirm`, `resolve` or `close`: triage is local. The public writes after `post` are `done` and the discovered-sweeps file.

`run` and `submit` are deliberately not for the agent. Both touch the network and the CLI's secrets, and the sweep directory is written by an agent that has read untrusted code, so `submit` treats it as hostile: a real direct child of the canonical `init` project's real `sweeps/`, its marker present and pointing at this login's own sweep, walked through open directory handles so that no link is followed and none is swapped in, regular files with one link only, `target/` and `audit/agents/*/scratch/` skipped, caps on entries, depth and sizes checked before anything is read, file list printed before encryption. Only `audit/`, the agent's output directory, is packaged. `findings.json` (required; converted from Cloudflare's format when that is what `audit/` holds) becomes `findings`, and every other UTF-8 text file in `audit/` becomes an `attachments` entry keyed by its path relative to `audit/`, which must pass `sweepky-core`'s lexical path check (`AttachmentPath`). Non-text files, and files at a path that fails the check, are skipped with a warning.

## Two ways to log in

Most people will use the pubky they already have in Ring, so that is the default. The dedicated identity exists for agents, CI, the testnet, and anyone who prefers one.

| | A. Pubky Ring (default) | B. CLI-held identity |
|---|---|---|
| Flag | none | `--identity <name>` |
| Whose identity | the one already in Ring | a new pubky the CLI creates, or one it created earlier under that name |
| Human steps | scan one QR, once | none |
| What is stored (0600, in `~/.config/sweepky/`) | the SDK's exported grant token: the grant scoped to `/pub/sweepky/:rw` plus the CLI's client key | the identity secret, optionally passphrase-wrapped (`--passphrase-file`), in a Sweepky file (not a Pubky recovery file) |
| Lifetime | two years from approval, fixed by the SDK (neither Ring nor the user chooses), or until revoked from Ring or by `logout`. `login` shows the expiry and the CLI warns within 30 days of it | until the file is deleted |
| If the file leaks | someone can write Sweepky records as you for up to two years unless you revoke, including a key record that lets them read later sweeps; `pull` alarms on that | that identity is theirs; your main identity is untouched |
| Homeserver | wherever the Ring identity lives | `--homeserver <pubkey>`; defaults to the testnet homeserver under `--testnet`, else to `homeserver.pubky.app`, which needs `--signup-token` |
| Session per command | restored from the token; writers serialise through a lock file because each restore replaces the previous bearer | a fresh sign-in per command, signed out on exit so two-year root grants do not pile up |

Credits accrue to whichever pubky is used; a dedicated identity can be mentioned from a pubky.app profile if its owner wants the two linked. B is the SDK's intended path for a key holder, not a Sweepky invention: its own signup example and end-to-end tests do exactly this. On production the CLI warns that `--identity` creates a separate public pubky and uses up a signup token.

**How the Ring sign-in looks.** `sweepky login` builds the SDK's grant flow (`PubkyGrantAuthFlow::builder`) with the relay URL from the network config, the default grant format and no encryption scopes, so today's Ring can approve it. The SDK's convenience constructor is not used: it never sets a relay, so a testnet login would post its approval through the production relay. The flow yields a `pubkyauth://` URL, then the CLI:

- Serves a single page on `127.0.0.1:<random port>/<random path>` and opens it in the default browser. The page shows a large QR of that URL, a "copy link" button worded "paste into Ring on your phone" (Ring reads the clipboard), what is being requested (`/pub/sweepky/:rw` and the client id `sweepky-cli`, which Ring displays as the app name), and a live status that flips to "approved, you can close this tab" when `await_approval()` returns.
- Prints the same URL and a small QR in the terminal as the fallback for SSH sessions and machines without a browser.
- After approval, checks that the granted capabilities include write on `/pub/sweepky/`. A future Ring may narrow what it approves; if so the CLI signs out and says what it needed.
- Hygiene: loopback only, random path so no other local page or process can guess it, serves exactly one flow, exits on approval or after a timeout. The URL carries the relay channel secret, so it is never logged or written to disk. The client id never changes between releases, because saved sessions are compared against it.

An agent can run `sweepky login` on a human's laptop: the page opens, the human scans, the agent carries on. Fully unattended setups use `--identity`.

**Refused:** importing an existing identity's secret or recovery file into the CLI. That secret controls the identity forever, including moving it to another homeserver, and this CLI runs under agents that read untrusted code. Ring exists to keep that secret off the laptop; `login` rejects recovery files (their first line is a fixed spec marker) and anything that looks like a raw key or mnemonic, and says why.

## The `/sweepky` skill

One skill, four roles: `run` (default), `post`, `pull`, `done`. `run` requires an `init` project; owners who pull open-bounty sweeps should summarise `untrusted/` in one too. The skill sets `disable-model-invocation: true`, because `post` and `done` make public writes and a human should type the command.

- Playbook-agnostic. In `run` it reads `./sweeps/<id>/scope.json` and the brief written by `sweepky run`, then follows the bounty's suggested playbook if installed in the project, otherwise whatever playbook the sweeper has configured, otherwise a plain careful review guided by the brief. It records which one it used.
- The request to the playbook is explicit, because Cloudflare's skill defaults to a guidance mode that writes no files and asks a question when the request is ambiguous: "full audit mode with report artifacts of `<absolute>/sweeps/<id>/target/<tid>/`, scoped to <paths or diff from scope.json>, profile <quick|standard>, output to the new directory `<absolute>/sweeps/<id>/audit/`; no prior runs, do not read other `sweeps/` directories". The output directory is new and outside the target, as the playbook requires; `sweeps/` is git-ignored.
- Carries the common findings schema and tells the agent to produce `findings.json` in it (or to leave Cloudflare's output in `audit/` for the CLI to convert).
- References `cloudflare/security-audit-skill` at commit `c1c8a8c1471069fb0e188eeaff69b8e8db6564a8` as the default suggestion for `security` bounties. The pinned, project-local install line is `npx skills@1.7.2 add https://github.com/cloudflare/security-audit-skill#c1c8a8c1471069fb0e188eeaff69b8e8db6564a8 --skill security-audit --agent claude-code --copy -y` run inside the init project with `DISABLE_TELEMETRY=1`; the plain `--global` form installs HEAD, pins nothing, and lands under `~/.agents`, which the sandbox cannot read. `init` records the installed commit so `submit` can write it into `manifest.playbook`. The skill is referenced, not vendored, and not required.
- Run flow: `sweepky run` in a terminal → `claude --setting-sources project,local` in the init dir → `/sweepky` → the agent exits → `sweepky submit` in the terminal. The agent never calls the CLI.
- Tells the agent the trust rule: untrusted sweeps count for attribution; their content is summarised, never merged, and their fixes are never applied without a human.
- In `done`, tells the agent to show the proposed credits with the finding groups each sweeper contributed to, and to let the human decide.

## Rust conventions (teaching notes, keep in code comments)

- `sweepky-core` does no network or file I/O, so it is unit-testable and could compile to WASM later. The package envelope is built from an in-memory list of files; the directory walk and its safety rules live in the CLI.
- Typed errors with `thiserror` in `sweepky-core`; `anyhow` only in `sweepky-cli`, library and binary alike, which only needs a good message.
- Secrets: `age::x25519::Identity` wipes itself on drop and has no `Debug`, so hold it directly; it does not implement `Zeroize`, so wrapping it in `SecretBox` would not compile. `SecretString` for the bech32 identity string, passphrases and the grant token (which the SDK hands back as a plain `String`, so move it in at once); `Zeroizing<Vec<u8>>` for file buffers.
- Open enums (`kind`, `status`, `alg`) are newtype `String`s with `as_known() -> Option<Known>` helpers, never closed serde enums, so unknown values from newer clients are skipped rather than failing the whole feed.
- Sealed content (findings, attachments, the unknown fields of a package or its manifest) never derives `Debug`. Its hand-written `Debug` prints structure and counts only, and destructures the value naming every field, with no `..` in the pattern, so a field added later does not compile until someone decides whether it may print. Types built from it, such as the finding groups and the merged report, print it through that `Debug`.
- Unknown top-level fields are preserved with `#[serde(flatten)] extra: Map` so rewrites do not drop them. The findings types name that map `unknown`, because a finding has a real `extra` field. `done` is a rewrite, so this is tested from the start.
- Pin `age` exactly: it is pre-1.0 and its docs call releases "beta". Leaving out `plugin` removes the code path behind its one security advisory (already patched in 0.12.1, so this is defence in depth).
- Pubkys are a newtype that parses both `pubky<z32>` and raw z32 and compares by bytes ([01](01-records-and-discovery.md#compatibility-rules-every-client-follows)).
