## Known limits (say them in the README)

- Only the owner can read findings. The circle, and everyone else, sees only that sweeps happened and who was credited.
- Key records are trusted as published. An active operator of the owner's homeserver, or someone holding the owner's leaked grant, can add a reading key; the owner's CLI alarms on keys it did not create and sweepers pin an owner's key set and warn on changes.
- Some identities cannot write `/pub/sweepky/` at all: production's free IP-verified signup tokens, the path Bitkit uses, allow only Paykit and Bitkit paths and 2 MB. `login` explains the 403 and suggests a dedicated identity.
- No age implementation has a published independent audit; some primitives it builds on had point-in-time audits of older versions.
- Metadata is public: paths, timing, padded sizes, recipient count (reveals how many devices the owner has).
- No forward secrecy: the ciphertext is public forever, and whoever holds the owner's key file later can read every sweep encrypted to it. Won't-fix findings stay out of the system. Rust age has no post-quantum recipients yet; `alg` on key records is the migration hook.
- Losing the owner's key file loses sweeps not yet pulled; pulled sweeps are on local disk.
- Production writes are permanent in practice: paths, timing and content hashes stay in the public event history, and anyone may have copied the ciphertext.
- Static review only, and under the Cloudflare skill's own rules a `confirmed` record needs an observed local result, so static-only sweeps yield essentially no `confirmed` records and no severities until a sandboxed runner exists.
- Finding ids are local to a sweep. Grouping by location is a heuristic the owner confirms; a bug reported at two sites is two groups until merged by hand.
- Pro/Max 5-hour windows: a `standard` whole-repo sweep can hit the limit mid-phase; scope with `paths` or use `quick`.
- Open-bounty discovery sees only homeservers on the watch list. Circle members can live on any homeserver. The board additionally needs members' homeservers to have a public domain and TLS.
- A dedicated CLI identity on the production homeserver needs a signup token from Pubky's gate, like any other identity.
- Self-credit is ignored, but an owner can still sweep their own bounty with a second identity and credit that one. Nobody can tell an alternate identity from a different person. The defence is that credits count only from owners the reader trusts, and the `known` label shows how many distinct owners the credits came from, so reputation built by one owner reads as `owners: 1`.
- Credits are per bounty, not per finding, so a sweeper's public record says how many bounties they helped on and nothing about severity.
- Each developer runs their own unmodified Claude Code on their own plan. The tool never reads or proxies Claude credentials.

## Production homeserver (as deployed on 2026-10-15)

Read from the `production` branch of `pubky/pubky-stack`, whose deployment workflow writes the live `config.toml` for `homeserver.pubky.app` and pins the homeserver at v0.16.1. Re-read it before relying on any value; it changes. The nginx front proxy's config is not in that repo.

| Setting | Value | Effect on Sweepky |
|---|---|---|
| Signup | token required | Option B on production needs `--signup-token`; Ring users already have an identity |
| Write paths and quota | per identity, from its signup token. SMS, Google and Lightning tokens: the 1024 MB default, any path. Free IP-verification tokens (what Bitkit creates): 2 MB, writable only under `/pub/paykit/` and `/pub/bitkit.to/` | Those identities cannot use Sweepky. `login`'s first key write returns 403 and the CLI says so; no endpoint lets a client read its own quota or paths |
| Write rate | 1 MB/s sustained, 20 MB burst, per signed-in user; throttles instead of rejecting | None |
| Grant sign-in and refresh (`POST /auth/grant/session`) | no request limit; a bearer lasts 1 h and the SDK re-mints it lazily | None. The 20/min rule is on the deprecated cookie `POST /session`, which Sweepky never uses |
| `/events/` reads | 3/s per IP, burst 10 | None for one poll per 30–60 s; the one-off cursor search stays inside the burst |
| `/events-stream` | 1/s per IP, burst 5 | Used once per open bounty to read the starting cursor |
| Deletes under `/pub/` | 5/s per path owner, burst 50 | None |
| Storage backend | Google Cloud Storage; a throttled write returns 429 with `Retry-After` | Retry on 429; never rewrite one path in a tight loop |

Signup tokens come from Pubky's gate service, Homegate (`homegate.pubky.app`): SMS verification, Google sign-in, a Lightning payment (1000 sats), or free IP verification. Ring also accepts operator invite codes (`XXXX-XXXX-XXXX`). Only the IP-verified token carries the restriction above.

**The token is obtainable as text, confirmed 2026-10-15 from the pubky.app source and live endpoints.** It is never only inside a QR code:

1. **Homegate's API returns it as JSON.** SMS: `POST /sms_verification/send_code` then `POST /sms_verification/validate_code` → `{valid, signupCode, homeserverPubky}`. Lightning: `POST /ln_verification` → a BOLT11 invoice, then `GET /ln_verification/<id>/await` → `{isPaid, signupCode, homeserverPubky}`. Homegate ships an `openapi.yaml` marked as AI-generated and possibly inaccurate; the shapes above come from the pubky.app client code.
2. **The web signup page has a "copy sign-up link" button.** The link is the SDK's signup deep link and carries the token as the plain `st` query parameter.
3. **Invite links** have the form `pubky.app/invite/<code>`; the code is in the URL.

Pubky Ring also has a plain text field for a signup token when adding a pubky to a homeserver, so users already handle these as text. v1 is bring-a-token: `login --identity … --signup-token <code>` plus a printed list of the ways to get one. A `--pay` helper driving the Lightning flow is a later addition only if Synonym confirms third-party use of Homegate's API; the IP-verification route is never automated.
